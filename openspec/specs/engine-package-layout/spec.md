## 目的
定义核心运行时逻辑在 `trpg_py` 包内的组织边界，以及 `trpg_py` 顶层与 `trpg_py.engine` 命名空间的公共导出契约。

## 需求

### 需求: 核心运行时逻辑必须归入 engine 命名空间
系统必须将执行器、原子操作分发和骰子运行时能力组织在 `trpg_py.engine` 命名空间下。状态路径存储能力必须归入 `trpg_py.store` 命名空间；`engine` 只消费该能力，而不是再维护独立的状态工具薄模块。新增核心运行时实现禁止继续以包根目录平铺模块作为唯一归属。

#### 场景:核心逻辑通过 engine 子模块组织
- **当** 开发者查看包内执行引擎相关实现
- **那么** 执行编排、操作处理和骰子能力位于 `trpg_py.engine` 下
- **那么** 状态路径读写与兼容辅助位于 `trpg_py.store` 下
- **那么** 后续新增同类运行时能力有明确的 `engine` 落点

### 需求: 公共 API 必须保留兼容导出
系统必须继续支持调用方从 `trpg_py` 顶层导入稳定公共 API，例如 `execute_task`、`validate_task_document`、`FixedDiceRoller` 和 `RandomDiceRoller`。系统禁止要求调用方通过额外的包根目录 facade 模块访问这些稳定入口。

#### 场景:现有顶层导入仍然可用
- **当** 调用方执行 `from trpg_py import execute_task, FixedDiceRoller`
- **那么** 导入成功
- **那么** 调用方无需因为内部迁移而修改这类稳定入口

#### 场景:顶层稳定入口不依赖额外 facade 模块
- **当** 开发者整理 `trpg_py` 包结构
- **那么** 顶层稳定 API 由 `trpg_py.__init__` 统一提供
- **那么** 不需要再维护 `trpg_py.executor` 或 `trpg_py.dice` 这类包根目录转发模块

### 需求: engine 命名空间必须提供显式引擎入口
系统必须允许调用方通过 `trpg_py.engine` 访问核心运行时入口，以支持后续按子模块扩展与集成。该命名空间必须至少暴露执行器入口和引擎常用构件，而不是仅作为空目录存在。

#### 场景:调用方可以从 engine 访问执行器
- **当** 调用方执行 `from trpg_py.engine import execute_task`
- **那么** 导入成功
- **那么** 该入口可用于执行现有任务文档

### 需求: engine 必须区分 core 与 combat 子包
系统必须在 `trpg_py.engine` 下明确区分通用执行框架与战斗领域逻辑。与任务执行、引用解析、报告模型和骰子运行时相关的通用能力必须归入 `engine.core`；与选择、检定、伤害、治疗、资源和效果相关的战斗语义必须归入 `engine.combat`。

#### 场景:开发者可以区分通用引擎与战斗领域代码
- **当** 开发者查看 `trpg_py.engine` 目录结构
- **那么** 能够明确看到 `engine.core` 与 `engine.combat` 的职责边界
- **那么** 不需要通过文件内容猜测某个模块属于运行时框架还是战斗规则

### 需求: combat 操作逻辑不得继续集中在单一 operations 文件
系统必须将战斗操作逻辑拆分为多个按职责组织的模块。系统禁止继续由单个大号 `operations.py` 同时承载目标选择、检定、伤害、治疗、效果、资源与相关辅助逻辑。

#### 场景:combat 操作按职责拆分
- **当** 开发者查看战斗操作实现
- **那么** 目标选择、检定结算、伤害治疗或效果处理至少有明确的模块划分
- **那么** 系统不得要求维护者继续在一个单文件中定位全部 combat 逻辑
