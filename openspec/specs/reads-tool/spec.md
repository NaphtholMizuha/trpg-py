# reads-tool 规范

## 目的
待定 - 由归档变更 add-reads-tool-for-planner 创建。归档后请更新目的。
## 需求
### 需求: reads 工具必须驻留在 agent.tools 命名空间
系统必须在 `trpg_py.agent.tools` 命名空间下提供名为 `read` 的工具能力，并且该能力必须可以被 Python 调用方直接导入和使用，而不是仅作为 planner 内部私有辅助逻辑存在。

#### 场景:调用方从 agent.tools 使用 read
- **当** 开发者为 planner 或其他 agent 组装工具集
- **那么** 可以从 `trpg_py.agent.tools` 访问 `read` 工具实现
- **那么** 调用方不需要自行封装状态值读取逻辑

### 需求: reads 工具必须包装 state-store 的 reads 能力
系统必须让 `read` 工具复用底层 `state-store.reads` 作为状态值读取来源，禁止维护一套与现有点路径语义不一致的独立读取实现。

#### 场景:read 返回路径对应的当前值
- **当** 调用方向 `read` 提交一个或多个点路径
- **那么** 工具会复用 `state-store.reads` 读取这些路径上的当前值
- **那么** 返回结果中的路径语义与现有状态存储接口保持一致

### 需求: reads 工具必须显式区分命中、无命中和错误
系统必须通过稳定的结构化语义区分“至少一个路径命中值”“请求路径均未命中”“工具执行错误”，禁止把这些情况统一折叠成模糊字符串或空对象。对于 planner 而言，`status=no_match` 必须足够稳定，能够驱动其把相关值视为当前 state 缺失的事实，而不是继续无限尝试同一读取主题。

#### 场景:read 返回命中结果
- **当** 调用方向 `read` 提交的路径中存在至少一个有效路径
- **那么** `read` 返回成功语义
- **那么** 返回体必须包含每个请求路径对应的读取结果

#### 场景:read 返回无命中结果
- **当** 调用方向 `read` 提交的路径均不存在
- **那么** `read` 返回无命中语义
- **那么** 调用方可以据此判断这是证据不足而非系统故障
- **那么** 返回体可以附带建议路径帮助有限修正
- **那么** planner 不得围绕同一无命中读取主题无限重试

#### 场景:read 返回错误结果
- **当** `read` 在执行过程中发生工具级异常
- **那么** `read` 返回明确错误语义
- **那么** 调用方可以区分该失败与正常无命中

### 需求: reads 工具必须保持只读且无副作用
系统必须要求 `read` 只读取当前状态值，而禁止写入状态、修改默认 world state、执行任务或引入其他运行期副作用。

#### 场景:planner 使用 read 做证据确认
- **当** planner 在规划过程中调用 `read`
- **那么** 当前 state 不得因本次调用而发生任何变化
- **那么** 返回结果只包含读取值、无命中建议或错误摘要

### 需求: reads 工具必须支持可手动运行的 smoke 脚本
系统必须提供一个位于 `smoke/test_reads.py` 的可手动运行脚本，用于让开发者直接观察 `reads` 的值读取、无命中和错误边界，而不是只能通过单元测试断言理解该工具行为。

#### 场景:开发者运行 reads smoke 脚本
- **当** 开发者在本地执行 `smoke/test_reads.py` 或等价命令
- **那么** 脚本会展示至少一次命中值读取结果
- **那么** 脚本会展示至少一次无命中结果
- **那么** 开发者可以从输出中看出 `reads` 的输入输出边界

### 需求: reads 工具每次调用必须使用 loguru 记录输入和输出
系统必须要求 `read` 工具在每次调用时通过 `loguru` 记录调用输入、输出状态和错误信息，禁止把这类运行期日志责任留给上层调用方临时实现。

#### 场景:read 成功读取值
- **当** 调用方向 `read` 提交有效路径且工具成功返回值
- **那么** 系统必须记录本次调用的输入路径摘要
- **那么** 系统必须记录返回状态和命中数量等结果摘要

#### 场景:read 无命中
- **当** 调用方向 `read` 提交的路径均不存在且工具返回无命中语义
- **那么** 系统必须记录本次调用的输入路径摘要
- **那么** 系统必须记录无命中状态
- **那么** 若返回了建议路径，日志中必须可观察到建议数量或样本摘要

#### 场景:read 调用失败
- **当** `read` 在执行过程中发生异常并返回错误语义
- **那么** 系统必须记录本次调用的输入路径摘要
- **那么** 系统必须记录错误类型和错误信息

### 需求: reads smoke 脚本必须支持正常嵌套 TOML 作为默认状态来源
系统必须让 `smoke/test_reads.py` 读取正常嵌套 TOML world state fixture 作为默认状态来源，禁止继续假设默认 fixture 顶层键本身就是点路径字符串。

#### 场景:开发者运行 reads smoke 脚本
- **当** 开发者执行 `smoke/test_reads.py` 且默认状态文件为 `config/world_state.toml`
- **那么** 脚本可以直接消费嵌套 TOML 解析结果作为 state
- **那么** `reads` 工具仍然使用既有点路径输入读取对应值

### 需求: read 工具在无命中时必须返回建议路径
系统必须要求状态值读取工具在 `status=no_match` 时返回少量结构化建议路径，帮助调用方从拼写错误、层级错误或近似字段名收敛到真实存在的 canonical 点路径；建议路径不得伪装成已成功读取的值。

#### 场景:read 对不存在路径返回建议路径
- **当** 调用方向 `read` 提交的路径均不存在
- **那么** 返回状态仍然必须是 `no_match`
- **那么** 返回体必须包含零个或多个建议路径
- **那么** 每条建议都必须使用当前 state 中真实存在的 canonical 点路径

### 需求: read 必须支持 planner 以批量方式确认同类状态值
系统必须保证 `read` 可以稳定消费一组 bare store paths，并让 planner 用一次调用确认同类候选值。禁止把同一取证主题强制拆成多个彼此独立的单路径读取，导致 planner 工具往返放大。

#### 场景:planner 批量读取同类候选值
- **当** planner 已经发现一组同类候选路径，例如多个 spell slot、多个已知法术或多个目标关键属性
- **那么** planner 可以在一次 `read` 调用中提交这组路径
- **那么** 返回体必须保留每个请求路径对应的结果
- **那么** 调用方可以基于这一组结果直接完成对比和收口

### 需求: read 的无命中结果必须可作为缺失事实证据消费
系统必须保证 `read` 在 `status=no_match` 时表达的是“当前 state 中未找到这些请求路径上的事实”，供 planner 直接消费为缺失事实证据。禁止把 `no_match` 设计成模糊的“建议继续猜更多路径”信号。

#### 场景:read 在建议修正后仍无命中
- **当** 调用方向 `read` 提交的路径均不存在
- **当** 返回体已提供建议路径
- **那么** 返回状态仍然必须是 `no_match`
- **那么** 调用方可以将该结果解释为当前 state 中缺失对应值事实
- **那么** 建议路径只作为有限修正线索，不得伪装成命中值
