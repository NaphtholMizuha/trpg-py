# fetch-keys-tool 规范

## 目的
待定 - 由归档变更 add-store-keys-and-fetch-keys-tool 创建。归档后请更新目的。
## 需求
### 需求:fetch_keys 工具必须驻留在 agent.tools 命名空间
系统必须在 `trpg_py.agent.tools` 命名空间下提供 `fetch_keys` 工具能力，并且该能力必须可被 Python 调用方直接导入和使用。

#### 场景:调用方从 agent.tools 使用 fetch_keys
- **当** 开发者为 planner agent 组装工具集
- **那么** 可以从 `trpg_py.agent.tools` 访问 `fetch_keys` 工具实现
- **那么** 调用方不需要直接编写 state 遍历逻辑

### 需求:fetch_keys 工具必须包装 store.keys 能力
系统必须让 `fetch_keys` 工具复用 `store.keys` 作为底层路径枚举来源，禁止维护一套独立且不一致的路径发现实现。

#### 场景:fetch_keys 返回路径枚举结果
- **当** 调用方向 `fetch_keys` 提交查询参数
- **那么** 工具会调用 `store.keys` 获取路径列表
- **那么** 返回结果中的路径格式与 `store` 点路径语义保持一致

### 需求:fetch_keys 工具必须支持全量与按范围查询
系统必须允许调用方在不提供范围参数时获取全量路径，并在提供范围参数（例如 `prefix`）时返回范围内路径。

#### 场景:fetch_keys 全量枚举
- **当** 调用方不提供范围过滤参数
- **那么** 工具返回当前 state 的可枚举路径集合

#### 场景:fetch_keys 按范围枚举
- **当** 调用方提供 `prefix` 等范围过滤参数
- **那么** 工具只返回匹配该范围的路径

### 需求:fetch_keys 工具必须显式区分成功、无命中和错误
系统必须通过稳定的结构化语义区分命中、无命中和执行错误，禁止把不同情况折叠成同一种模糊结果。

#### 场景:fetch_keys 范围内无路径
- **当** 调用方提交有效范围参数但没有匹配路径
- **那么** 工具返回无命中语义
- **那么** 调用方可以区分这是正常空结果而不是系统故障

#### 场景:fetch_keys 执行失败
- **当** 底层调用失败或输入参数非法
- **那么** 工具返回明确错误语义
- **那么** 调用方可以区分该失败与正常空结果

### 需求:系统必须提供可运行的 fetch_keys 演示测试脚本
系统必须提供一个位于 `smoke/test_fetch_keys.py` 的可直接运行测试脚本，用于让开发者直接观察 `store.keys` 与 `agent.tools.fetch_keys` 的核心行为，而不是仅依赖单元测试断言。

#### 场景:开发者运行演示脚本观察 fetch_keys 功能
- **当** 开发者在本地执行 `smoke/test_fetch_keys.py` 或等价命令
- **那么** 脚本会展示至少一次全量路径枚举结果
- **那么** 脚本会展示至少一次按范围枚举结果
- **那么** 开发者可以从脚本输出看出新能力的功能边界

### 需求:fetch_keys 演示脚本不必须接入统一项目配置
系统必须允许 `smoke/test_fetch_keys.py` 这类用于展示 `fetch_keys` 行为的仓库脚本继续使用脚本局部默认输入、fixture 文件或命令行参数，禁止把统一项目配置当作该演示脚本可运行性的强制前置条件。

#### 场景:开发者运行 fetch_keys 演示脚本
- **当** 开发者在本地执行 `smoke/test_fetch_keys.py` 或等价命令
- **那么** 脚本可以在不读取统一项目配置的前提下展示 `fetch_keys` 的核心行为
- **那么** 演示脚本仍然满足观察全量枚举与按范围枚举的目标

### 需求:fetch_keys 演示脚本必须从统一项目配置读取长期默认输入
系统必须要求 `fetch_keys` 的演示/测试脚本通过统一项目配置获取长期默认输入来源与默认演示参数，禁止继续把这些长期默认行为写死在脚本级常量中作为唯一真相。

#### 场景:fetch_keys 演示脚本读取统一默认输入
- **当** 开发者在不显式传参的情况下运行 `fetch_keys` 演示脚本
- **那么** 脚本从统一项目配置读取默认输入来源或默认演示参数
- **那么** 开发者可以通过统一配置调整脚本默认行为

### 需求:fetch_keys 返回语义必须可直接驱动 planner 分支决策
系统必须保证 `fetch_keys` 的 `ok/no_match/error` 三类返回语义稳定可区分，供 planner 直接判定“路径已确认”“信息不足”或“系统故障”，禁止将不同结果折叠为模糊输出。

#### 场景:planner 根据 no_match 触发澄清
- **当** planner 使用有效前缀调用 `fetch_keys` 且返回 `status=no_match`
- **那么** planner 可以将该结果解释为证据不足
- **那么** planner 可以触发 `needs_human` 而不是误判为系统错误

#### 场景:planner 根据 error 触发阻塞
- **当** `fetch_keys` 返回 `status=error`
- **那么** planner 可以将该结果解释为工具故障
- **那么** planner 可以进入 `blocked` 或降级流程

### 需求:fetch_keys 工具每次调用必须使用 loguru 记录输入和输出
系统必须要求 `fetch_keys` 工具在每次调用时通过 `loguru` 记录调用输入、输出状态和错误信息，禁止把这类日志责任留给上层调用方临时实现。

#### 场景:fetch_keys 返回命中路径
- **当** 调用方向 `fetch_keys` 提交有效参数且工具返回 `status=ok`
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录返回状态为成功以及路径数量等结果摘要

#### 场景:fetch_keys 无命中
- **当** 调用方向 `fetch_keys` 提交有效参数且工具返回 `status=no_match`
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录无命中状态

#### 场景:fetch_keys 调用失败
- **当** `fetch_keys` 在执行过程中发生异常并返回错误语义
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录错误类型和错误信息
