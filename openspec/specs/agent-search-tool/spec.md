## 需求
### 需求:agent search 工具必须驻留在 agent.tools 命名空间
系统必须在 `trpg_py.agent.tools` 命名空间下提供规则搜索工具能力，并且该能力必须可以被 Python 调用方直接导入和使用，而不是只作为某个 agent 框架内部的匿名回调存在。

#### 场景:调用方从 agent.tools 使用搜索能力
- **当** 开发者为 planner agent 组装工具集
- **那么** 可以从 `trpg_py.agent.tools` 访问搜索工具实现
- **那么** 不需要直接依赖 Qdrant 客户端细节来完成一次规则检索

### 需求:search 默认配置必须通过 api_key_env 获取 API 密钥
系统必须让 search 的统一配置默认通过 `api_key_env` 获取 API key，禁止要求调用方在项目配置文件中直接写入 search 密钥。

#### 场景:search 从统一配置读取默认密钥
- **当** 调用方通过统一配置构造默认 searcher 且未显式传入 `api_key`
- **那么** search 必须使用配置加载层解析后的环境变量密钥
- **那么** 调用方无需在配置文件中直接保存真实密钥

### 需求:search 工具必须根据 query 从 Qdrant 检索规则原文
系统必须允许调用方提供 query，并使用该 query 向 Qdrant 检索匹配的规则文本。系统返回的命中结果必须保留原始文本及必要元数据，禁止把检索结果替换为模型生成的摘要或规则推断。search 默认认证信息必须通过统一配置解析后的环境变量密钥获取，而不是要求调用方把密钥直接写入项目配置文件。

#### 场景:search 返回匹配原文
- **当** 调用方向 search 工具提交一个有效 query
- **那么** 工具会向 Qdrant 发起检索
- **那么** 返回结果中的每条命中都包含匹配原文
- **那么** 返回结果可以包含诸如标题、定位信息、分数等必要元数据
- **那么** 返回结果不得伪装成规则事实提取或 `TaskDocument` 建议
- **那么** 默认配置路径不得要求调用方在配置文件中直接保存真实密钥

### 需求:search 工具必须支持混合检索和 rerank
系统必须通过混合检索召回候选规则文本，并使用 reranker 对候选结果进行最终重排。系统禁止将第一版 `search` 工具降级为仅依赖单一召回路径的简单检索。

#### 场景:search 使用混合检索召回候选
- **当** 调用方向 search 工具提交一个有效 query
- **那么** 工具必须结合至少两类检索信号召回候选结果
- **那么** 系统不得只依赖单一关键词匹配或单一向量召回完成检索

#### 场景:search 使用 reranker 输出最终排序
- **当** 混合检索召回了多个候选结果
- **那么** 工具必须使用 reranker 对候选进行重排
- **那么** 返回给调用方的命中顺序必须反映重排后的最终排序

### 需求:search 工具必须显式区分成功命中、空结果和错误
系统必须通过稳定的返回语义区分成功命中、无命中和检索错误三种情况，禁止把这些情况统一折叠为同一种空列表结果。

#### 场景:search 无命中
- **当** 调用方提交一个合法 query 但 Qdrant 中没有匹配文本
- **那么** 工具返回空结果语义
- **那么** 调用方可以判断这是一次正常的无命中，而不是系统错误

#### 场景:search 检索失败
- **当** Qdrant 不可用、请求无效或底层检索过程失败
- **那么** 工具返回明确的错误语义
- **那么** 调用方可以区分该失败与正常无命中

### 需求:search 工具必须提供 LangChain tool 包装
系统必须为搜索能力提供 LangChain tool 包装，并且该包装必须复用同一套核心检索逻辑，而不是维护一份独立实现。

#### 场景:agent 通过 LangChain tool 调用 search
- **当** planner agent 将 search 注册为 LangChain tool 并发起调用
- **那么** 该调用会复用核心 search 检索能力
- **那么** 返回语义与直接调用核心 search 工具保持一致

### 需求:search 工具必须从统一项目配置读取默认运行参数
系统必须要求 search 工具的默认 API 接入参数、Qdrant 连接参数、集合名以及检索默认参数来自统一项目配置，而禁止继续以模块内环境变量读取和隐式默认值作为长期配置来源。

#### 场景:search 使用统一配置创建默认搜索器
- **当** 调用方未显式提供 search 的连接与检索参数
- **那么** 系统从统一项目配置读取默认 API、Qdrant 和检索配置
- **那么** 默认搜索器行为与项目配置文件保持一致

### 需求:search 模块必须通过统一配置入口消费配置
系统必须要求 search 模块通过集中配置入口获取默认运行配置，而禁止在模块内部直接读取 `OPENAI_*`、`SILICONFLOW_*`、`QDRANT_*` 等环境变量作为长期行为来源。

#### 场景:search 模块不直接解析独立环境变量
- **当** search 需要默认 API key、base URL 或 Qdrant URL
- **那么** search 通过统一配置入口读取对应字段
- **那么** search 模块不再自行解析独立环境变量集合

### 需求:search 工具必须提供可手动运行的集成测试脚本
系统必须提供一个位于 `smoke/test_search.py` 的可手动运行脚本，用于让开发者直接验证 search 工具的真实检索效果，而不是只依赖自动化测试或底层客户端调用。

#### 场景:开发者手动验证 search 效果
- **当** 开发者在本地执行 `smoke/test_search.py` 并提供 query 或其他参数
- **那么** 脚本调用系统现有 search 能力完成一次检索
- **那么** 输出中可以观察命中、无命中或错误等结构化结果

### 需求:search 返回语义必须可直接驱动 planner 分支决策
系统必须保证 `search` 的 `ok/no_match/error` 三类返回语义稳定可区分，供 planner 直接判定“规则证据充分”“规则证据不足”或“检索故障”，禁止将不同结果折叠为同一空结果。

#### 场景:planner 根据 no_match 识别规则证据不足
- **当** planner 提交合法 query 且 `search` 返回 `status=no_match`
- **那么** planner 可以将该结果解释为规则证据不足
- **那么** planner 可以转入 `needs_human` 或回退策略

#### 场景:planner 根据 error 识别检索故障
- **当** `search` 返回 `status=error`
- **那么** planner 可以将该结果解释为检索链路故障
- **那么** planner 可以进入 `blocked` 或恢复流程

### 需求:search 工具每次调用必须使用 loguru 记录输入和输出
系统必须要求 `search` 工具在每次调用时通过 `loguru` 记录调用输入、输出状态和错误信息，禁止只在调用方脚本中临时打印或完全不留运行期日志。

#### 场景:search 成功返回命中结果
- **当** 调用方向 `search` 提交有效 query 且工具返回命中结果
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录返回状态为成功以及命中数量等结果摘要

#### 场景:search 无命中
- **当** 调用方向 `search` 提交有效 query 且工具返回 `status=no_match`
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录无命中状态

#### 场景:search 调用失败
- **当** `search` 在检索过程中发生异常并返回错误语义
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录错误类型和错误信息
