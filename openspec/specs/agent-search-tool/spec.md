## 需求
### 需求: agent search 工具必须驻留在 agent.tools 命名空间
系统必须在 `trpg_py.agent.tools` 命名空间下提供规则搜索工具能力，并且该能力必须可以被 Python 调用方直接导入和使用，而不是只作为某个 agent 框架内部的匿名回调存在。

#### 场景:调用方从 agent.tools 使用搜索能力
- **当** 开发者为 planner agent 组装工具集
- **那么** 可以从 `trpg_py.agent.tools` 访问搜索工具实现
- **那么** 不需要直接依赖 Qdrant 客户端细节来完成一次规则检索

### 需求: search 默认配置必须通过 api_key_env 获取 API 密钥
系统必须让 search 的统一配置默认通过 `api_key_env` 获取 API key，禁止要求调用方在项目配置文件中直接写入 search 密钥。

#### 场景:search 从统一配置读取默认密钥
- **当** 调用方通过统一配置构造默认 searcher 且未显式传入 `api_key`
- **那么** search 必须使用配置加载层解析后的环境变量密钥
- **那么** 调用方无需在配置文件中直接保存真实密钥

### 需求:search 工具必须根据 query 从 Qdrant 检索规则原文
系统必须允许调用方提供 query，并使用该 query 向 Qdrant 检索匹配的规则文本。系统返回的命中结果必须保留原始文本及必要元数据，禁止把检索结果替换为模型生成的摘要或规则推断。对于当前 `trpg_knowledge` 知识库，search 必须以 payload 中的 `text` 作为命中正文来源，并稳定暴露 `book`、`path`、`doc_type`、`title`、`parent_id`、`section_titles` 等当前 schema 字段，而不是依赖旧版 `content`、`file`、`parent_content` 等历史字段作为长期契约。search 默认认证信息必须通过统一配置解析后的环境变量密钥获取，而不是要求调用方把密钥直接写入项目配置文件。search 还必须允许调用方显式提供查询模式，以表达这次检索更偏向术语定位、术语加结算信息，还是纯规则场景。

#### 场景:search 返回匹配原文
- **当** 调用方向 search 工具提交一个有效 query
- **那么** 工具会向 Qdrant 发起检索
- **那么** 返回结果中的每条命中都包含匹配原文
- **那么** 返回结果可以包含诸如标题、定位信息、分数等必要元数据
- **那么** 返回结果不得伪装成规则事实提取或 `TaskDocument` 建议
- **那么** 默认配置路径不得要求调用方在配置文件中直接保存真实密钥

#### 场景:search 返回当前知识库的稳定来源字段
- **当** `search` 命中了当前 `trpg_knowledge` 集合中的节点
- **那么** 每条命中的正文必须来自 payload 的 `text`
- **那么** 每条命中的元数据必须可以稳定提供 `book`、`path`、`doc_type`、`title`
- **那么** 每条命中的元数据必须在存在时保留 `parent_id` 和 `section_titles`
- **那么** 调用方不得被迫依赖 `file`、`type`、`parent_content` 等历史键名来理解命中来源

#### 场景:search 接受显式查询模式
- **当** 调用方向 `search` 提交一个有效 query 并附带 `mode`
- **那么** 工具必须接受该 `mode` 并继续返回同样稳定的原文和元数据字段
- **那么** 调用方不得为了表达检索意图而创建额外的并行 search 工具

### 需求: search 工具必须支持混合检索和 rerank
系统必须通过混合检索召回候选规则文本，并使用 reranker 对候选结果进行最终重排。系统禁止将第一版 `search` 工具降级为仅依赖单一召回路径的简单检索。对于当前父子节点知识库，reranker 必须以候选子节点正文为主进行排序，父节点正文只能在最终命中确定后作为补充上下文回收，禁止在候选重排前把完整父块批量注入 reranker 造成长文本污染。

#### 场景:search 使用混合检索召回候选
- **当** 调用方向 search 工具提交一个有效 query
- **那么** 工具必须结合至少两类检索信号召回候选结果
- **那么** 系统不得只依赖单一关键词匹配或单一向量召回完成检索

#### 场景:search 使用 reranker 输出最终排序
- **当** 混合检索召回了多个候选结果
- **那么** 工具必须使用 reranker 对候选进行重排
- **那么** 返回给调用方的命中顺序必须反映重排后的最终排序

#### 场景:search 先对子节点 rerank 再补父节点上下文
- **当** 混合检索召回了多个候选结果，且其中部分候选带有 `parent_id`
- **那么** 工具必须先基于候选子节点正文完成 reranker 重排
- **那么** 工具不得在候选重排前向 reranker 批量注入完整父节点正文
- **那么** 工具必须在最终命中顺序确定后，才按需回收父节点正文并填入 `parent_text`

### 需求: search 工具必须支持当前 RAG 知识库的父子节点上下文回收
系统必须在命中带有 `parent_id` 的子节点时，根据该 `parent_id` 尝试回收父节点正文，并以可选 `parent_text` 形式返回给调用方，禁止继续把 payload 内嵌 `parent_content` 作为当前知识库的长期依赖。

#### 场景:命中子节点后回收父节点正文
- **当** `search` 命中了一个 payload 含有 `parent_id` 的子节点
- **那么** 系统必须尝试根据该 `parent_id` 读取父节点
- **那么** 父节点读取成功时，该命中的返回结果必须包含 `parent_text`
- **那么** 命中的 `text` 仍然必须保持为子节点正文，而不是被父节点正文替换

#### 场景:父节点上下文不可回收时降级返回
- **当** `search` 命中了子节点，但 `parent_id` 缺失、父节点不存在或父节点读取失败
- **那么** 系统不得因此把整次检索改判为 `error`
- **那么** 系统必须继续返回该子节点命中结果
- **那么** 该命中可以不包含 `parent_text`

### 需求: search 工具必须显式区分成功命中、空结果和错误
系统必须通过稳定的返回语义区分成功命中、无命中和检索错误三种情况，禁止把这些情况统一折叠为同一种空列表结果。

#### 场景:search 无命中
- **当** 调用方提交一个合法 query 但 Qdrant 中没有匹配文本
- **那么** 工具返回空结果语义
- **那么** 调用方可以判断这是一次正常的无命中，而不是系统错误

#### 场景:search 检索失败
- **当** Qdrant 不可用、请求无效或底层检索过程失败
- **那么** 工具返回明确的错误语义
- **那么** 调用方可以区分该失败与正常无命中

### 需求: search 工具必须提供 LangChain tool 包装
系统必须为搜索能力提供 LangChain tool 包装，并且该包装必须复用同一套核心检索逻辑，而不是维护一份独立实现。

#### 场景:agent 通过 LangChain tool 调用 search
- **当** planner agent 将 search 注册为 LangChain tool 并发起调用
- **那么** 该调用会复用核心 search 检索能力
- **那么** 返回语义与直接调用核心 search 工具保持一致

### 需求: search 工具必须从统一项目配置读取默认运行参数
系统必须要求 search 工具的默认 API 接入参数、Qdrant 连接参数、集合名以及检索默认参数来自统一项目配置，而禁止继续以模块内环境变量读取和隐式默认值作为长期配置来源。

#### 场景:search 使用统一配置创建默认搜索器
- **当** 调用方未显式提供 search 的连接与检索参数
- **那么** 系统从统一项目配置读取默认 API、Qdrant 和检索配置
- **那么** 默认搜索器行为与项目配置文件保持一致

### 需求: search 模块必须通过统一配置入口消费配置
系统必须要求 search 模块通过集中配置入口获取默认运行配置，而禁止在模块内部直接读取 `OPENAI_*`、`SILICONFLOW_*`、`QDRANT_*` 等环境变量作为长期行为来源。

#### 场景:search 模块不直接解析独立环境变量
- **当** search 需要默认 API key、base URL 或 Qdrant URL
- **那么** search 通过统一配置入口读取对应字段
- **那么** search 模块不再自行解析独立环境变量集合

### 需求: search 返回语义必须可直接驱动 planner 分支决策
系统必须保证 `search` 的 `ok`、`no_match` 和 `error` 三类返回语义稳定可区分，供 Context Agent 与主 agent 直接判定“规则证据充分”“规则证据不足”或“检索故障”。系统禁止将不同结果折叠为同一空结果。

#### 场景:Context Agent 根据 no_match 识别规则证据不足
- **当** Context Agent 提交合法 query 且 `search` 返回 `status=no_match`
- **那么** Context Agent 可以将该结果解释为规则证据不足
- **那么** 主 agent 可以据此决定继续补充上下文或返回 `needs_human`

#### 场景:Context Agent 根据 error 识别检索故障
- **当** `search` 返回 `status=error`
- **那么** Context Agent 可以将该结果解释为检索链路故障
- **那么** 主 agent 可以进入 `blocked` 或恢复流程

### 需求: search 工具每次调用必须使用 loguru 记录输入和输出
系统必须要求 `search` 工具在每次调用时通过 `loguru` 记录调用输入、输出状态和错误信息，禁止只在调用方脚本中临时打印或完全不留运行期日志。

#### 场景:search 成功返回命中结果
- **当** 调用方向 `search` 提交有效 query 且工具返回命中结果
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录返回状态为成功以及命中数量等结果摘要

#### 场景:search 无命中
- **当** 调用方向 `search` 提交有效 query 且工具返回 `status=no_match`
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录无命中状态

#### 场景:search 调用失败
- **当** `search` 在检索过程中发生异常并返回错误语义
- **那么** 系统必须记录本次调用的输入参数摘要
- **那么** 系统必须记录错误类型和错误信息

### 需求:search 工具必须支持显式查询模式
系统必须允许调用方通过 `mode` 显式表达规则检索意图，支持 `term`、`balanced`、`semantic` 三种模式。系统禁止继续把所有规则检索都隐含视为同一种 HyDE 风格查询。

#### 场景:调用方以术语模式检索明确规则名
- **当** 调用方向 `search` 提交一个带有明确规则术语的查询，并将 `mode` 设置为 `term`
- **那么** 工具必须接受该模式并按正常检索流程返回结果
- **那么** 调用方可以将该查询理解为用于定位规则条目身份

#### 场景:调用方以平衡模式检索术语加结算细节
- **当** 调用方向 `search` 提交一个保留明确术语锚点且补充少量结算信息的查询，并将 `mode` 设置为 `balanced`
- **那么** 工具必须接受该模式并按正常检索流程返回结果
- **那么** 调用方可以将该查询理解为同时服务于规则身份定位与少量结算信息确认

#### 场景:调用方以语义模式检索规则场景
- **当** 调用方向 `search` 提交一个没有可靠术语锚点的规则场景描述，并将 `mode` 设置为 `semantic`
- **那么** 工具必须接受该模式并按正常检索流程返回结果
- **那么** 调用方可以将该查询理解为场景化规则检索，而不是明确术语定位

### 需求:search 工具必须记录查询模式以支持调试和评估
系统必须在每次 `search` 调用的日志或可观察输出中记录实际使用的 `mode`，禁止让调用方只能从 query 文本猜测本次检索意图。

#### 场景:search 成功返回命中时记录 mode
- **当** 调用方向 `search` 发起带有 `mode` 的检索并成功返回命中结果
- **那么** 系统必须记录本次调用使用的 `mode`
- **那么** 系统必须继续记录 query、limit、fetch_k 和结果摘要

#### 场景:search 无命中或失败时记录 mode
- **当** 调用方向 `search` 发起带有 `mode` 的检索且返回 `no_match` 或 `error`
- **那么** 系统必须记录本次调用使用的 `mode`
- **那么** 调试人员必须能够从日志中区分这是术语检索、平衡检索还是语义检索

### 需求:search 返回结果必须可直接作为 Context Agent 的规则证据输入
系统必须保证 `search` 的返回结构足够稳定，使 Context Agent 可以直接将命中结果整理为规则证据，而不是先把返回值降格为自由文本再二次解析。

#### 场景:Context Agent 消费 search 结果
- **当** Context Agent 调用 `search` 获取规则原文
- **那么** 返回结果必须保留原始命中文本和必要元数据
- **那么** Context Agent 可以直接基于这些字段构造高信息密度规则证据
