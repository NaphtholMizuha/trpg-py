## 上下文

当前 ask 能力已经分成两层：agent/runtime 产出统一 `AskRequest` / `AskResponse` 契约，Python CLI 作为第一个交互宿主负责展示和采集回答。但现有 Context Agent eval 路径只做到“生成 ask 请求并展示出来”，还没有把 ask 真正变成一次完整的 CLI 交互回合。

这导致一个很具体的缺口：开发者可以看见 `ask_requests`，却不能在同一次 eval 运行中用默认值、候选选项或自定义输入完成回答，也就无法验证 ask 契约在真实终端里的可用性。对于一个以手动调试和高信息密度观察为目标的 eval 脚本来说，这条链断在“看见问题”而不是“完成回答”，会让 ask 能力很难被真正检验。

这次设计只补 eval / CLI 调试链路，不把范围扩到完整 planner 多轮恢复执行。也就是说，我们要解决的是“让 DM 在 eval 中完成 ask 回合”，而不是“让整个 planner 自动拿着答案继续跑到 resolution”。

## 目标 / 非目标

**目标：**
- 让 Context Agent eval 脚本在交互式 Python CLI 中真正执行 ask 交互，而不只是展示 ask 请求。
- 让 eval 脚本支持 ask 请求中的候选选项、默认值和自定义输入，并回填为统一的 `AskResponse` 列表。
- 让一次 eval 运行同时展示 ask 请求和 ask 回答，便于开发者人工核对。
- 让非交互模式保持可预测：不能交互时明确跳过 ask 采集，而不是卡住或隐式失败。
- 补齐自动测试，确保 CLI ask 交互不会因为后续重构退化回“只显示、不采集”。

**非目标：**
- 本次不实现 planner / resolution 的自动重新调用。
- 本次不引入新的交互宿主，例如 HTTP、Web UI 或 Typer。
- 本次不把 ask 扩成复杂问卷或多页表单系统。
- 本次不改变 ask 的统一协议，只消费已有契约。

## 决策

### 决策 1：将 eval ask 闭环定义为“展示 + 采集 + 回显”，而不是“展示 + 继续执行”

本次 eval 脚本的闭环到 `AskResponse` 为止。脚本在同一次运行中：
- 展示 `AskRequest`
- 采集 DM 回答
- 生成并展示结构化 `AskResponse`

但不在本次 change 中自动用这些回答重跑 planner 或 resolution。

选择理由：
- 这正好补齐当前最明显的断点，范围清晰。
- 这样可以先把 ask 契约在 CLI 中验证扎实，再单独提案“回答后继续执行”。
- 避免把一次小而明确的交互闭环升级成多轮 runtime 改造。

备选方案：
- 直接在本次中实现回答后自动重新进入 planner。未采用，因为这会把范围扩到多轮状态管理和恢复执行。
- 继续只展示 ask 不采集。未采用，因为这无法验证 ask 工具是否真的可用。

### 决策 2：Context Agent eval 脚本直接复用统一 CLI ask adapter

ask 交互逻辑应继续集中在通用 Python CLI ask adapter 中，eval 脚本负责在合适时机调用它，而不是在脚本里复制一套输入解析和默认值处理逻辑。

选择理由：
- 避免 eval 脚本和 ask adapter 两边维护不同交互细节。
- 统一默认值、自定义输入、选项渲染的行为。
- 以后其他 CLI 调试入口如果也要消费 ask，可直接复用。

备选方案：
- 在 eval 脚本里内联输入逻辑。未采用，因为会制造第二套 ask 交互实现。

### 决策 3：非交互模式下显式跳过 ask 采集，并保留 ask 请求展示

当 eval 脚本运行在 `--json`、管道或非 TTY 场景时，系统必须继续输出 `ask_requests`，但不尝试采集交互输入。若需要显式提示，可在结果中保留说明字段或在人类可读输出中说明“未进入交互模式”。

选择理由：
- 自动化环境和留档环境不能被交互阻塞。
- ask 请求本身仍然是有价值的调试输出，不应因为不能交互而被隐藏。
- 这能保持 CLI 手动调试与非交互脚本调用的行为边界清晰。

备选方案：
- 在非交互模式下直接报错。未采用，因为这会让 JSON/管道留档场景变差。
- 在非交互模式下偷偷选择默认值。未采用，因为这会把“人工确认”伪装成系统确认。

### 决策 4：eval 输出必须同时展示 ask 请求与 ask 回答

一旦采集到了 `AskResponse`，eval 输出必须能直接看见：
- 问题 ID / 问题文本
- 可选项与默认值（请求视图）
- 实际选择或自定义输入（回答视图）

这样开发者在单次运行结果里就能审查“系统问了什么”和“DM答了什么”。

选择理由：
- 只展示回答会丢失问题上下文。
- 只展示问题会看不见实际交互是否成功。
- 这与 eval 脚本“高信息密度观察”的定位一致。

备选方案：
- 只在内部返回 ask 响应，不在输出中展示。未采用，因为手动 eval 的价值就在于可见性。

## 风险 / 权衡

- [交互路径和非交互路径行为分叉] → 通过明确的 TTY / `--json` 判定与测试覆盖保持行为稳定。
- [CLI adapter 改动导致 ask 默认值或自定义输入行为漂移] → 用独立测试固定默认选择、自定义输入与请求回显。
- [用户误以为 eval 已经会自动继续执行 planner] → 在文档和输出中明确本次闭环止于 `AskResponse`，不自动重跑后续链路。
- [eval 脚本承担过多业务逻辑] → 继续让 ask 解析逻辑留在通用 adapter，脚本只负责编排与展示。

## 迁移计划

1. 修改 `context-agent-eval-script` 相关规范，明确 eval 脚本必须在 CLI 中执行 ask 交互并展示回答。
2. 修改 `agent-ask-tool` 规范，补充 Python CLI eval 路径对 `AskResponse` 采集的要求。
3. 修改 `planner-e2e-eval-suite` 规范，强调 ask 交互闭环属于子 agent 专项 eval，不进入端到端批量回归主职责。
4. 实现阶段复用现有 CLI ask adapter，让 eval 脚本在交互式场景中调用它并回显结果。
5. 补齐自动测试与手动示例，验证默认值、自定义输入和非交互跳过行为。

回滚策略：
- 若交互采集路径在短期内不稳定，可保留 ask 请求展示能力并临时关闭回答采集入口，但不得破坏统一 ask 契约。
- 若输出格式引发兼容问题，可先以新增字段方式扩展 eval 结果，避免破坏现有 JSON 消费者。

## 开放问题

- `AskResponse` 是否需要在 eval 结果中额外携带来源时间戳或交互顺序，以便未来做多轮回放。
- 非交互模式下是否需要一个明确的布尔字段标识“存在 ask 但未采集回答”，还是仅靠 `ask_responses` 为空即可。
- 后续“采集完 ask 回答后继续执行”的 change 是否应优先接回 Context Agent 复跑，还是直接接到 planner 主入口。
