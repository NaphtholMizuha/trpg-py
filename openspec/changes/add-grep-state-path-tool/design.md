## 上下文

当前 planner 的状态取证链路主要依赖 `list(prefix)` 做路径发现，再使用 `read(paths)` 做值确认。这种接口对“已知 canonical 路径或前缀”的调用方很友好，但对大模型并不自然：模型通常知道自己想找“谁的 AC / HP / spell slots / attack modifier”，却不知道状态树里精确的 bare store path 应该如何命名。结果是 planner 会围绕近似前缀和近似路径重复 `list` 与 `read`，把预算浪费在路径猜测上，而不是证据收口上。

现有 `list` 和 `read` 已经有明确职责与稳定语义：
- `list` 负责路径枚举与建议。
- `read` 负责精确路径值确认。

这次变更不打算让它们承担模糊检索职责，而是在两者之间补一个更适合 planner 思维方式的“grep 风格叶子路径发现”工具。

## 目标 / 非目标

**目标：**
- 提供一个关键词驱动的叶子路径检索工具，让 planner 不需要先猜中 prefix 就能得到一批相关候选路径。
- 让 planner 默认采用 `grep -> read` 的状态发现链路，在需要时才回退到 `list` 做补充导航。
- 保持现有 bare store path 与 `TaskDocument` `$ref` 语义不变，不引入新的状态路径协议。
- 保持 `grep`、`list`、`read` 三者职责分离，避免功能重叠导致语义模糊。

**非目标：**
- 不替换现有 `list` 或 `read`。
- 不改变底层 `state-store` 的点路径读写语义。
- 不在本次变更中引入 embedding / 向量索引等重型检索基础设施。
- 不让 `grep` 直接返回状态值或代替 `read` 做值确认。

## 决策

### 决策 1：新增独立的 `grep` 工具，而不是继续扩展 `list(prefix)`

`list` 的契约是“按范围枚举 canonical 路径”，它适合前缀导航，不适合语义模糊查找。如果把关键词检索、相关性排序和前缀枚举都揉进同一个工具，planner 将更难理解何时该用哪种模式，现有 `list`/`fetch_keys` 规范也会被迫扩大职责边界。

因此新增独立 `grep` 工具：
- 输入一组关键词或短查询。
- 基于现有 state 的 canonical 点路径集合做轻量模糊匹配。
- 仅返回叶子路径候选、分数/排序和匹配原因。

考虑过的替代方案：
- 直接扩展 `list(prefix)` 支持关键词参数：拒绝。会混淆“范围枚举”和“模糊检索”两种不同语义。
- 让 planner 先 `list` 全量再自行筛选：拒绝。会继续放大 token 和工具成本。

### 决策 2：`grep` 只检索叶子路径，不返回中间节点，也不返回值

planner 真正需要的是“下一步可读什么”，而不是状态树的完整层级结构。因此 `grep` 只返回叶子路径候选，避免把模型再次拉回结构导航问题。

同时，`grep` 不返回值：
- 避免与 `read` 的职责重叠。
- 避免把“可能匹配的路径”误当成“已确认的事实”。
- 让 planner 必须通过一次显式 `read` 完成值确认。

考虑过的替代方案：
- `grep` 同时返回值预览：暂不采用。虽然能减少一次调用，但会把工具边界从“发现路径”扩展为“发现 + 读取”，并弱化 `read` 的唯一事实来源角色。

### 决策 3：匹配策略采用轻量关键词/路径段模糊匹配，而不是引入重型检索系统

本次工具面向的是运行时 state 路径，而不是大规模文档库。canonical 点路径数量相对可控，且路径自身已经包含较多结构信息，因此优先使用轻量方案：
- 对路径按 segment/token 切分。
- 对查询关键词做规范化。
- 使用 token overlap、路径段命中和简单别名/同义词映射做打分。
- 返回有限数量的 top-k 叶子路径。

这样可以在不引入额外外部依赖的前提下，显著改善路径发现精度。

考虑过的替代方案：
- 使用 embedding 检索路径：暂不采用。复杂度和依赖成本过高，不适合先验证 planner 行为收益。
- 使用纯 substring contains：不完全采用。过于脆弱，难以覆盖缩写、同义词和 segment 顺序差异。

### 决策 4：planner 默认优先 `grep`，`list` 降为补充导航工具

在新的规划策略中：
- 当 planner 只知道“想找哪些事实”而不知道 canonical 路径时，必须优先使用 `grep`。
- 当 `grep` 已返回一组候选叶子路径时，planner 必须优先批量 `read` 一次收口。
- 仅当 planner 需要观察某个命中 root 下的结构，或 `grep` 无法缩小候选范围时，才允许回退到 `list`。

这样做的原因是，当前主要预算浪费来自“围绕 prefix 反复试探”，而不是“确认值”本身。

### 决策 5：保留现有 no_match / error 语义风格，并让 `grep` 结果能直接驱动 planner 收口

`grep` 需要和现有 `search`、`list`、`read` 一样，稳定区分：
- `ok`
- `no_match`
- `error`

其中：
- `ok` 表示找到一组相关候选路径。
- `no_match` 表示当前 state 中没有足够相关的叶子路径，planner 可将其视为缺失状态发现证据。
- `error` 表示工具故障。

`grep` 的返回体还需要暴露每个候选的匹配原因，帮助 planner 理解“为什么是这些路径”，减少再次试探。

## 风险 / 权衡

- [关键词匹配过宽，返回噪音路径过多] → 通过叶子路径限制、top-k 截断和匹配原因输出降低选择成本。
- [关键词匹配过窄，漏掉真实路径] → 保留 `list` 作为补充导航路径，并允许后续增量扩展别名表。
- [planner 同时拥有 `grep` 和 `list` 后仍然乱用工具] → 在 planner prompt 和规范中明确“默认 `grep -> read`，`list` 仅作补充”。
- [新工具与 `read` 职责模糊] → 明确 `grep` 禁止返回值，事实确认仍必须通过 `read` 完成。

## Migration Plan

1. 新增 `grep` 工具规范与实现，保证其可从 `trpg_py.agent.tools` 访问，并提供 smoke 验证入口。
2. 将 `grep` 接入 planner 默认工具集与提示词，引导 planner 优先用它做状态路径发现。
3. 保留 `list` 与 `read` 现有接口，避免破坏现有调用方。
4. 在 smoke / 调试链路中对比加入 `grep` 前后的 planner 工具调用轨迹，确认状态发现回合数下降。
5. 若效果不理想，可回滚 planner prompt 中对 `grep` 的优先级要求，同时保留新工具实现而不影响既有链路。

## Open Questions

- 关键词输入是仅接受 `terms: list[str]`，还是同时支持单个 `query: str` 并在工具内部切词？
- 别名/同义词映射是否需要在首版就覆盖常见字段（如 `armor class -> ac`, `health -> hp`, `spell slot -> spell_slots`）？
- `grep` 的匹配原因应暴露到什么粒度，既帮助 planner 选择，又不让返回体过长？
