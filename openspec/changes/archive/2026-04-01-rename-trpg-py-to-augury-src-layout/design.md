## 上下文

当前仓库有三类 Python 内容同时平铺在仓库根目录附近：
- 正式运行时代码位于 `trpg_py/`
- 手动 smoke 验证脚本位于 `smoke/`
- 自动测试位于 `tests/`

这套布局目前还能工作，是因为仓库根目录天然落在 Python 模块搜索路径中，且多个 smoke 脚本会在启动时手工把仓库根插入 `sys.path`。但这带来了几个长期问题：
- 包名、目录名和项目名之间缺乏清晰边界，`trpg_py` 既是源码根又是公共导入命名空间。
- `smoke/` 与 `tests/` 分散在根目录，导致“哪些属于源码树、哪些属于验证入口”不够直观。
- 目录迁移、发布或 IDE/测试工具配置更依赖当前工作目录和隐式导入行为，而不是标准的 `src` 布局。

这次设计的核心不是改业务逻辑，而是建立稳定的源码布局真相：`src/` 是唯一 Python 源码根，`augury` 是唯一长期包命名空间，smoke 与 tests 也在 `src/` 下清晰分层。

## 目标 / 非目标

**目标：**
- 将运行时代码迁移到 `src/augury/`，并以 `augury` 作为唯一公共导入命名空间。
- 将手动 smoke 脚本迁移到 `src/smoke/`，将自动测试迁移到 `src/tests/`。
- 更新打包、测试发现、脚本入口和文档命令，使新布局可直接支撑本地开发与验证。
- 清理对“仓库根目录天然可导入”和“旧包名 `trpg_py`”的长期依赖。

**非目标：**
- 不改变 engine、planner、RAG、store 或工具本身的业务语义。
- 不在本次设计中引入第二套长期兼容包命名空间，同时维护 `trpg_py` 与 `augury` 两份真相。
- 不重做 smoke 脚本的人类可读输出风格或测试框架本身，只调整其位置与导入方式。
- 不借这次目录迁移顺手重构无关模块边界。

## 决策

### 决策 1：采用完整的 `src/` 布局，而不是只移动主包

本次不是仅把 `trpg_py/` 移到 `src/`，而是同时把 `smoke/` 和 `tests/` 一并收敛到 `src/` 下，形成：
- `src/augury/`
- `src/smoke/`
- `src/tests/`

这样做的原因是，用户明确希望三类 Python 代码都进入 `src/`，并且这能把“与 Python 执行直接相关的目录”统一收敛到一个源码根下。相比“只迁移主包，保留根级 smoke/tests”，这种布局的边界更一致，也更方便 IDE、测试发现和文档表达。

考虑过的替代方案：
- 只把 `trpg_py/` 移到 `src/`：不满足用户对 `smoke` 和 `tests` 一并迁移的要求。
- 保持根级 `smoke/` 和 `tests/`：继续保留当前布局的不一致。

### 决策 2：以 `augury` 作为唯一长期包命名空间

迁移后正式包目录为 `src/augury/`，公共导入、内部模块导入和规范中的长期命名空间都以 `augury` 为准。我们不把 `trpg_py` 保留为长期并行入口，只允许在迁移过程中临时改写导入。

这样做的原因是，若继续长期并存 `trpg_py` 与 `augury`，会让文档、规范、导入示例和后续新代码再次产生双重真相，削弱这次重构的价值。

考虑过的替代方案：
- 仅改目录名，不改导入命名空间：与用户目标不符，也无法真正完成包重命名。
- 长期保留 `trpg_py -> augury` 兼容包装：短期平滑，但会把旧名字重新固化进规范和新代码。

### 决策 3：同步更新打包与测试发现，使导入依赖 `src` 布局而不是根目录巧合

迁移后需要同时调整项目元数据和测试/脚本运行方式，让 `augury` 可从 `src/` 稳定发现，而不是继续依赖“从仓库根直接执行所以刚好能导入”的隐式行为。Smoke 脚本若仍支持直接脚本执行，也必须围绕 `src` 根定位，而不是继续假设包就在仓库根旁边。

考虑过的替代方案：
- 只移动文件，不改测试与脚本 bootstrap：会立即导致导入失败或继续散落新的 `sys.path` 修补逻辑。
- 强制所有脚本都只能通过特殊环境变量运行：会增加开发者心智负担。

### 决策 4：文档与规范命令统一切换到 `src/smoke` 和 `src/tests`

README、OpenSpec 和相关示例命令将以新路径为唯一长期入口，例如：
- `python -B src/smoke/test_engine.py fireball`
- `python -B -m unittest discover -s src/tests -v`

这样做的原因是，目录重构如果只改代码不改命令文档，很容易让后续维护者沿着旧路径继续新增脚本或测试。

考虑过的替代方案：
- 文档保留旧命令并靠说明解释：会制造额外过渡期和歧义。
- 额外保留根级包装脚本：短期方便，但会重新引入双入口问题。

### 决策 5：配置治理边界随包名同步迁移到 `augury`

统一配置规范中“包内长期运行配置”的治理对象将从 `trpg_py` 切换为 `augury`。同时，引用 planner smoke 默认 world state 的脚本路径也更新为 `src/smoke/test_planner.py`，确保配置约束与新布局一致。

考虑过的替代方案：
- 只改代码目录，不改配置规范文字：会让 OpenSpec 中的配置边界与实际实现脱节。

## 风险 / 权衡

- [导入路径全面变更导致回归面广] → 通过一次性更新内部导入、文档命令、测试断言和 smoke 入口，避免半迁移状态长期存在。
- [`src` 布局下脚本直接运行更依赖正确 bootstrap] → 在任务中显式包含 pyproject、测试发现和脚本入口调整，避免只做目录搬运。
- [外部使用者可能仍依赖 `trpg_py` 导入路径] → 在提案中明确标记为 breaking，并把 README 与规范全部改到新路径，减少误导。
- [同时迁移 `smoke` 与 `tests` 会增加一次性改动量] → 这是用户明确目标；通过先建立目录和发现规则，再批量改导入与命令，控制实现顺序。

## Migration Plan

1. 新增 `src-project-layout` 规范，声明 `src/augury`、`src/smoke`、`src/tests` 为新的唯一长期布局。
2. 修改 package layout、tool/planner smoke 与 project config 相关规范，把 `trpg_py` 和根级 `smoke/` 契约切换到 `augury` + `src/`。
3. 实现阶段先创建新目录和项目配置支撑，再迁移运行时代码与导入路径。
4. 随后迁移 `smoke/` 与 `tests/`，更新命令、文档和自动测试发现路径。
5. 完成验证后移除旧目录与旧命名空间残留，避免长期双入口。

回滚策略：若迁移中出现较大导入或工具链兼容问题，可临时在单个实现分支中恢复旧目录名继续排查，但长期目标仍是只保留 `src/augury`、`src/smoke` 与 `src/tests`。

## Open Questions

- 项目发布名是否也同步从 `trpg-py` 切换为 `augury`，还是仅切换导入命名空间？本设计默认两者对齐，以减少认知分裂。
- 是否需要提供极短期的 `trpg_py` 兼容包装用于外部调用方过渡？本设计默认不保留长期兼容层，但实现前可再确认一次发布节奏。
