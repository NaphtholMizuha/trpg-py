## 上下文

当前仓库中 `trpg_py.agent` 仍是占位状态，尚未形成稳定的 agent 工具层，但后续 planner agent 已经明确需要两类基础能力：读取当前 state 的可引用表面，以及检索规则原文。此次变更只落地第一批工具中的 `search`，并且明确它的职责边界是“根据 query 从 Qdrant 检索规则文本”，而不是执行规则推理或直接生成 `TaskDocument`。

这次设计涉及两个新的集成边界：

- 与 Qdrant 的外部检索集成
- 与 LangChain tool 协议的包装集成

因此需要在实现前把模块边界、返回形状和错误语义定清楚，避免后续 planner agent 直接绑死在某个底层客户端或某个特定的工具返回文本格式上。

## 目标 / 非目标

**目标：**
- 在 `trpg_py.agent.tools` 下建立首个可复用的工具模块组织方式。
- 提供一个面向 Python 调用方的 `search` 工具实现，输入 query 后可执行混合检索和 rerank，并返回最相关的匹配原文。
- 提供一个 LangChain tool 包装，使 agent 可以直接把该能力注册到工具列表中。
- 固定工具的结构化输出，至少覆盖成功命中、空结果和检索失败三类情况。
- 保持搜索工具只返回原始命中文本与必要元数据，不在工具层引入规则归纳逻辑。

**非目标：**
- 不在本次设计中实现 `fetch_keys` 或其他 agent 工具。
- 不在本次设计中实现规则事实抽取、法术展开或 `TaskDocument` 生成。
- 不要求本次变更完成 Qdrant 数据入库流水线，但默认允许复用现有 embedding / sparse / rerank 能力完成检索。
- 不要求 LangChain 成为工具层唯一入口；LangChain 只是包装层，不是核心实现所在。

## 决策

### 决策: 核心搜索逻辑与 LangChain 包装分层

核心搜索逻辑必须先以普通 Python 接口落在 `trpg_py.agent.tools` 内，再由单独的适配层包装为 LangChain tool。这样可以避免后续测试、脚本调用或非 LangChain agent 只能绕过工具层使用底层客户端。

考虑过的替代方案：
- 直接只实现 LangChain tool：接入快，但会把核心能力与某个 agent 框架耦死，后续测试和复用都会变差。
- 先实现纯函数，不提供工具包装：模块更纯，但不能满足当前用户要求，也会把 LangChain 适配工作推迟到后续。

### 决策: 工具返回结构化 payload，而不是自由文本

搜索工具必须返回结构化 payload，例如 `status`、`hits`、`error` 等字段，而不是只返回一段拼接文本。planner agent 需要根据是否命中、是否为空结果、是否发生错误来决定下一步行为；这些分支不应依赖模型重新解析自然语言提示。

考虑过的替代方案：
- 只返回字符串：实现最简单，但不利于 planner 判断空结果和错误。
- 返回规则事实或摘要：会把推理职责推到工具层，违背本次范围。

### 决策: 命中结果保留原文和必要元数据，但不做规则推断

每个命中结果应至少包含原文文本、定位信息和检索分数。工具禁止输出“这代表一次 dex save”或“建议生成 damage.apply”这类推断性字段。这样可以保持工具职责稳定：它只提供证据，不替 planner 做决策。

考虑过的替代方案：
- 返回结构化规则事实：对 planner 更友好，但与当前“LLM 自行推理”的产品方向冲突。
- 只返回原文，不返回任何元数据：会削弱 planner 对证据质量和来源的判断能力。

### 决策: search 第一版采用混合检索 + reranker，而不是单一路径检索

搜索工具第一版应直接采用混合检索策略，以提高规则原文场景下的召回质量和排序稳定性。这里的“混合检索”指至少结合 dense 和 sparse 两类召回信号，并在候选集合上使用 reranker 做最终重排。这样可以同时覆盖专有名词、规则关键词、自然语言描述和近义表达，减少 planner 因检索遗漏而做出错误推理。

考虑过的替代方案：
- 仅做单一路径 Qdrant 查询：实现更小，但对规则书这类既依赖术语也依赖语义的问题，召回鲁棒性偏弱。
- 只做混合召回不做 rerank：可用，但最终排序质量更容易受召回噪声影响，尤其在多条规则相似时更明显。

### 决策: Qdrant 客户端和集合配置通过注入提供

搜索工具不应在模块内部硬编码 Qdrant 地址、集合名或混合检索策略细节。实现应允许调用方在构造工具时注入 Qdrant 客户端和必要配置，例如 collection 名称、默认 `top_k`、召回数量、是否启用 rerank，以及相关 embedding / rerank 客户端或适配器。这样可以让测试使用替身客户端，也能让生产环境按不同规则集或索引进行配置。

考虑过的替代方案：
- 模块内读取全局环境变量并创建全部检索依赖：使用方便，但测试和多集合场景不灵活。
- 每次调用都传完整连接信息：最灵活，但调用噪音太大，不适合作为 agent 常用工具。

### 决策: 优先参考 multi-prompt 分支中的现有检索与工具模式

本次实现应优先参考本仓库 `multi-prompt` 分支中的已有代码，尤其是 `src/tools/rag.py` 中的混合检索与 rerank 封装，以及 `src/tools/toolkit.py` 中 `SearchTool` 的 LangChain `BaseTool` 包装方式。这样可以复用已经验证过的工程模式，例如懒加载客户端、工具输入 Schema、混合召回链路和工具包装结构，同时避免在当前分支从零摸索集成方式。

不过当前变更不会直接复制 `multi-prompt` 的全部实现，而是有选择地吸收其中的稳定模式：

- 复用的方向：Qdrant 客户端懒加载、混合召回与 rerank 分层、检索器与工具包装分层、Pydantic 输入 Schema、LangChain `BaseTool` 集成方式。
- 不直接照搬的部分：当前分支以自由文本字符串作为工具输出的做法、与 `src.tools`/`TrpgToolkit` 强耦合的目录布局，以及任何与当前仓库包结构不匹配的模块组织。

考虑过的替代方案：
- 完全忽略参考实现，从零设计：概念更纯，但会重复探索已经存在的工程细节。
- 直接原样移植 `multi-prompt`：实现速度快，但会把当前分支引入过多不在本次范围内的依赖和返回格式耦合。

### 决策: 空结果与系统错误必须显式区分

无命中属于正常业务结果，必须通过 `status=no_match` 或等价语义返回；Qdrant 不可用、参数非法或响应异常属于错误，必须以 `status=error` 或明确异常语义区分。planner agent 对这两类情况的后续行为完全不同，因此不能混成同一种“空列表”。

考虑过的替代方案：
- 无命中和错误都返回空数组：简单但不可恢复。
- 对所有异常都抛 Python 异常：对库调用方便，但对 LangChain tool 来说不利于稳定返回给 agent。

## 风险 / 权衡

- [Qdrant 返回载荷结构不稳定] → 在设计中限制工具只依赖一小组稳定字段，并在适配层统一映射为项目内部 payload。
- [混合检索和 rerank 增加外部依赖与运行复杂度] → 将召回、重排和最终 payload 映射分层封装，便于独立替换和测试。
- [返回原文可能过长，增加 token 成本] → 通过 `top_k`、单条长度限制和可选上下文控制输出规模。
- [LangChain tool 包装可能引入额外输入输出约束] → 保持核心搜索接口独立，包装层只做参数和返回值适配。
- [后续 `fetch_keys`、其他工具可能需要统一返回风格] → 本次先确立 `status + payload` 的通用模式，为后续工具保持一致性。
- [参考分支包含较完整的检索链路] → 优先复用其中的混合检索与 rerank 模式，但将具体依赖与输出适配为当前仓库的 `agent.tools` 结构和结构化 payload。

## Migration Plan

本次变更是新增能力，不涉及现有执行器或 store 接口迁移。落地顺序应为：

1. 建立 `trpg_py.agent.tools` 包结构和搜索模块。
2. 实现核心混合检索搜索接口，包括 dense / sparse 召回与 rerank 重排。
3. 实现 LangChain tool 包装，并确保其复用核心接口而非复制逻辑。
4. 为成功、空结果和错误路径补充测试。

如果后续需要回滚，可以移除 agent 工具包和相关依赖，而不会影响当前 engine/store 能力。

## Open Questions

- `search` 的 query 输入是否只接受单个字符串，还是第一版就允许 `ruleset`、`top_k` 之类的显式参数。
- LangChain tool 应返回结构化字典，还是序列化后的 JSON 字符串；这取决于项目计划使用的 LangChain 版本和 agent executor 习惯。
- Qdrant 中单条命中的 payload 是否天然包含 `title`、`section`、`locator` 等元数据；如果没有，需要先约定一个最小 payload 模式。
- 混合检索链路里 dense embedding、sparse embedding 和 reranker 的具体提供方是否完全沿用 `multi-prompt`，还是在当前仓库抽象成可替换适配器。
