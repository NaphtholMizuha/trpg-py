## 上下文

当前项目的运行配置已经开始在多个模块内分散生长。`planner` 使用一组 `DEFAULT_*` 和 `ENV_*` 常量自行解析模型、超时和工具预算；`search` 直接在构造器中读取 `SILICONFLOW_*`、`OPENAI_*`、`QDRANT_*` 等环境变量。这样的方式在单模块阶段还能接受，但随着 planner、search、后续更多 agent 能力和存储/检索配置继续增加，系统会逐渐出现以下问题：

- 配置源不唯一：有的配置来自构造参数，有的来自环境变量，有的来自模块常量
- 默认值不透明：调用方很难知道当前生效的到底是哪套默认配置
- 配置解析逻辑重复：每个模块都要自己处理默认值、环境变量和类型转换
- 测试与生产语义漂移：测试可以直接传参数，生产却依赖环境，行为不易审计

用户希望把这些分散配置统一收敛到一个外部 TOML 文件，并确保项目级配置入口只有一处。这意味着这次变更不仅是“换个读取方式”，而是要建立一个新的跨模块配置架构。

## 目标 / 非目标

**目标：**
- 定义全项目唯一配置源，使用根目录外部 TOML 文件承载运行配置。
- 提供 `trpg_py.config` 之类的统一配置模块，集中负责配置加载、类型校验和共享访问。
- 让 `planner` 与 `search` 改为消费统一配置，而不是继续在模块内部维护 `DEFAULT_*` 和环境变量解析逻辑。
- 保留测试和特殊场景的显式注入能力，但确保业务运行路径只有一个统一配置入口。
- 明确配置缺失和配置非法时的失败语义，避免静默回退到隐藏默认值。

**非目标：**
- 不在本次设计中把所有历史代码一次性迁移到配置系统，只覆盖当前已存在的明显运行配置入口。
- 不在本次设计中引入多环境配置合并、远程配置中心或热更新机制。
- 不在本次设计中继续支持“每个模块各自解析环境变量”作为长期方案。
- 不在本次设计中把 `pyproject.toml` 复用为业务运行配置文件，避免与打包元数据耦合。

## 决策

### 决策: 使用单一根目录 `config/config.toml` 作为唯一运行配置文件

项目运行配置统一落在仓库根目录 `config/config.toml`，由该文件承载 planner、search 等运行参数。这样配置文件位置显式、独立于打包元数据，也便于今后直接查看、审计和版本管理。

考虑过的替代方案：
- 继续使用环境变量：接入快，但配置源分散、类型不透明。
- 把业务配置塞进 `pyproject.toml`：文件更少，但会把运行时配置与项目元数据耦合在一起。
- 每个模块一个配置文件：局部清晰，但违背“全项目仅此一份配置”的目标。

### 决策: 提供集中配置模块和类型化配置模型

系统应新增集中配置模块，例如 `config/config.config`，负责：
- 读取 `config/config.toml`
- 将其解析为类型化配置模型
- 暴露统一访问入口
- 在配置非法时快速失败

这能让 planner/search 共享同一份解析和校验逻辑，而不是各自重复处理字符串到数值/布尔/字典的转换。

考虑过的替代方案：
- 只提供字典加载函数：实现更小，但调用方仍要自己处理字段校验。
- 在每个模块局部定义自己的 Pydantic 模型：可行，但会把统一配置再次拆散。

### 决策: 运行时默认不再以环境变量作为业务配置真相

运行时默认以统一 TOML 文件为配置真相。允许测试或高级调用方通过显式注入配置对象/配置路径覆盖，但常规业务路径不再把环境变量作为主要配置来源。这样可以真正实现“项目只有一份配置”的要求，而不是把 TOML 变成另一层包装。

考虑过的替代方案：
- 保留“环境变量 > TOML > 默认值”的多级优先级：兼容性好，但会重新引入多真相。
- 完全禁止显式注入：最纯粹，但测试和嵌入式调用场景会变得笨重。

### 决策: planner 与 search 迁移为消费统一配置，而不是保留模块级默认常量

`planner` 当前的模型、超时、重试和工具预算，`search` 当前的嵌入模型、Qdrant 地址、集合名和 rerank API 参数，都应迁移到统一配置。模块内部允许保留少量结构常量（例如协议字段名），但不再保留项目级运行配置常量作为长期事实来源。

考虑过的替代方案：
- 只迁移 planner：范围小，但 search 仍会继续分散配置。
- 只新增配置模块，不迁移现有模块：概念上更纯，但无法真正解决当前问题。

### 决策: 配置加载失败时应快速失败，而不是静默回退

若配置文件缺失、字段非法或必要配置缺少，系统应返回明确错误而不是继续使用隐式默认值。这样虽然短期更严格，但能避免运行时在错误配置下悄悄工作，尤其对 planner/search 这类外部依赖多的模块更重要。

考虑过的替代方案：
- 缺失字段时静默回退默认值：更宽容，但会削弱统一配置的可审计性。

## 风险 / 权衡

- [统一配置会提高初次启动门槛] → 提供清晰的示例配置文件和文档，降低上手成本。
- [一次性迁移 planner 与 search 会带来改动面] → 通过集中配置模块隔离影响面，优先迁移当前最明显的两个模块。
- [失去环境变量直连会影响某些部署方式] → 保留显式配置注入与配置文件路径注入能力，覆盖测试和嵌入式使用场景。
- [配置模型过早膨胀] → 只纳入当前真实存在的运行参数，避免一次性抽象未来所有配置。
- [配置文件缺失导致启动失败] → 在错误信息中明确指出缺失文件路径和所需字段。

## Migration Plan

1. 新增统一项目配置规范与设计文档。
2. 引入根目录 `config/config.toml` 示例和 `trpg_py.config` 集中加载模块。
3. 先迁移 `planner` 的默认配置和 factory 解析逻辑到统一配置。
4. 再迁移 `search` 的 API/Qdrant/检索默认配置到统一配置。
5. 删除或收缩模块内项目级 `DEFAULT_*` 与环境变量解析逻辑。
6. 为配置加载、迁移后模块行为和错误分支补充测试。
7. 更新 README 和运行说明，明确新的唯一配置入口。

回滚策略：若迁移出现兼容性问题，可以临时保留集中配置模块并让 planner/search 接受显式参数注入，同时回退统一配置文件为非必需；这样不会影响 engine 本身的执行能力。
