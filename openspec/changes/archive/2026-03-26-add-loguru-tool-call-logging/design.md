## 上下文

当前 planner 相关链路已经有了结构化结果和 smoke/debug 输出，但工具调用本身仍然缺少统一日志。`search` 和 `fetch_keys` 的输入参数、返回状态和错误信息大多只存在于函数返回值里，只有当调用方显式打印或测试断言时才看得见。

这带来两个直接问题：

- planner 或其他 agent 一旦误用工具参数，运行时很难从日志里快速定位是哪一次调用出了问题。
- 外部依赖故障（例如检索失败、路径枚举异常）只能从最终返回体间接推断，缺少每次工具调用的审计痕迹。

用户希望 agent 每次使用工具时都通过 `loguru` 记录输入和输出，因此这次变更需要把日志职责下沉到工具层，并定义统一的日志边界。

## 目标 / 非目标

**目标：**
- 为 `search`、`fetch_keys` 等 agent 工具增加统一的 `loguru` 输入/输出日志。
- 让 planner 在调用这些工具时天然拥有工具日志，而不需要在 planner 层重复手写日志代码。
- 明确成功、无命中和错误三类调用都必须留下可读日志。
- 为工具日志增加测试，保证日志字段和分支行为稳定。

**非目标：**
- 不在本次设计中为整个工程引入复杂的集中日志配置系统。
- 不在本次设计中记录完整底层网络请求细节或敏感认证信息。
- 不在本次设计中保证所有未来 agent 工具自动具备日志，除非它们显式接入这一约定。
- 不在本次设计中替代 planner 的结构化 debug 负载；工具日志与 debug 负载是互补关系。

## 决策

### 决策: 在工具实现内部记录日志，而不是由 planner 或 smoke 脚本代打

日志记录将放在 `search` 和 `fetch_keys` 的工具实现内部，而不是放在 planner 调用点或 smoke 脚本里。这样无论工具是被 planner、测试还是未来其他 agent 入口调用，都能获得一致的日志行为。

考虑过的替代方案：
- 在 planner 层手工包一层日志：只能覆盖 planner，无法覆盖直接工具调用。
- 仅在 smoke 脚本里打印输入输出：适合演示，但不满足运行期审计需求。

### 决策: 用统一日志事件结构记录“输入 + 输出摘要 + 错误”

每次工具调用都应至少记录：

- 工具名
- 输入参数
- 输出状态（如 `ok` / `no_match` / `error`）
- 输出摘要（例如命中数量、返回项数量）
- 错误类型和错误信息（如果有）

日志重点是帮助定位调用行为，而不是完整复制所有大对象内容。对返回值较大的情况，应优先记录摘要而不是无边界展开。

考虑过的替代方案：
- 记录完整输出 payload：最直接，但可能导致日志噪音过大。
- 只记录输入不记录输出：无法判断调用是否成功以及返回了什么。

### 决策: 使用 loguru 作为统一日志入口，并把它声明为项目依赖

本次变更会显式引入 `loguru` 并通过 `from loguru import logger` 记录工具日志，而不是继续依赖 `print` 或标准库 `logging` 的临时写法。这样后续如果项目需要统一日志格式、sink 或等级控制，也有一个清晰入口。

考虑过的替代方案：
- 使用标准库 `logging`：依赖更少，但与用户明确要求的 `loguru` 不一致。
- 自己封装日志工具：抽象更重，当前需求还不需要。

### 决策: 默认记录调用日志，但避免泄漏敏感信息和无限增长

日志必须默认开启，才能满足“每次使用工具都记录”的目标；但日志内容必须避免泄漏密钥等敏感字段，并对大结果使用摘要形式，防止日志不可读。

考虑过的替代方案：
- 默认关闭，靠 debug 开关开启：更安静，但不满足用户要求。
- 原样输出所有参数和返回值：实现简单，但有噪音和潜在敏感信息风险。

## 风险 / 权衡

- [日志量显著增加] → 只记录输入、状态和结果摘要，避免无边界输出大型 payload。
- [未来更多工具日志格式不一致] → 在这次设计中先定义统一字段约定，后续新工具沿用。
- [loguru 作为新依赖带来维护成本] → 依赖面较小，先限定在 agent 工具层使用。
- [错误日志与结构化返回重复] → 接受这部分重复，换取运行期可观测性和排障速度。

## Migration Plan

1. 将 `loguru` 加入项目依赖。
2. 在 `search` 与 `fetch_keys` 工具实现中增加统一日志记录。
3. 为正常命中、无命中和错误路径补充日志测试。
4. 视需要补充 README 或 smoke 说明，告诉开发者工具日志会自动输出。
