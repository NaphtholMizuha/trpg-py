## 上下文

当前项目已经有基础的单元测试与示例驱动测试，能够覆盖攻击暴击、豁免不因天然 20 自动成功、范围伤害减半、自定义字段映射以及资源不足失败等部分行为，但边界覆盖还不均衡。现有 `heal.apply` 仅按当前生命值加治疗量写回，没有处理生命上限，因此用户要求的“回血不能超过上限”尚未被显式实现和验证。

## 目标 / 非目标

**目标：**
- 为关键规则边界补充一组稳定、可重复的回归测试。
- 让优势、劣势、大成功、大失败和范围选择等规则行为都至少有一个直接测试。
- 为治疗操作增加生命上限封顶行为，并确保该行为兼容显式路径模板。
- 为 `main.py` 的人类可读展示增加集成测试，验证输出能向读者解释任务结果，而不是只暴露内部 JSON。

**非目标：**
- 不重构现有执行器或操作分派结构。
- 不扩展新的范围几何类型或新的检定标签。
- 不引入新的测试框架，继续使用现有 `unittest` 与固定骰子夹具。
- 不把集成测试写成脆弱的逐字快照；重点验证高价值信息是否出现。

## 决策

### 决策 1：继续使用确定性固定骰子测试关键规则边界

- 采用 `FixedDiceRoller` 驱动天然 20、天然 1、优势取高、劣势取低和优势/劣势抵消等测试。
- 这样能让失败定位到具体规则分支，而不是把多个行为混在单个示例任务里。
- 备选方案：只扩展示例 JSON 的端到端测试。
  该方案可读性较高，但在检查单一规则分支时不如专门单元测试直接。

### 决策 2：将测试拆分为检定类单元测试和操作类回归测试

- `tests/test_checks.py` 负责检定结果与标签语义。
- `tests/test_operations.py` 负责范围选择、资源扣减、治疗封顶等状态变更行为。
- 新增 `tests/test_main.py` 负责 `main.py` 的集成测试，验证示例输出是否呈现任务状态、步骤摘要和关键状态变化。
- 备选方案：把全部测试堆入一个文件。
  该方案实现简单，但后续继续扩展时会让失败定位和维护成本上升。

### 决策 3：`main.py` 集成测试断言“关键信息存在”，而不是锁死整段文案

- 集成测试将直接调用 `main.main()` 或等价入口，并捕获标准输出。
- 断言重点放在高价值片段，例如任务名、步骤类型与结果、目标列表、生命值变化等。
- 这样既能约束“是否清楚”，又不会因为措辞微调就导致测试大量失效。
- 备选方案：对整段输出做精确字符串快照。
  该方案对文案改动过于敏感，不利于持续优化展示效果。

### 决策 4：治疗封顶优先支持显式上限路径，并保留默认布局的合理推断

- `heal.apply` 新增对 `target_hp_max_path` 与 `target_hp_max_path_template` 的支持。
- 若未显式提供，但生命值当前路径是默认的 `...hp.current` 形式，系统可尝试读取同级 `...hp.max` 作为默认上限。
- 若既没有显式上限路径，也无法从默认布局推断上限，则保持现有“仅加值写回”的行为，避免强制所有状态结构都提供生命上限字段。
- 备选方案：强制所有治疗步骤都必须提供上限路径。
  该方案最明确，但会让默认布局的使用成本提高，也不利于已有示例平滑演进。

## 风险 / 权衡

- [默认上限推断依赖 `hp.current -> hp.max` 命名约定] → 仅将其作为显式路径缺失时的兜底，并继续优先支持路径模板。
- [测试数量增多后维护成本上升] → 通过将测试按规则域拆分，降低单个文件复杂度。
- [`main.py` 展示文案可能持续迭代] → 集成测试只断言解释性强的关键片段，不锁死全文。
- [现有示例状态可能缺少 `hp.max`] → 治疗封顶测试使用专门夹具，不强制改动所有现有示例。

## 迁移计划

- 先补充变更规范与任务清单。
- 实现 `heal.apply` 的上限解析与封顶逻辑。
- 添加并运行新的回归测试，确认现有示例不回归。
- 为 `main.py` 增加集成测试，确认示例输出在保留可读性的同时仍与执行结果一致。
