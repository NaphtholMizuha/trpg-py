## 上下文

现在的 `grep` 工具在实现上会沿着展平后的状态行顺序扫描，并在达到 `limit` 后停止。这个行为虽然简单，但会把“相关性”隐含地绑定到状态枚举顺序上，带来两个实际问题：

- 高噪音查询时，前几条命中可能全是无关属性，真正有用的证据被截断在后面
- 调用方不得不通过不断调高 `limit` 来“碰运气”，而不是直接拿到更相关的前几条

用户当前的设计判断很清楚：

- 不要再把 `limit` 作为 `grep` 的默认核心语义
- 先让 `grep` 返回按相关性排好的命中
- 命中结果不再只是整行字符串，而应包含 `key`、`value` 和 `sim`
- 调用方如果真的只想看前几条，再在排序后的结果上截断

## 目标 / 非目标

**目标：**
- 让 `grep` 先收集所有命中，再按相关性排序。
- 让 `grep` 的返回项成为结构化对象，便于调用方直接消费 path、value 和排序分数。
- 让 `limit` 退化为可选的结果截断参数，而不是默认决定扫描深度的核心机制。
- 在不引入复杂 embedding 或外部检索器的前提下，提供可解释、稳定的轻量排序规则。
- 让 `task_node` 的 prompt 更明确地学会如何使用 `grep`，包括如何构造查询、如何判断结果是否有用、以及如何消费 `key/value/sim`。

**非目标：**
- 本次设计不引入向量排序或额外模型调用。
- 本次设计不要求一版内解决所有自然语言别名问题。
- 本次设计不要求 planner 立即改写所有调用方式，只要求 `grep` 的语义先变正确。

## 决策

### 决策 1：`grep` 必须先收集命中，再做排序

`grep` 不应在扫描过程中因为默认 `limit` 提前停止，而应先收集所有命中的扁平化行，然后再基于查询表达式做排序。

这样做的原因是：
- 相关性排序必须看到完整命中集合才有意义
- 这能把“状态枚举顺序”从结果质量中剥离出去

替代方案：
- 继续边扫描边截断：实现简单，但返回质量不稳定

### 决策 2：`limit` 保留为可选的结果截断，而不是默认行为中心

`limit` 仍然可以保留在输入 schema 中，但它的语义应当是“对排序后结果进行可选截断”。默认调用不应依赖低 `limit` 来拿到看起来还行的前几条。

这样做的原因是：
- 与现有 API 更兼容
- 让调用方仍然可以在需要时控制输出体积
- 但不再让 `limit` 决定能否看到相关结果

替代方案：
- 完全删除 `limit`：语义更纯，但会增加调用方迁移成本

### 决策 3：相关性排序采用轻量、可解释的规则打分

第一版相关性排序采用规则打分，而不是 embedding 或外部 reranker。推荐的信号包括：

- 表达式中命中的词项数量
- 命中是否出现在 path 段而不只是 value 文本中
- 精确词项或短语匹配优先于宽松同义词扩展
- 同时满足多个子条件的行优先于只满足弱条件的行

这样做的原因是：
- 调试和测试都更容易解释
- 不引入额外依赖
- 与现有布尔表达式求值实现兼容

替代方案：
- embedding 排序：潜在更强，但当前阶段过重

### 决策 4：命中结果改为结构化对象

`grep` 的每条命中结果不再返回单个整行字符串，而应至少返回：

- `key`: 扁平化状态路径
- `value`: 原始值或可 JSON 表达的值
- `sim`: 当前排序分数

这样做的原因是：
- 调用方不必再自己从 `"a.b.c = value"` 中拆 path/value
- `sim` 可以让排序结果变得可观察、可调试
- 与“排序优先”的设计更一致

替代方案：
- 继续返回整行字符串：兼容性更好，但会把结构解析负担留给所有调用方

### 决策 5：排序后结果仍然必须保持稳定性

如果两条结果的相关性得分相同，`grep` 应保持稳定次序，例如回退到原始展平顺序，以避免相同输入产生不稳定的结果排列。

这样做的原因是：
- 测试更稳定
- smoke 和 planner 行为更容易复现

### 决策 6：同步更新 task_node prompt，显式教会 agent 更好地使用 grep

仅仅把 `grep` 变成“结构化且已排序”还不够，`task_node` 还需要被明确教会如何利用这个工具。提示词需要增加两类内容：

- 文字规则：
  - 什么时候优先用 `grep`
  - 如何从自然语言实体、物品、法术名构造更合适的查询
  - 如何消费结构化命中里的 `key`、`value`、`sim`
  - 在什么情况下把低相关命中排除在 `context_lines` 外
- few-shot：
  - 至少给出 1-2 个代表性例子，例如攻击类和施法类
  - 展示“instruction -> grep 查询思路 -> 结构化命中 -> TaskDraft 取舍”的过程

这样做的原因是：
- 工具能力升级后，prompt 需要同步对齐，否则 agent 仍可能沿用旧的“整行字符串 + 低 limit”心智模型
- `task_node` 当前高度依赖 prompt 行为，few-shot 往往比抽象规则更容易稳定下来

替代方案：
- 只改工具，不改 prompt：实现最省事，但 agent 可能不会立刻用好新能力

## 风险 / 权衡

- [轻量规则排序仍然可能不够聪明] → 先追求“明显更好且可解释”，后续再升级。
- [不默认截断可能让结果变长] → 通过可选 `limit` 在排序后截断控制输出规模。
- [结构化结果会带来接口变更] → 一次性把 smoke、测试和 planner 调用方一起迁移。
- [few-shot 可能过拟合少数案例] → 用少量代表性示例配合通用文字规则，而不是堆很多特例。
- [排序逻辑会增加 grep 的 CPU 开销] → 当前状态规模可接受，且收益大于成本。

## Migration Plan

1. 调整 `grep` 的命中收集逻辑，使其先收集全量命中。
2. 为命中行引入轻量相关性打分并稳定排序。
3. 将命中结果改为 `key / value / sim` 的结构化对象。
4. 将 `limit` 应用于排序后的结果切片，而不是扫描时提前停止。
5. 更新 `task_node` prompt，加入 few-shot 与明确文字规则，指导 agent 更好地使用 `grep`。
6. 更新 `grep` 单测和 smoke，验证排序优先级、结构化返回和默认行为。
7. 让 planner 侧逐步减少对低 `limit` 的依赖，并直接消费结构化命中。

## Open Questions

- 是否要在后续版本中把 path 命中和 value 命中的权重拆得更细？
- 是否需要在 debug 日志里额外暴露排序前后结果数量，而不暴露每条的内部打分细节？
- few-shot 示例是否需要区分攻击类与施法类各一组，还是先只保留最小代表集？
