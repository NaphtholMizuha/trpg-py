## 上下文

当前 planner 的主要问题不在于缺少工具，而在于单次 `agent.invoke(...)` 内缺少可靠的收口机制。日志已经显示出三类重复行为：同一路径或前缀多次 `list/read`、同一规则主题重复 `search`、以及候选 `TaskDocument` 在 `lint` 上反复修补。虽然 prompt 中已经存在 `tool_budget` 提示，但该预算目前只是软约束，无法阻止运行时继续调用工具。

这次变更会同时触及 planner prompt、planner runtime、tool 返回语义和 smoke 验证，因此属于跨模块行为变更。另一个重要约束是：不能把 planner 的抗打转能力建立在硬编码 DnD 规则表之上；系统仍然必须基于 canonical state、通用工具语义和有限的 runtime 护栏来收口。

## 目标 / 非目标

**目标：**
- 让 planner 将 `list/read` 的 `status=no_match` 视为“当前 state 中没有该事实”的有效证据，而不是无限重试信号。
- 鼓励 planner 在同一取证主题上优先批量 `read`，减少零散的单路径读取。
- 为单次 planner 运行增加真正的工具调用次数上限，避免一次 `agent.invoke(...)` 内长时间打转。
- 在缺失法术、缺失法术位、错误路径等常见场景下，让 planner 更快收口为 `needs_human`、拒绝规划或稳定候选文档。

**非目标：**
- 不引入新的 planner projection 层或第二套 state 表示。
- 不尝试穷举 DnD 法术、职业或规则例外，也不把规则判断硬编码进路径建议逻辑。
- 不改变 engine 的 canonical state 结构或执行契约。

## 决策

### 决策 1：将 `no_match` 解释为“缺失事实”，而不是“继续猜测”
- 选择：当 `list` 或 `read` 返回 `status=no_match` 时，planner 必须把该结果视为当前 state 下未找到对应事实的证据。若工具同时提供了建议路径，planner 只允许基于建议再做一次邻近修正；再次失败后必须收口，而不是继续自由试探。
- 理由：真正导致打转的不是第一次 `no_match`，而是模型把 `no_match` 当成“我还没找对”的无限探索许可。
- 替代方案：
  - 只增加更多建议路径而不改变 planner 语义。缺点是建议越多，模型越可能继续试探。
  - 对每个领域缺口硬编码专门规则。缺点是不可扩展且与规则系统耦合过深。

### 决策 2：把“同类值确认”收敛为批量 `read`
- 选择：prompt 与 planner 运行策略都应明确要求：一旦已经发现一组同类候选路径，优先使用一次批量 `read(paths=[...])` 读取，而不是拆成多次单路径调用。
- 理由：AC、HP、spell slots、known spells 这类值通常天然成组。批量读取能减少工具往返，也让模型更容易在一次观察中完成对比和收口。
- 替代方案：
  - 保持完全自由的逐条 `read`。缺点是容易演化成长链条低价值工具调用。
  - 另做 `read_bundle` 专用工具。缺点是新增心智模型，超出本次最小改动范围。

### 决策 3：在 runtime 层增加单轮工具调用硬上限
- 选择：为单次 planner 运行增加真实的 tool-call cap；一旦达到上限，planner 必须停止继续取证，并输出可解释的收口结果或修复反馈。
- 理由：prompt 只能鼓励收口，runtime 才能真正停止打转。工具预算必须从文本提示升级为执行期护栏。
- 替代方案：
  - 仅依赖 prompt 中的 `tool_budget`。缺点是已经证明不可靠。
  - 只限制某一类工具，例如只限 `search`。缺点是 `list/read/lint` 同样会形成局部循环。

### 决策 4：限制重复失败主题，而不是只限制总量
- 选择：除了总工具调用上限外，planner 还需要对“重复失败主题”做熔断，例如相同 bare path、相同 prefix、或同一缺失事实（如 `level_3` spell slots）连续失败后必须停止继续试探。
- 理由：总量限制能防止最坏情况，但不能单独阻止“把大部分预算都浪费在同一个洞里”。
- 替代方案：
  - 只保留总量限制。缺点是仍可能在少量预算里重复做低价值操作。
  - 仅在 prompt 中用语言提醒。缺点是模型不稳定，难以保证行为一致。

### 决策 5：将 `lint` 视为最终收口工具，而不是新的探索入口
- 选择：prompt 和 runtime 都要明确：`lint` 只用于候选 `TaskDocument` 的最终合法性校验；如果没有新的状态或规则证据，planner 不得通过反复 `lint` 制造新的探索循环。
- 理由：当前日志里 `lint` 已经被模型拿来做“试一版再修一版”的隐式循环节点。
- 替代方案：
  - 不限制 `lint` 次数。缺点是会掩盖真正的状态取证缺口。
  - 完全取消 `lint`。缺点是会失去 ready 前的重要只读校验闭环。

## 风险 / 权衡

- [收口过早可能让 planner 更常返回 `needs_human`] → 通过“允许基于 suggestions 再试一次”和“优先批量 `read`”保留最低限度的自助取证空间。
- [runtime 限额可能截断原本可成功的复杂规划] → 将预算设计成可配置值，并在 blocked/needs_human 中暴露“预算耗尽”这一真实原因。
- [批量 `read` 仍可能读取很多无用路径] → 在 prompt 中限定批量读取应围绕同类候选路径，避免把全量路径塞给 `read`。
- [重复失败主题识别若过于粗糙会误伤正常取证] → 优先以相同 bare path、相同 prefix、相同建议修正链为判定粒度，避免过度泛化。

## Migration Plan

1. 更新 planner prompt，明确 `no_match` 的收口语义、批量 `read` 优先级和 `lint` 使用边界。
2. 在 planner runtime 增加工具调用计数与重复失败主题跟踪。
3. 调整 `list/read` 相关测试和 smoke 入口，覆盖缺失事实快速收口场景。
4. 在 planner + engine smoke 中增加针对缺失法术位或缺失法术的可解释输出断言。
5. 若限额策略导致误伤复杂场景，可先提高预算阈值，再局部调优重复失败主题识别逻辑。

## Open Questions

- 工具调用上限是否应区分总量和 `search` 子预算，还是先保持统一预算更简单？
- 预算耗尽时更适合返回 `needs_human` 还是 `blocked`，是否需要按“证据不足”和“系统护栏触发”区分？
- 对 `lint` 的限制应当是独立计数，还是直接纳入总工具预算即可？
