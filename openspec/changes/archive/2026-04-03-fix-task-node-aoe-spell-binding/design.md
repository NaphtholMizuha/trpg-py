## 上下文

上一轮变更已经让 `TaskDraft` 具备 `evidence` 与 `states` 两个更诚实的证据字段，但 `task_node` 仍然可能把范围法术理解成单体结算任务。以 `Aldera用火球术攻击goblin` 为例，当前 smoke 会：
- 正确搜索到 `Fireball` 的范围、豁免和伤害规则
- 正确绑定 `spell_dc`、目标 `dex save` 与目标 `hp`
- 但错误地把 `Fireball` 默认绑定到 `level_1` 法术位
- 且完全不读取 actor / target 位置，也不表达爆点、覆盖范围或受影响对象集合

这说明问题不只在“证据是否暴露”，而在“任务结构是否先理解正确”。对于范围法术，`TaskDraft` 需要先表达覆盖判定，再表达逐对象结算；否则下游即使拿到了 `evidence`，也只能在错误的任务结构上继续翻译。

## 目标 / 非目标

**目标：**
- 要求 `task_node` 在具名法术任务中先确认法术身份，再绑定默认施法环级与法术位资源。
- 要求 `task_node` 在 AoE / burst / line / cone 等范围效果任务中，把位置、施法距离、覆盖范围和受影响对象集合纳入 judgments 与状态绑定。
- 让 `TaskDraft` 能诚实表达“先判定覆盖对象，再逐个结算”的范围法术结构。
- 让 `evidence` 与 `states` 稳定暴露法术环级绑定和位置判定所需证据。
- 让 smoke / 测试可以观察 `Fireball` 默认使用 3 环、不会误绑 1 环，并且不会在缺失位置判定时假装任务已完整。

**非目标：**
- 不在本次引入新的几何引擎或完整战棋距离计算模块。
- 不要求 `dsl_node` 本次就完全消费多目标 effect 结构。
- 不尝试一次解决所有非单体法术的 DSL 表达问题。
- 不修改搜索或 grep 底层检索算法。

## 决策

### 决策 1：把“法术身份 -> 默认环级 -> 资源路径”作为显式 prompt 约束
- 选择原因：当前模型已经能找到 `spell_slots.*`，但不会自然把 `actors.<caster>.spells.level_3 = ["火球术"]` 与 `actors.<caster>.spell_slots.level_3.current` 绑定起来。
- 方案：prompt 明确要求在具名法术任务中，先查该法术位于哪个已知/准备环级；若指令没有明确升环，默认绑定该法术本身的环级资源；若仍无法确认，则进入 `missing_info`。
- 替代方案：只靠更多 few-shot 暗示模型推断。
- 未选择原因：few-shot 有帮助，但不足以形成稳定的硬约束。

### 决策 2：把 AoE 覆盖判定上升为任务结构的一部分，而不是附属细节
- 选择原因：`Fireball` 的核心并不是“让 goblin 做一次豁免”，而是“选定爆点后，对覆盖范围内对象逐个结算”。如果不把覆盖判定提升为 judgments 之一，模型就会自然退回单体攻击模板。
- 方案：prompt 明确要求范围法术任务必须包含：
  - 施法距离或作用距离前提
  - 爆点 / 覆盖范围 / 受影响对象集合判定
  - 对每个受影响对象进行 save / damage 结算
- 并且 few-shot 必须显式展示“先读取 actor / target 位置，再决定覆盖关系或暴露缺口”的步骤
- 替代方案：只在 `evidence` 里记录“Fireball 是 20 尺半径”。
- 未选择原因：这只能补充事实，不能修正任务结构。

### 决策 3：保持 `TaskDraft` 字段形态轻量，优先收紧语义而不是立刻引入复杂新 schema
- 选择原因：当前用户想修的是提示词和 `TaskDraft` 的表达诚实度，而不是立刻设计一个完整多目标 AST。
- 方案：保留现有字段集合，但要求：
  - `task` 与 `judgments` 明确出现覆盖对象判定
  - `reads` 覆盖位置、范围与资源绑定所需路径
  - `states` 暴露位置与法术环级相关状态证据
  - `evidence` 暴露范围/豁免/伤害等摘要化规则证据
- 替代方案：新增 `targets`, `targeting`, `area_shape`, `slot_level` 等结构化字段。
- 未选择原因：这会把范围扩大到数据模型重构，超出本次聚焦。

### 决策 4：在位置或爆点信息不足时，必须显式暴露缺口，而不是继续假装单目标可执行
- 选择原因：当前最危险的不是“少查一条证据”，而是“缺关键前提时依旧返回看起来完整的任务稿”。
- 方案：规范要求当范围覆盖无法根据当前状态确认时，`TaskDraft` 必须把缺口写入 `missing_info`，而不是直接把单个宾语实体当作唯一受影响对象。
- 替代方案：允许模型在明显近距离时默认判定覆盖。
- 未选择原因：这会让行为依赖隐式推断，难以稳定测试。

### 决策 5：few-shot 需要教“模式”，不能直接复用 Fireball 评测样例
- 选择原因：如果 prompt few-shot 直接使用 `Fireball`，后续 smoke / eval 很容易被样例污染，模型可能是在回忆模板而不是学习范围任务的通用结构。
- 方案：few-shot 采用约 5-6 个任务类型原型来教模型先分类、再检索、再起草，例如：
  - 单体攻击
  - 单体法术
  - 范围法术
  - 治疗 / 增益
  - 状态 / 条件效果
  - 纯状态查询
- 其中范围法术示例可使用 `Lightning Bolt`、`Thunderwave` 或其他非 Fireball 的具名范围效果，并且必须显式演示位置获取与覆盖判定。
- 替代方案：直接把 `Fireball` 写进 few-shot。
- 未选择原因：这会让评测失真，降低 smoke 对真实泛化能力的观察价值。

## 风险 / 权衡

- [风险] 增加 AoE 与环级绑定约束后，task_node 可能更频繁地产生 `missing_info`
  - 缓解措施：只对范围法术和具名法术触发这些硬约束，普通单体任务保持现有路径。

- [风险] 仅靠 prompt 收紧语义，仍可能不足以完整表达多目标 effect
  - 缓解措施：本次先确保任务理解不再明显失真；若下游 DSL 仍不足，再单独推进结构化 targeting 变更。

- [风险] 位置判断可能被过度简化成“只读 actor/target position”
  - 缓解措施：在设计上明确本次只要求读取并暴露位置前提，不承诺完整几何求解。

- [风险] few-shot 如果直接复用评测样例，会导致 smoke 结果看起来变好但泛化能力没有提升
  - 缓解措施：few-shot 只教任务类型原型和范围任务模式，不直接使用 `Fireball` 作为示例；`Fireball` 仅保留在 smoke 与测试中。

## Migration Plan

1. 更新 `planner_task_node_system` / `planner_task_node_user`，加入法术身份绑定、默认环级绑定与 AoE 覆盖判定的硬约束，并用约 5-6 个任务类型原型 few-shot 进行覆盖，其中范围效果示例必须是非 Fireball 且显式演示位置获取与覆盖判定。
2. 调整 `TaskDraft` 的说明或模型注释，使其语义明确支持范围法术的任务结构。
3. 视需要在 `task_node` 后处理里增加轻量校验，例如当范围法术缺少位置证据时不应输出看似完整的状态证据。
4. 增加 smoke 与测试，覆盖：
   - `Fireball` 默认绑定 3 环
   - 不误用 `level_1` 法术位
   - 会读取位置，或把位置 / 覆盖缺口暴露到 `missing_info`

## Open Questions

- `TaskDraft` 是否需要在后续演进出显式的 `targeting` / `affected_entities` 结构字段？
- 当前 world state 是否需要一个更统一的“已准备法术 -> 默认环级”表示，避免完全依赖 `spells.level_n` 命名约定？
- 若 actor 与 target 的位置已经足够判断“当前显然在 20 尺半径内”，是否允许 task_node 直接输出这一判断，还是仍要求显式保留爆点不确定性？
