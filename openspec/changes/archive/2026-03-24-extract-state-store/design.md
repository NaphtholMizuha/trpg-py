## 上下文

当前项目中的状态读写能力由 `trpg_py/engine/state.py` 提供底层点路径工具，再由 `engine/executor.py`、`engine/operations.py` 与 `refs.py` 在各自语境中直接调用。这样做的优点是简单，但代价是：

- 状态访问语义以零散函数形式分布，缺少单一维护点。
- `engine` 内部实现实际上被 `engine` 外模块间接依赖，边界不清晰。
- 调用方需要自己拼装“先读再算再写”的流程，导致状态修改语义分散。

这次变更的目标不是引入复杂的领域状态对象，而是在保持当前嵌套字典与点路径语义不变的前提下，建立一个统一的状态存储包作为共享抽象。

## 目标 / 非目标

**目标：**

- 提供一个独立的状态存储包，集中维护点路径 map 的解析、读取、写入和修改能力。
- 只暴露 `read`、`reads`、`write`、`writes`、`mod`、`mods` 六个接口，形成统一调用面。
- 让 `executor`、`operations`、`refs` 通过该接口访问状态，收敛路径语义实现。
- 保持当前 `StatePathError` 与点路径语义兼容，避免任务执行行为回归。
- 在迁移阶段保留薄兼容层，降低对现有导出路径的破坏。

**非目标：**

- 不在本次变更中重新设计状态 schema，例如 `actors.*.hp.current` 的结构约定。
- 不把状态从可变字典改造成不可变数据结构或事件溯源模型。
- 不在本次变更中扩展新的查询语言、通配符路径或事务语义。
- 不要求一次性移除所有旧导出；兼容层可以短期保留。

## 决策

### 1. 新增独立状态存储包，而不是继续扩展 `engine/state.py`

将状态访问能力提升为 `engine` 外的共享模块，语义上更贴近当前真实依赖关系。这样 `engine` 成为状态存储能力的使用者，而不是实现宿主。

考虑过的替代方案：

- 继续保留在 `trpg_py/engine/state.py`
  - 优点：改动最小
  - 缺点：继续模糊模块边界，`refs.py` 等非 engine 模块仍然需要借道 `engine`
- 直接把现有函数平移到 `trpg_py/state.py`
  - 优点：迁移成本低
  - 缺点：只能改善物理位置，无法把“单项/批量/修改”语义明确建模为统一接口

### 2. 用六个高层接口替代低层 `get/set/has`

公开 API 固定为：

- `read(path)`
- `reads(paths)`
- `write(path, value)`
- `writes(items)`
- `mod(path, fn)`
- `mods(items)`

其中：

- `read/reads` 负责获取当前值
- `write/writes` 负责写入目标值
- `mod/mods` 负责基于旧值派生新值并写回

这样可以把“修改”提升为一等语义，减少调用点手动执行 `read -> transform -> write` 的重复逻辑。

考虑过的替代方案：

- 继续公开 `get_path/set_path/has_path`
  - 优点：完全兼容现状
  - 缺点：API 过底层，无法表达批量写入与基于旧值修改
- 设计面向对象的 `StateStore` 大类并公开更多方法
  - 优点：可扩展性强
  - 缺点：对当前代码库来说过重，容易超出本次整理目标

### 3. 保留当前点路径与错误语义

底层行为延续现有实现：

- 点号分隔 token
- 数字 token 优先兼容 dict 中的数字字符串键，再尝试列表索引
- 读取缺失路径时报 `StatePathError`
- 写入时禁止创建非法中间列表节点
- 写入值采用深拷贝隔离

这样迁移主要改变调用接口，而不是改变业务行为。

考虑过的替代方案：

- 简化规则，只支持 dict/list 其中一种
  - 优点：实现更纯粹
  - 缺点：会破坏现有状态兼容性
- 写入时更激进地自动创建结构
  - 优点：调用方更省事
  - 缺点：会掩盖路径错误，改变当前失败模式

### 4. 兼容层只做转发，不保留双份语义

`trpg_py/state.py` 与必要的旧导出可以暂时保留，但应只转发到新状态存储包，不再保留另一套独立实现。这样可以避免语义漂移。

考虑过的替代方案：

- 立刻删除旧导出
  - 优点：边界最干净
  - 缺点：对现有调用点与外部使用者过于激进
- 长期并存两套 API
  - 优点：迁移压力低
  - 缺点：维护成本高，最终会再次分叉

## 风险 / 权衡

- 迁移过程中接口命名改变较大 → 通过兼容层与分阶段替换调用点降低风险
- `mods/writes` 的参数形状若设计不清，后续调用会混乱 → 在实现前先固定统一输入输出约定，并补测试覆盖
- `refs`、`executor`、`operations` 分别访问 `state/context/results`，抽象过度可能让上下文边界混淆 → 将“点路径语义层”和“业务命名空间层”分开，前者复用，后者各自包装
- 如果新包既提供函数又维护内部状态对象，调用模型可能不一致 → 明确以“围绕底层 map 工作的轻量接口”作为主模式

## 迁移计划

1. 新建状态存储包，实现与现有路径语义等价的底层能力。
2. 在新包上定义 `read/reads/write/writes/mod/mods` 六个公开接口，并补充路径/批量/修改测试。
3. 让 `trpg_py/state.py` 和必要旧导出转发到新包，形成兼容层。
4. 迁移 `refs.py` 到新接口，确保 `context/state/result` 路径解析共用同一语义层。
5. 迁移 `engine/executor.py` 的 change commit 逻辑到新接口。
6. 迁移 `engine/operations.py` 中显式 `get_path/has_path` 调用到新接口。
7. 更新 `engine/__init__.py` 与相关导出文档，明确新推荐 API。
8. 在确认无剩余直接依赖后，再评估是否移除旧导出。

## 开放问题

- 新状态存储包应采用什么模块名最贴切：`state_store`、`store` 还是继续沿用 `state`？
  - 使用 `store`
- `reads/writes/mods` 的返回值应更偏向列表顺序结果，还是路径到结果的映射？
  - 顺序结果
- `mod/mods` 是否需要支持“缺失路径上的变换”，还是严格要求目标路径预先存在？
  - 严格要求存在
