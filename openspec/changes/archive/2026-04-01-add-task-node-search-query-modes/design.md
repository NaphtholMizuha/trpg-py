## 上下文

当前 `search` 工具底层已经采用 dense + sparse 混合召回并使用 reranker 重排，但 `task_node` 的提示词将规则检索统一引导为中文 HyDE 风格自然语言查询。这在没有明确规则名的场景下有价值，但在存在明确术语锚点时会把检索意图从“定位规则条目”改写成“寻找相似规则场景”，从而增加 `火球术` 命中 `连锁闪电` 等相似法术的风险。

这次变更要解决的重点不是更换底层检索算法，而是让 `task_node` 能显式表达三类检索意图：
- `term`: 先定位明确规则术语
- `balanced`: 保留术语锚点，同时补充少量结算细节
- `semantic`: 在没有可靠术语时使用语义化规则场景查询

## 目标 / 非目标

**目标：**
- 保持单一 `search` 工具接口，不引入两个独立 search 工具。
- 为 `search` 增加可观测的 `mode` 参数，让 LLM 选择查询意图而不是底层数学参数。
- 调整 `task_node` prompt，使其先判断是否存在明确规则术语，再决定使用 `term`、`balanced` 或 `semantic`。
- 为三种模式补充 few-shot 与 query 构造规则，减少“所有规则查询都被 HyDE 化”的倾向。

**非目标：**
- 不引入双路并行 `term + HyDE` 检索。
- 不立即修改 Qdrant 融合算法、RRF 权重或 reranker 模型。
- 不要求第一阶段就让 retriever 对不同 mode 使用完全不同的底层召回策略。

## 决策

### 决策 1：维持单一 `search` 工具，增加 `mode`
- 选择原因：比双工具和双路并行检索更简单，也比让 LLM 选择底层权重更可控。
- 替代方案：拆成 `term_search` 与 `semantic_search` 两个工具。
- 未选择原因：会增加 tool surface 和 prompt 决策负担，当前阶段更需要先验证 query discipline 是否足够。

### 决策 2：把三模式定义为 query 组织方式，而不是底层参数模板
- `term`: query 必须短，保留规则术语原词，可附英文名或别名。
- `balanced`: query 必须保留术语锚点，并补 1-3 个当前 judgments 需要确认的规则点。
- `semantic`: query 采用中文自然语言描述规则场景，仅在没有可靠术语锚点时使用。
- 选择原因：LLM 更擅长选择“检索意图”，而不是稳定选择检索超参数。
- 替代方案：暴露 sparse/dense 权重或 RRF 参数给 LLM。
- 未选择原因：LLM 不适合直接选择数学参数，而且当前实现没有天然暴露可调权重接口。

### 决策 3：先做 prompt-level mode，再视需要升级为 retriever-level mode
- 第一阶段让 `mode` 主要用于：
  - 约束 query 构造
  - 提升日志可观测性
  - 支撑 smoke / agent 测试
- 第二阶段如有必要，再让 retriever 根据 mode 调整候选召回或 rerank 细节。
- 选择原因：先控制变量，验证问题主要是不是出在 query formulation。

### 决策 4：明确 evidence interpretation 的职责分工
- `term` 命中优先用于确认规则身份。
- `balanced` 命中用于同时确认规则身份和少量结算细节。
- `semantic` 命中用于在无术语锚点时推断规则场景，但不得在规则身份不明确时假装已确认规则名称。
- 选择原因：今天的问题并不只是召回错，而是 LLM 拿相似规则文本当目标规则使用。

## 风险 / 权衡

- [风险] `balanced` 与 `semantic` 的边界对模型来说仍可能模糊
  - 缓解措施：在 system prompt 和 few-shot 中明确“存在术语锚点时优先 `term` 或 `balanced`”。

- [风险] 只改 prompt 和接口，不改底层检索器，收益可能有限
  - 缓解措施：先通过 `火球术`、`反制法术`、`借机攻击` 等术语强查询验证命中改善，再决定是否需要 retriever-level mode。

- [风险] 模型仍然偏爱 `semantic`，因为它更像自然语言解释
  - 缓解措施：在提示词中把 `semantic` 限制为“仅在没有可靠术语锚点时使用”。

- [风险] 新增 `mode` 会增加工具接口复杂度
  - 缓解措施：只引入三个固定枚举值，并保留默认模式以兼容已有调用。

- [权衡] 放弃双路并行检索降低了质量上限
  - 取舍原因：当前优先目标是用最小复杂度解决术语被 HyDE 化的问题，而不是追求检索系统的最终上限。
