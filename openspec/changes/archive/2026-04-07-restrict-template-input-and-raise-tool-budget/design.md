## 上下文

上一轮变更已经把 `template` 变成了 `dsl_node` 的真实工具调用，这让真实日志终于暴露出新的主矛盾：
- agent 会先传入接近但非法的模板枚举值，例如 `area_spell`
- 第一次查询 `no_match` 后还需要再做一次保守回退
- 在当前默认预算下，这条常见回路很容易在抵达 `lint` 或最终结构化输出前耗尽图递归额度

现在的问题不再是“工具是否存在”，而是：
1. `template` 输入契约不够硬，导致模型能把自由字符串塞进去
2. `dsl_node` 默认预算太紧，无法容纳一次误查后的保守纠偏

## 目标 / 非目标

**目标：**
- 用类型约束或等价机制把 `template` 输入限制为受控枚举值。
- 明确非法枚举输入的行为，使其成为可诊断的受控失败，而不是隐蔽的普通 no-match。
- 提高 `dsl_node` 默认工具预算，让“误查一次 -> 保守回退 -> lint”成为默认可承受路径。
- 让 prompt 对合法枚举值和 `unknown` 的使用规则更明确。

**非目标：**
- 不扩展 `template` 支持的任务族数量。
- 不把 `dsl_node` 改写为确定性编译器。
- 不在本次引入新的外层 workflow 阶段。
- 不把预算无限放大；目标是覆盖现实中的最小常见回路，而不是放任无界重试。

## 决策

### 决策 1：template 输入必须使用真实枚举类型，而不是普通字符串

- 选择原因：只靠 prompt 约束无法阻止模型输出 `area_spell` 这类近似值。
- 方案：将 `TemplateInput` 与相关查询入口切换到 `Literal`/枚举值集合或等价严格校验机制。
- 替代方案：继续接受任意字符串，再在查询层做模糊归一化。
- 未选择原因：这会继续纵容模型瞎编近义值，削弱“受控输入”本身的意义。

### 决策 2：非法枚举值必须快速失败并留下结构化诊断

- 选择原因：如果非法值只表现为普通 no-match，就很难分辨“模板不存在”和“输入根本不合法”。
- 方案：对非法枚举值返回结构化错误或等价可观察失败，至少指明是哪一个字段越界。
- 替代方案：将非法值默默映射到 `unknown`。
- 未选择原因：这会掩盖模型分类错误，也会让日志和评估看起来过于乐观。

### 决策 3：提高 dsl_node 默认工具预算以容纳一次纠偏

- 选择原因：真实链路里最常见的回路是“template 误查一次 -> fallback 一次 -> lint 一次”，当前默认预算过于紧绷。
- 方案：提高 `DslNodeDependencies.max_tool_calls` 的默认值，并让对应 recursion limit 覆盖至少这条最小纠偏链路。
- 替代方案：维持预算不变，只寄希望于 prompt 一次命中。
- 未选择原因：这与真实运行中已经观察到的错误模式不符。

### 决策 4：prompt 必须把 unknown 说明为唯一合法保守值

- 选择原因：预算提高后，如果 prompt 还允许模型自由编造接近值，只会把更多预算浪费在坏查询上。
- 方案：明确只允许使用文档化枚举值，无法确定时只能填 `unknown`。
- 替代方案：允许模型输出“接近语义的自由值”，再靠工具容错。
- 未选择原因：会再次把收敛问题转嫁给工具层。

## 风险 / 权衡

- [风险] 严格枚举会让更多错误直接暴露为显式失败
  - 缓解措施：这是有意为之；显式失败比伪装成 no-match 更利于调试和后续训练。

- [风险] 提高默认预算会增加一次运行的最坏工具成本
  - 缓解措施：只提高到覆盖常见纠偏链路，不做无界增长；同时保持 prompt 的停止条件约束。

- [风险] 模型可能在更高预算下重复犯同一类输入错误
  - 缓解措施：通过严格输入类型和 prompt 约束，让第一次非法输入就变成强反馈，而不是继续温和漂移。

## Migration Plan

1. 收紧 `template` 输入类型与校验行为。
2. 更新 prompt 中关于合法枚举值和 `unknown` 的说明。
3. 提高 `dsl_node` 默认工具预算，并保持 recursion limit 与之对应。
4. 补充测试，覆盖非法输入、保守回退和提高预算后的默认行为。
5. 用 smoke 重新观察真实链路中的 template 查询和预算消耗。

## Open Questions

- 非法枚举输入更适合在 pydantic 层直接抛验证错误，还是转成工具层结构化 `error` 响应？
- 默认预算提高到 4 还是 5 更合适，才能覆盖常见回路又不过度放宽？
