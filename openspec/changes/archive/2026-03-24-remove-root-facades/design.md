## 上下文

当前 `trpg_py` 的实现主体已经归入 `trpg_py.engine` 与 `trpg_py.store`，但包根目录仍保留了一组仅做 re-export 的模块。这些文件并不承载独立实现，却让包根目录看起来像同时支持多套并行入口。随着 `engine.core`、`engine.combat` 和 `store` 包边界逐渐明确，继续保留这些薄 facade 会弱化新的目录结构，也会放大“哪些入口是稳定承诺”的歧义。

这次变更是一个包结构收口动作，涉及公开导入路径、测试导入方式和目录组织规则，因此需要在实现前明确破坏性边界与迁移顺序。

## 目标 / 非目标

**目标：**
- 让 `trpg_py` 包根目录只保留精简且明确的稳定公共 API。
- 删除没有独立职责的根目录薄 facade 文件，避免目录层级表达与真实实现归属冲突。
- 将实现访问路径统一到 `trpg_py.engine...`、`trpg_py.store...` 与 `trpg_py.errors`。
- 让测试、示例和文档都使用新的稳定导入约定。

**非目标：**
- 不在这次变更中继续重构 `engine` 或 `store` 的内部模块边界。
- 不扩展新的顶层公共 API，只收敛现有导出。
- 不为被删除的根目录模块新增 `compat/` 包或其他长期兼容层。

## 决策

### 决策 1：包根目录只保留 `__init__.py` 与少数真实顶层模块

`trpg_py.__init__` 将继续作为顶层稳定入口，`trpg_py.errors` 作为跨包共享错误定义保留在根目录。其余仅承担转发职责的根目录模块全部移除。

- 选择这一方案是因为它能直接表达“根目录是公共 API，而不是实现散件集合”。
- 备选方案 A：保留现状，仅依赖约定说明哪些文件是 facade。
  - 否决原因：目录语义仍然模糊，且后续很容易继续扩散。
- 备选方案 B：把 facade 移入 `trpg_py.compat`。
  - 否决原因：虽然更清晰，但仍在维护一整套迁移层，不符合本次“采用方案 A”的收口目标。

### 决策 2：具体实现入口必须通过归属包访问

需要访问执行器、战斗操作、引用解析、模型或状态存储细节的代码，必须直接从 `trpg_py.engine...` 或 `trpg_py.store...` 导入，而不是依赖根目录旁路入口。

- 选择这一方案是因为实现归属已经明确，直接导入归属包可以避免重复 API 面。
- 备选方案：继续允许根目录和子包两套入口长期并存。
  - 否决原因：会持续制造维护负担，也会让规范难以约束未来新增模块的落点。

### 决策 3：稳定公共 API 只通过 `trpg_py.__init__` 维护

项目仍然保留顶层导入能力，但范围应当被压缩到长期承诺的少数构件，例如执行入口与常用骰子运行时能力。顶层 API 的变更由 `__init__.py` 统一管理，而不是由多个根目录模块分散承担。

- 选择这一方案是因为它能保留简单用法，同时避免根目录模块树继续膨胀。
- 备选方案：完全取消顶层导出，要求所有调用方都走子包路径。
  - 否决原因：会让简单用法退化，也超出了这次收口重构的必要范围。

## 风险 / 权衡

- [直接根目录模块导入会失效] → 在 proposal 和 specs 中明确标记为 BREAKING，并在实现时同步更新项目内测试、示例和文档作为迁移样例。
- [顶层 `__init__` 可能被误用为“万能导出桶”] → 在新规范中限制根目录只保留精简稳定 API，禁止为内部实现继续添加平铺入口。
- [外部用户可能依赖未承诺的 facade] → 在设计和任务中要求列出受影响模块，并通过发布说明给出迁移目标路径。

## Migration Plan

1. 先确定保留在 `trpg_py.__init__` 的稳定公共 API 列表，以及 `errors.py` 的保留策略。
2. 更新项目内所有导入，改为使用 `trpg_py` 顶层稳定 API 或直接使用 `trpg_py.engine...`、`trpg_py.store...`。
3. 删除根目录薄 facade 文件，并补充或调整测试以覆盖新导入路径。
4. 运行回归测试，确认删除 facade 后项目内不再依赖旧路径。
5. 在最终发布说明中标出被移除的根目录模块及对应迁移路径。

回滚策略：若迁移中发现仍存在关键调用方依赖旧路径，可在未发布前暂时恢复个别 facade，但该回滚仅用于过渡，不改变目标架构。
