## 上下文

当前仓库已经形成可用的执行引擎，但核心实现仍集中在 `trpg_py` 包根目录。`executor.py` 直接依赖 `operations.py`、`state.py`、`dice.py`、`refs.py` 与 `models.py`，而 `main.py` 和测试又依赖顶层导出。继续在根目录扩展会把“对外 API”和“内部引擎实现”混在一起，后续再加入解析器、插件化规则或其他运行时层时会更难分层。

这次变更的重点不是改变 DnD5e 规则行为，而是建立稳定的代码组织边界：把内部引擎实现收拢到 `trpg_py.engine`，同时为现有调用方保留兼容入口。

## 目标 / 非目标

**目标：**
- 建立 `trpg_py.engine` 作为核心运行时逻辑的统一命名空间。
- 将执行器、原子操作、状态工具和骰子能力迁移到 `engine` 子模块下的清晰分层文件中。
- 保留当前顶层公共 API 的兼容导出，避免现有示例、测试或外部调用方立即失效。
- 为后续新增引擎能力预留明确落点，减少继续向包根目录扩散实现代码。

**非目标：**
- 不在本次变更中修改任务文档格式、规则判定语义或执行报告结构。
- 不要求一次性重写所有数据模型或错误类型命名空间；若现有位置足够稳定，可先保留。
- 不引入新的第三方依赖，也不在本次变更中设计插件系统。

## 决策

### 决策 1：使用 `trpg_py.engine` 作为内部实现主命名空间

`engine` 可以明确表达“这是运行时内核”，比继续增加顶层模块更利于后续把解析、适配器、CLI 等外围能力与内核分开。

考虑过的替代方案：
- 继续保留顶层平铺模块：短期改动最小，但会继续放大模块边界混乱的问题。
- 使用更细碎的新顶层包（如 `runtime`、`core`）：可行，但当前目标聚焦于先建立一个稳定收纳层，`engine` 更直接。

### 决策 2：迁移内部实现，同时保留顶层兼容导入

现有 `main.py` 通过 `trpg_py` 顶层导入 `FixedDiceRoller` 与 `execute_task`，测试也大概率直接依赖当前模块路径。迁移时应让顶层继续 re-export 稳定公共 API，必要时保留轻量兼容包装模块，避免一次性破坏现有使用者。

考虑过的替代方案：
- 直接切断旧导入路径：结构更“干净”，但会让这次纯重构带来不必要的破坏性变更。
- 仅移动文件、不保留导出兼容：会把迁移成本转嫁给所有调用方，不利于渐进演进。

### 决策 3：按职责拆分 `engine` 内部模块，而不是把所有旧文件原样搬运

为了真正提升可扩展性，`engine` 下应体现基本职责分层，例如执行编排、操作执行、状态访问、随机数/骰子处理。这样后续扩展目标更清晰，也便于测试按模块聚焦。

考虑过的替代方案：
- 原样搬运到 `engine/` 后保持旧文件名和耦合关系：迁移成本低，但对后续扩展帮助有限。
- 一次性进行大规模重命名和接口抽象：长期可能更优，但本次风险较高，容易让重构和行为修改混在一起。

## 风险 / 权衡

- [风险] 迁移过程中包内导入路径容易出现循环依赖或漏改。 → 缓解措施：先定义清晰的 `engine` 分层边界，并补充针对导入与基本执行链路的测试。
- [风险] 旧导入路径兼容处理不完整，会导致 `main.py` 或外部调用方失效。 → 缓解措施：明确保留顶层公共导出，并为兼容导入增加回归测试。
- [风险] 仅做文件搬迁但不建立边界，收益会偏小。 → 缓解措施：任务中要求同时整理模块职责与导入入口，而不只是机械移动文件。

## 迁移计划

1. 创建 `trpg_py/engine/` 及其分层模块。
2. 将核心逻辑迁移到 `engine` 下，并调整包内导入。
3. 在 `trpg_py/__init__.py` 及必要的兼容模块中重新导出稳定 API。
4. 更新测试，覆盖 `engine` 新入口与现有顶层入口。
5. 运行相关测试与 demo，确认行为保持一致。

## 开放问题

- `models.py`、`errors.py`、`refs.py` 是否也应在本轮一并纳入 `engine`，还是先保留为共享基础模块，需要在实现时根据耦合度决定。
