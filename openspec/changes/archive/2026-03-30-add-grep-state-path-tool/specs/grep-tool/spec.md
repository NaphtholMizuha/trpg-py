## 新增需求

### 需求:grep 工具必须驻留在 agent.tools 命名空间
系统必须在 `trpg_py.agent.tools` 命名空间下提供名为 `grep` 的状态路径检索工具能力，并且该能力必须可以被 Python 调用方直接导入和使用，而不是仅作为 planner 内部私有辅助逻辑存在。

#### 场景:调用方从 agent.tools 使用 grep
- **当** 开发者为 planner 或其他 agent 组装工具集
- **那么** 可以从 `trpg_py.agent.tools` 访问 `grep` 工具实现
- **那么** 调用方无需自行遍历全部 state 路径来做模糊筛选

### 需求:grep 工具必须基于 canonical 点路径集合执行模糊检索
系统必须让 `grep` 基于当前 state 中真实存在的 canonical 点路径集合执行关键词匹配与排序，禁止返回不存在于当前 state 的伪路径，也禁止引入与既有点路径语义不一致的新路径格式。

#### 场景:grep 返回真实存在的候选路径
- **当** 调用方向 `grep` 提交一组关键词
- **那么** 工具只从当前 state 的 canonical 点路径中筛选候选
- **那么** 返回体中的每条候选路径都必须是当前 state 中真实存在的叶子点路径

### 需求:grep 工具必须返回叶子路径候选及匹配依据
系统必须让 `grep` 返回按相关性排序的叶子路径候选，并且每条候选必须包含可供调用方理解的匹配依据或原因，禁止只返回一个不可解释的裸字符串列表。

#### 场景:grep 返回排序后的叶子路径
- **当** 调用方向 `grep` 提交与状态事实相关的关键词
- **那么** 返回体包含一组按相关性排序的候选叶子路径
- **那么** 每条候选必须包含路径本身以及匹配原因、得分或等价解释字段
- **那么** 返回体不得把中间节点伪装成可直接读取的叶子路径

### 需求:grep 工具必须显式区分命中、无命中和错误
系统必须通过稳定的结构化语义区分 `grep` 的命中、无命中和执行错误，禁止把“没有相关路径”和“工具故障”折叠为同一种模糊结果。

#### 场景:grep 返回命中结果
- **当** 调用方向 `grep` 提交有效关键词且当前 state 中存在相关叶子路径
- **那么** `grep` 返回 `status=ok`
- **那么** 返回体包含一个或多个排序后的候选路径

#### 场景:grep 返回无命中结果
- **当** 调用方向 `grep` 提交有效关键词但当前 state 中不存在足够相关的叶子路径
- **那么** `grep` 返回 `status=no_match`
- **那么** 调用方可以据此判断这是状态发现证据不足而不是系统故障

#### 场景:grep 返回错误结果
- **当** `grep` 在执行过程中发生工具级异常
- **那么** `grep` 返回 `status=error`
- **那么** 调用方可以区分该失败与正常无命中

### 需求:grep 工具必须保持只做路径发现而不返回状态值
系统必须要求 `grep` 只负责路径发现，禁止直接返回候选路径上的当前状态值，也禁止将候选路径伪装为已确认事实；状态值确认必须继续通过 `read` 完成。

#### 场景:planner 使用 grep 做路径发现
- **当** planner 调用 `grep` 查找某类状态字段
- **那么** 返回体只包含候选路径及其匹配解释
- **那么** planner 若要确认当前值仍必须显式调用 `read`

### 需求:grep 返回语义必须可直接驱动 planner 分支决策
系统必须保证 `grep` 的返回结果足够稳定，使 planner 可以根据其结果决定“进入批量 `read` 收口”“回退到 `list` 做补充导航”或“将该事实视为当前 state 缺失”，禁止把 `grep` 设计成只能提供不可操作的模糊提示。

#### 场景:planner 根据 grep 命中进入 read 收口
- **当** `grep` 返回一组与关键词相关的叶子路径候选
- **那么** planner 可以直接选择其中一组候选做批量 `read`
- **那么** planner 无需先通过多轮 `list(prefix)` 才能进入值确认

#### 场景:planner 根据 grep 无命中决定补充策略
- **当** `grep` 返回 `status=no_match`
- **那么** planner 可以将该结果解释为当前 state 缺少相关路径发现证据
- **那么** planner 可以回退到 `list` 做补充导航或进入 `needs_human`
- **那么** planner 不得围绕同一关键词主题无限重试

### 需求:grep 工具每次调用必须使用 loguru 记录输入和输出
系统必须要求 `grep` 工具在每次调用时通过 `loguru` 记录调用输入、输出状态和错误信息，禁止把这类运行期日志责任留给上层调用方临时实现。

#### 场景:grep 成功返回候选
- **当** 调用方向 `grep` 提交有效关键词且工具返回 `status=ok`
- **那么** 系统必须记录本次调用的关键词摘要
- **那么** 系统必须记录返回状态以及候选数量等结果摘要

#### 场景:grep 无命中
- **当** 调用方向 `grep` 提交有效关键词且工具返回 `status=no_match`
- **那么** 系统必须记录本次调用的关键词摘要
- **那么** 系统必须记录无命中状态

#### 场景:grep 调用失败
- **当** `grep` 在执行过程中发生异常并返回错误语义
- **那么** 系统必须记录本次调用的关键词摘要
- **那么** 系统必须记录错误类型和错误信息

### 需求:grep 工具必须提供可手动运行的 smoke 脚本
系统必须提供一个位于 `smoke/test_grep.py` 的可手动运行脚本，用于让开发者直接观察 `grep` 的路径检索、无命中和错误边界，而不是只能通过单元测试断言理解其行为。

#### 场景:开发者运行 grep smoke 脚本
- **当** 开发者在本地执行 `smoke/test_grep.py` 或等价命令
- **那么** 脚本会展示至少一次关键词命中结果
- **那么** 脚本会展示至少一次无命中结果
- **那么** 开发者可以从输出中看出 `grep` 的输入输出边界
