## 上下文

当前项目已经具备一套可运行的 DnD5e 解析原型和一轮边界回归测试，但尚未把剩余高价值规则分支全部固化为可测试行为。尤其是非攻击检定的天然骰解释、伤害的 `on_save=none` 与暴击分支、`line` / `cone` 范围模板，以及 `main.py` 在 `skipped` 步骤与自定义布局案例上的展示效果，都属于“用户一看就会拿来判断系统是否可信”的部分。

同时，`main.py` 当前通过多段 `if example_name == ...` 维护 demo 状态与骰子，单次只能跑一个案例。随着 demo 数量增加，这种方式会越来越不利于维护，也不方便一次性展示全部能力。

## 目标 / 非目标

**目标：**
- 将剩余 Top 8 高价值规则分支正式纳入规范与测试。
- 让 `main.py` 支持一次运行全部已注册 demo，并以稳定顺序输出每个案例的摘要。
- 为 `skipped` 步骤、自定义布局结果和批量 demo 输出补上集成测试。

**非目标：**
- 不引入新的 CLI 框架或第三方测试框架。
- 不实现完整的战棋几何系统，只覆盖当前已支持且最值得验证的范围模板。
- 不把 `main.py` 演变为完整的测试运行器；它仍然是 demo/展示入口，而不是替代 `unittest`。

## 决策

### 决策 1：将剩余规则缺口转化为“实现 + 测试 + demo”成组交付

- 对于 `save nat1`、`ability/skill nat20`、暴击伤害、`on_save=none`、`line` / `cone` 等分支，不只补单测，也补至少一个面向演示的案例或可读输出断言。
- 这样能同时保护内部语义和对外展示，减少“代码是对的，但别人看不懂”的情况。
- 备选方案：只继续补单元测试。
  该方案实现快，但不能直接提升演示层的说服力。

### 决策 2：用显式 demo 注册表替代 `main.py` 中分散的条件分支

- 引入一个集中式 demo 注册表，统一描述 demo 名称、任务文件、初始状态构造和固定骰子。
- 单案例模式与 `all` 批量模式都基于同一注册表运行，避免重复逻辑。
- 备选方案：继续在 `build_demo_state` / `build_demo_roller` 中堆叠 `if` 分支。
  该方案短期可行，但 demo 数量继续增长时会迅速变得难维护。

### 决策 3：`all` 模式按稳定顺序逐个运行 demo，并输出分段摘要

- `main.py all` 将遍历全部已注册 demo，并为每个 demo 渲染独立摘要区块。
- 若某个 demo 失败，批量运行仍应继续，以便一次性暴露全部结果；最终再给出整体汇总状态。
- 备选方案：遇到第一个失败即停止。
  该方案更接近测试运行器，但不利于 demo 审阅与展示。

### 决策 4：`main.py` 集成测试只断言高价值信息

- 对 `skipped`、自定义布局、批量模式等场景，测试只校验任务名、步骤状态、关键路径变更和分段标题等高价值片段。
- 备选方案：做全文快照。
  该方案会让展示文案难以演进。

## 风险 / 权衡

- [批量 demo 模式会让 `main.py` 逻辑更复杂] → 通过集中注册表和共用渲染逻辑控制复杂度。
- [规则分支越多，示例与测试的维护成本越高] → 只补高价值、容易回归且最能建立信任的案例。
- [批量运行继续执行失败案例后，输出可能更长] → 使用清晰的分段标题和最终汇总降低阅读负担。

## 迁移计划

- 先扩展 combat operations 的规则分支规范。
- 再补 `demo-runner` 规范，明确 `all` 模式和展示行为。
- 实现规则分支、demo 注册表与批量运行。
- 最后补单元测试、操作测试和 `main.py` 集成测试。
