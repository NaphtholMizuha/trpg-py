## 新增需求

### 需求:search 工具必须支持当前 RAG 知识库的父子节点上下文回收
系统必须在命中带有 `parent_id` 的子节点时，根据该 `parent_id` 尝试回收父节点正文，并以可选 `parent_text` 形式返回给调用方，禁止继续把 payload 内嵌 `parent_content` 作为当前知识库的长期依赖。

#### 场景:命中子节点后回收父节点正文
- **当** `search` 命中了一个 payload 含有 `parent_id` 的子节点
- **那么** 系统必须尝试根据该 `parent_id` 读取父节点
- **那么** 父节点读取成功时，该命中的返回结果必须包含 `parent_text`
- **那么** 命中的 `text` 仍然必须保持为子节点正文，而不是被父节点正文替换

#### 场景:父节点上下文不可回收时降级返回
- **当** `search` 命中了子节点，但 `parent_id` 缺失、父节点不存在或父节点读取失败
- **那么** 系统不得因此把整次检索改判为 `error`
- **那么** 系统必须继续返回该子节点命中结果
- **那么** 该命中可以不包含 `parent_text`

## 修改需求

### 需求:search 工具必须支持混合检索和 rerank
系统必须通过混合检索召回候选规则文本，并使用 reranker 对候选结果进行最终重排。系统禁止将第一版 `search` 工具降级为仅依赖单一召回路径的简单检索。对于当前父子节点知识库，reranker 必须以候选子节点正文为主进行排序，父节点正文只能在最终命中确定后作为补充上下文回收，禁止在候选重排前把完整父块批量注入 reranker 造成长文本污染。

#### 场景:search 使用混合检索召回候选
- **当** 调用方向 search 工具提交一个有效 query
- **那么** 工具必须结合至少两类检索信号召回候选结果
- **那么** 系统不得只依赖单一关键词匹配或单一向量召回完成检索

#### 场景:search 先对子节点 rerank 再补父节点上下文
- **当** 混合检索召回了多个候选结果，且其中部分候选带有 `parent_id`
- **那么** 工具必须先基于候选子节点正文完成 reranker 重排
- **那么** 工具不得在候选重排前向 reranker 批量注入完整父节点正文
- **那么** 工具必须在最终命中顺序确定后，才按需回收父节点正文并填入 `parent_text`

### 需求:search 工具必须根据 query 从 Qdrant 检索规则原文
系统必须允许调用方提供 query，并使用该 query 向 Qdrant 检索匹配的规则文本。系统返回的命中结果必须保留原始文本及必要元数据，禁止把检索结果替换为模型生成的摘要或规则推断。对于当前 `trpg_knowledge` 知识库，search 必须以 payload 中的 `text` 作为命中正文来源，并稳定暴露 `book`、`path`、`doc_type`、`title`、`parent_id`、`section_titles` 等当前 schema 字段，而不是依赖旧版 `content`、`file`、`parent_content` 等历史字段作为长期契约。search 默认认证信息必须通过统一配置解析后的环境变量密钥获取，而不是要求调用方把密钥直接写入项目配置文件。

#### 场景:search 返回匹配原文
- **当** 调用方向 search 工具提交一个有效 query
- **那么** 工具会向 Qdrant 发起检索
- **那么** 返回结果中的每条命中都包含匹配原文
- **那么** 返回结果可以包含诸如标题、定位信息、分数等必要元数据
- **那么** 返回结果不得伪装成规则事实提取或 `TaskDocument` 建议
- **那么** 默认配置路径不得要求调用方在配置文件中直接保存真实密钥

#### 场景:search 返回当前知识库的稳定来源字段
- **当** `search` 命中了当前 `trpg_knowledge` 集合中的节点
- **那么** 每条命中的正文必须来自 payload 的 `text`
- **那么** 每条命中的元数据必须可以稳定提供 `book`、`path`、`doc_type`、`title`
- **那么** 每条命中的元数据必须在存在时保留 `parent_id` 和 `section_titles`
- **那么** 调用方不得被迫依赖 `file`、`type`、`parent_content` 等历史键名来理解命中来源

### 需求:search 工具必须提供可手动运行的集成测试脚本
系统必须提供一个位于 `smoke/test_search.py` 的可手动运行脚本，用于让开发者直接验证 search 工具的真实检索效果，而不是只依赖自动化测试或底层客户端调用。该脚本的人类可读输出必须优先展示当前知识库的来源字段和章节路径，便于开发者核对命中是否与 `rag.md` 中定义的 schema 一致。

#### 场景:开发者手动验证 search 效果
- **当** 开发者在本地执行 `smoke/test_search.py` 并提供 query 或其他参数
- **那么** 脚本调用系统现有 search 能力完成一次检索
- **那么** 输出中可以观察命中、无命中或错误等结构化结果

#### 场景:smoke 输出展示当前知识库来源字段
- **当** `smoke/test_search.py` 以人类可读模式打印命中结果
- **那么** 输出必须能够展示 `title`、`doc_type`、`book`、`path`
- **那么** 输出必须在存在时展示 `section_titles`
- **那么** 输出不得继续只依赖 `file`、`locator`、`type` 等旧字段作为主要来源摘要
