## 上下文

当前仓库只有最小 Python 工程骨架，还没有战斗状态模型、规则执行框架或规范化测试结构。用户希望通过一个任务 JSON 描述 DnD5e 战斗动作，例如攻击意图、豁免判定、伤害数值、资源消耗和状态写回路径，然后由 Python 执行器按步骤更新状态。

这个需求本质上不是“实现一个具体法术”，而是建立一层可组合的规则执行引擎。它需要同时解决三类问题：

- 如何描述战斗动作：任务 JSON 的结构、步骤顺序、输入参数与条件分支。
- 如何读写战斗状态：点分路径访问、路径不存在时的行为、执行结果如何回写。
- 如何复用规则逻辑：把检定、伤害、资源和效果处理收敛成原子操作，而不是在每个动作里重复写流程代码。
- 如何选定作用对象：既支持直接给定单体目标，也支持基于范围、阵营和过滤条件动态查找目标集合。
- 如何适配不同状态结构：让任务 JSON 显式声明它依赖哪些状态字段，而不是把 `hp`、`ac`、坐标或效果列表写死在引擎实现里。

约束如下：

- 第一阶段应保持为纯 Python 内部能力，不依赖数据库、Web 服务或外部规则引擎。
- 任务 JSON 必须可测试、可复现，不能依赖任意 Python 表达式执行。
- DnD5e 规则覆盖范围只聚焦战斗解析核心路径，不一次性实现全部职业、法术和特殊边缘规则。

## 目标 / 非目标

**目标：**

- 定义一个可校验的任务 JSON 结构，用于描述由多个步骤组成的 DnD5e 判定流程。
- 提供一个执行器，按顺序运行步骤，并维护统一的执行上下文、步骤结果和最终状态变更。
- 提供点分路径状态访问器，支持从嵌套字典/列表中读取和写入战斗状态。
- 提供统一的目标集合模型，让单体目标和范围目标都能作为步骤结果被后续消费。
- 提供显式字段映射能力，使选择、检定、伤害和效果类步骤都能适配不同的状态字段组织形式。
- 提供一组可注册的原子操作，至少覆盖检定、豁免、伤害、资源扣减和效果增减。
- 输出标准化执行报告，便于测试、调试和上层系统消费。

**非目标：**

- 不在本次变更中实现完整 DnD5e SRD、所有法术/职业特性或完整条件系统。
- 不支持在任务 JSON 中执行任意 Python 代码或动态脚本。
- 不实现持久化、网络 API、图形界面或完整战斗编排系统。
- 不处理多线程并发解析或跨战斗会话的共享状态同步。

## 决策

### 决策 1：任务模型采用“统一文档外形 + 顺序步骤”

任务文档采用统一顶层外形：

- `task_id`
- `version`
- `policy`
- `context`
- `steps`

其中 `steps` 为顺序执行数组。每个步骤采用统一结构：

- `id`
- `type`
- `kind`
- `tags`（可选）
- `when`（可选）
- `args`

执行器按数组顺序执行步骤；是否跳过步骤由 `when` 条件控制，而不是通过隐式代码分支实现。

这样选择的原因：

- 顺序步骤最贴合战斗解析流程，容易从“先命中，再豁免，再伤害，再写状态”的思维映射到 JSON。
- 统一的顶层与步骤外形便于做 schema 校验、模板生成和示例编写。
- `type` 与 `kind` 的组合让能力边界清楚，避免 JSON 拥有任意执行能力。
- 步骤 ID 可为后续步骤提供稳定引用，也有利于调试与测试断言。

备选方案：

- 方案 A：用嵌套 DSL 表达整棵规则树。被放弃，因为编辑和调试成本更高。
- 方案 B：直接把 Python 函数名暴露给 JSON。被放弃，因为会削弱校验、可移植性和安全性。

### 决策 1.5：步骤类型采用有限类别，优先遵循“选择→检定→结算”的数据流

步骤 `type` 使用有限的领域类别：

- `select`
- `check`
- `damage`
- `heal`
- `resource`
- `effect`
- `state`

其中 `kind` 用于在类别内部细分，例如 `check.attack`、`check.save`、`select.target`、`select.area`。虽然任务可以按需要组织步骤，但推荐的主路径是：

1. `select`
2. `check`
3. `damage` / `heal` / `effect` / `resource` / `state`

这样选择的原因：

- 这和实际 DnD5e 动作解析顺序最接近，读写体验自然。
- 把“找目标”“判定”“结算”拆开后，步骤职责更清晰，也更容易复用。
- 有限类别比无限 `op` 名称集合更适合长期维护与文档化。

备选方案：

- 方案 A：允许任意自定义步骤类型。被放弃，因为会削弱规范约束和互操作性。
- 方案 B：只用一个通用 `action` 类型。被放弃，因为后续行为分歧会被掩盖。

### 决策 2：值引用分为 `literal`、`state`、`context`、`result`

步骤参数中的值既可以是字面量，也可以是引用对象。执行器支持四类来源：

- `literal`：直接值。
- `state`：从战斗状态的点分路径读取。
- `context`：从任务级上下文读取，例如施法者、目标、DC 或外部注入变量。
- `result`：读取先前步骤输出，例如命中结果、豁免是否成功、已掷出的伤害值。

统一引用语法优先使用结构化引用，例如：

- `{ "$ref": "context.actor_id" }`
- `{ "$ref": "state.actors.hero_1.ac" }`
- `{ "$ref": "result.attack_roll.outcome" }`

这样选择的原因：

- 能让 JSON 在不引入表达式语言的前提下完成大部分数据流转。
- 把持久状态、执行期变量和中间结果区分开，减少路径歧义。

备选方案：

- 方案 A：所有值都用点分路径字符串表示。被放弃，因为无法区分状态与步骤结果来源。
- 方案 B：引入通用表达式求值器。被放弃，因为复杂度和安全风险过高。

### 决策 2.5：目标选择作为独立的选择类原子操作

目标确定不只依赖 `target_id`。很多 DnD5e 动作需要先从状态中查找候选目标，再依据范围、阵营、标签、存活状态或显式排除条件得出最终目标集合。因此，目标选择将被建模为一类独立原子操作，例如 `select.target`、`select.area` 和 `select.filtered`。

这些操作的统一输出为目标集合，而不是单一目标标识。即使是单体目标，也以 `target_ids` 长度为 1 的形式返回，供后续步骤复用。

这样选择的原因：

- 把“找谁受影响”和“如何结算影响”解耦，避免范围逻辑散落在伤害、豁免和效果操作内部。
- 单体与范围目标共享同一数据流，能降低后续步骤接口复杂度。
- 为法术、技能和 AI 决策提供稳定的中间结果格式。

备选方案：

- 方案 A：把范围查找嵌入 `damage` 或 `save` 操作。被放弃，因为会让操作职责混乱且难以复用。
- 方案 B：仅支持显式 `target_id`。被放弃，因为无法表达范围法术、多目标增益和按条件筛选目标。

### 决策 2.55：选择类操作通过 `field_map` 适配候选对象结构

选择类操作不假设候选对象必须固定拥有 `id`、`side`、`alive`、`tags`、`position.x` 和 `position.y` 这些字段。相反，任务 JSON 可以在步骤参数中声明 `field_map`，把这些逻辑字段映射到实际状态对象中的任意路径，例如：

- `id -> meta.id`
- `side -> faction.side`
- `alive -> status.alive`
- `position.x -> space.grid.col`
- `position.y -> space.grid.row`

这样选择的原因：

- 选择类操作最容易受到状态结构差异影响，先在这里引入显式映射可以显著提升复用性。
- 逻辑字段名保持稳定，而实际状态结构可以按项目需要自由组织。

备选方案：

- 方案 A：要求所有状态对象都实现统一 actor schema。被放弃，因为会限制上层系统的数据建模。
- 方案 B：为每种状态结构单独实现一套选择逻辑。被放弃，因为重复度和维护成本过高。

### 决策 2.6：骰子规格在 JSON 中显式给出，规则语义与公式分离

所有带随机性的步骤都必须在任务 JSON 中显式声明骰子规格。例如，攻击、豁免和属性检定使用 `1d20`，伤害使用单个或多个显式骰子规格，如 `1d8`、`2d6`。这些骰子规格负责声明随机基础，但不承担完整规则语义。

优势、劣势、天然骰追踪、暴击、半伤、修正值来源和伤害类型等规则信息将作为独立字段表达，而不是编码进单个复杂公式字符串。对于检定步骤，优势/劣势与天然骰追踪优先使用标签数组表达，例如 `tags=["nat","adv"]`，而不是在公式中写成 `2d20kh1`。

这样选择的原因：

- 显式骰子规格便于校验、测试和执行日志输出。
- 把随机基础与规则语义分离后，JSON 更稳定，也更容易支持不同规则集或 house rule。
- 可以避免引入一个难以约束的表达式 DSL。

备选方案：

- 方案 A：使用单个复杂公式字符串承载全部语义，例如 `2d20kh1+5`。被放弃，因为解析复杂、校验困难且不利于规则扩展。
- 方案 B：在 JSON 中完全省略骰子规格，由操作内部隐式决定。被放弃，因为会削弱任务文档的显式性和可审计性。

### 决策 2.7：检定采用统一 `type=check` 描述，使用 `kind` 与 `tags` 区分语义

检定类步骤使用统一的领域描述：

- `type=check`：声明该步骤属于检定步骤
- `kind`：区分 `attack`、`save`、`ability`、`skill` 等具体检定类别
- `tags`：附加检定标签，例如 `nat`、`adv`、`disadv`

其中：

- `nat` 表示该步骤需要保留并解释自然骰值
- `adv` / `disadv` 表示该步骤具有优势或劣势候选语义

执行器可在内部将这些标签归并为规范化的执行参数，但任务 JSON 对调用方暴露的结构优先保持为 `type + kind + tags`。

这样选择的原因：

- 所有检定步骤共享同一外形，JSON 更一致，便于校验与模板化生成。
- `kind` 保留 DnD5e 语义分支，让攻击、豁免和能力检定可以共用框架但不混淆规则。
- `tags` 适合承载可组合的附加语义，后续也更容易扩展其他标记。

备选方案：

- 方案 A：为攻击、豁免、能力检定分别定义完全独立的步骤结构。被放弃，因为会导致重复字段过多。
- 方案 B：只保留 `op`，不引入 `type` 与 `kind`。被放弃，因为对上层 JSON 作者来说语义不够直观。

### 决策 3：状态变更由原子操作返回，执行器统一提交

原子操作不直接修改共享状态，而是返回结构化结果：

- `outputs`：该步骤供后续引用的中间结果。
- `changes`：建议写入的状态变更列表。
- `events`：可供日志或上层系统消费的事件。

执行器负责校验这些变更、按顺序提交到状态对象，并在执行报告中记录每次写入。

这样选择的原因：

- 统一提交点更容易测试，也便于未来加入审计、回滚或 dry-run。
- 原子操作可以更接近纯函数，降低耦合。

备选方案：

- 方案 A：每个操作直接持有状态对象并原地修改。被放弃，因为调试和测试成本更高。

### 决策 3.25：计算依赖字段通过显式路径模板声明

凡是原子操作在计算或写回过程中依赖的状态字段，都应允许由任务 JSON 显式给出，而不是依赖固定默认路径。典型例子包括：

- 攻击检定依赖的目标 AC
- 豁免/能力/技能检定依赖的修正值
- 伤害和治疗依赖的目标生命值路径
- 效果操作依赖的效果列表路径

这些字段优先通过显式路径或路径模板声明，例如：

- `target_ac_path`
- `target_ac_path_template`
- `modifier_path`
- `modifier_path_template`
- `target_hp_path_template`
- `effects_path_template`

这样选择的原因：

- 这让引擎对状态结构的耦合降到最低。
- 任务 JSON 更接近一个可移植的执行计划，而不是隐式绑定到某个项目的内部状态模型。

备选方案：

- 方案 A：为常见字段保留一套硬编码默认路径。可以作为兼容层存在，但不应成为唯一用法。
- 方案 B：把所有字段适配工作都放到状态预处理阶段。被放弃，因为这会把显式性从任务文档中拿掉。

### 决策 3.5：步骤间数据流统一通过 `result.<step_id>` 传递

每个步骤的标准输出将被挂载到执行结果命名空间中，后续步骤通过 `result.<step_id>.<field>` 引用前序结果。例如：

- `result.pick_target.target_ids`
- `result.attack_roll.outcome`

这样选择的原因：

- 步骤间依赖关系清晰且可追踪。
- 这种方式便于在日志、调试和测试中直接定位数据来源。

备选方案：

- 方案 A：把所有中间值写回全局 `context`。被放弃，因为会让执行期数据与输入上下文混杂。

### 决策 4：点分路径支持字典键和列表索引，写入时允许创建缺失的字典节点

状态访问器采用点分路径形式，例如 `actors.goblin_1.hp.current`。若路径片段为整数，则视为列表索引；若为字符串，则视为字典键。写入时允许自动创建缺失的字典节点，但不自动扩容列表。

这样选择的原因：

- 点分路径足够直观，也便于和 JSON 任务配置搭配。
- 自动创建字典节点可以减少大量样板初始化代码。
- 禁止自动扩容列表能避免索引错误悄悄掩盖数据问题。

备选方案：

- 方案 A：只支持字典、不支持列表。被放弃，因为效果列表和目标集合很常见。
- 方案 B：写入时禁止创建任何缺失节点。被放弃，因为配置使用成本较高。

### 决策 5：执行流程采用“先校验，后执行，运行时失败即停止后续步骤”

执行器在真正修改状态前，先完成任务结构、步骤引用、操作名和基础参数的校验。若校验失败，则整个任务不得产生状态写入。若执行过程中某一步运行失败，则保留此前已提交的变更，停止后续步骤，并在结果中标记失败步骤和错误原因。

这样选择的原因：

- 结构问题应尽早暴露，避免半执行半失败。
- 对战斗流程来说，前序步骤已经产生的命中、消耗或日志通常不应被隐式回滚。

备选方案：

- 方案 A：整任务事务性回滚。暂不采用，因为需要额外的状态快照与冲突语义设计。

### 决策 6：随机数通过注入的掷骰接口提供

所有涉及 d20 或伤害骰的操作都通过统一的掷骰接口获取结果，而不是直接调用全局随机函数。测试时可注入固定结果或伪随机种子，确保执行结果可复现。

这样选择的原因：

- 这是测试判定流程的关键基础设施。
- 后续也可以无缝接入真实骰子服务、日志或回放。

备选方案：

- 方案 A：在操作内部直接调用 `random`。被放弃，因为测试不可控。

### 决策 6.5：天然 20/1 与优势/劣势按检定类型解释

检定操作共享统一的输出结构，但不共享完全相同的规则语义。默认情况下：

- 攻击检定中，天然 20 表示自动命中且触发暴击，天然 1 表示自动失手。
- 豁免检定中，天然 20 和天然 1 默认不表示自动成功或自动失败。
- 属性/技能检定中，天然 20 和天然 1 默认不表示自动成功或自动失败。

检定结果对外统一返回四态枚举 `outcome`：

- `success`
- `fail`
- `crit_success`
- `crit_fail`

但 `crit_success` 与 `crit_fail` 是否可出现，以及它们的实际含义，取决于 `kind` 与规则配置。默认情况下，攻击检定在 `nat` 标签开启时会将天然 20/1 映射为 `crit_success` / `crit_fail`；豁免检定与属性/技能检定默认仍只返回 `success` / `fail`，除非规则策略显式放宽。

优势和劣势也不编码进骰子公式，而通过 `tags` 表达，并在执行时归并为普通、优势或劣势三态结果；同侧来源不叠加，优势与劣势同时存在时相互抵消。

这样选择的原因：

- 这更贴近 DnD5e 默认规则，避免把攻击语义错误地套用到豁免或能力检定。
- 统一输出结构可以复用执行框架，而按操作类型解释能保留规则准确性。
- 四态结果让后续伤害、日志和特效步骤更容易基于单一字段分支。

备选方案：

- 方案 A：让所有 d20 检定都共享天然 20/1 的自动成功/失败语义。被放弃，因为不符合默认 DnD5e 规则。
- 方案 B：把优势/劣势编码进公式字符串。被放弃，因为这会让掷骰表达和规则解释耦合过深。
- 方案 C：只返回布尔成功值，不提供四态结果。被放弃，因为会丢失暴击/大失败这一层关键分支信息。

### 决策 7：第一阶段范围查找仅依赖基础空间模型

范围选择操作依赖战斗状态中的基础空间信息，例如坐标、阵营、标签和存活状态。第一阶段仅支持基础几何与过滤：

- 基于点位或格点坐标的简单距离判断
- 基础形状，如单体、球形、锥形或线形
- 基于阵营、标签、显式排除列表和存活状态的过滤

第一阶段不要求实现复杂视线、掩护、绕行和不规则几何。

这样选择的原因：

- 能以较低复杂度覆盖大多数常见法术与动作。
- 避免在执行框架落地前把问题膨胀成完整战棋空间系统。

备选方案：

- 方案 A：同时实现视线、遮挡和掩护。被放弃，因为会显著扩大首期范围。

## 风险 / 权衡

- [JSON 配置较冗长] → 先保证执行模型清晰，后续再通过模板、宏或更高层动作定义减少样板。
- [统一任务外形会引入固定样板] → 优先保证可校验性和稳定数据流，再通过高层模板与示例降低编写成本。
- [`field_map` 和路径模板会让 JSON 变长] → 把它们限定在真正依赖状态结构的步骤里使用，并保留合理的兼容默认值。
- [Dnd5e 规则边界复杂] → 第一阶段只定义核心原子操作，把抗性、优势来源、特例法术作为后续扩展点。
- [范围选择依赖空间模型] → 先约定最小 actor 空间字段，只支持基础距离与过滤，复杂几何后续扩展。
- [显式骰子规格会让步骤参数更细碎] → 保持骰子、修正值和规则语义分字段表达，优先可校验性，后续再通过高层模板减轻样板。
- [`tags` 语义可能逐步膨胀] → 首期只标准化 `nat`、`adv`、`disadv`，新增标签需要明确规则和消费方。
- [运行时失败会留下部分已提交状态] → 在执行报告中完整记录已应用变更，并为未来事务模式预留扩展空间。
- [点分路径写入灵活但可能掩盖拼写错误] → 对关键路径增加预校验，并在测试中覆盖常见错误路径。

## Migration Plan

这是一个全新能力，没有现有调用方需要迁移。推荐按以下顺序落地：

1. 先建立状态访问器、数据模型和执行器骨架。
2. 再实现最小原子操作集合与测试。
3. 最后补充示例任务 JSON，作为后续技能/法术实现的基础。

如果实现中发现任务模型不够表达复杂战斗动作，可在不破坏既有字段的前提下通过新增操作或上下文字段扩展。

## Open Questions

- 伤害结算第一阶段是否需要内建临时生命值、抗性、易伤与免疫规则，还是先通过显式乘数/钩子实现？
- buff/debuff 的唯一性和叠加规则是否需要在第一阶段就标准化？
- 是否需要在任务级提供显式的 `transactional` 模式，为未来完整回滚做准备？
- 范围选择的坐标模型应优先采用抽象距离还是显式二维坐标？
- 是否需要在任务级 `policy` 中预留规则变体开关，以支持非默认的天然 20/1 house rule？
- 默认路径是否应长期保留为兼容层，还是在后续版本中要求所有关键依赖字段都显式声明？
