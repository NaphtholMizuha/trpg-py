## ADDED Requirements

### 需求:任务文档必须先校验再执行
系统必须在执行任何步骤前校验任务文档结构，包括任务标识、步骤数组、步骤 `id` 唯一性、步骤 `op` 是否存在、引用目标是否合法，以及每个操作要求的基础字段是否齐备。若校验失败，系统禁止产生任何状态写入。

#### 场景:无效任务在执行前被拒绝
- **当** 调用方提交的任务缺少步骤 `id` 或引用了不存在的前序步骤结果
- **那么** 系统返回校验失败结果
- **那么** 原始状态对象不得发生变化

### 需求:任务文档必须使用统一的顶层结构
系统必须要求任务文档使用统一顶层字段：`task_id`、`version`、`policy`、`context` 和 `steps`。若缺少 `task_id`、`version` 或 `steps`，系统必须将任务视为无效。

#### 场景:缺少顶层标识字段的任务被拒绝
- **当** 调用方提交一个缺少 `task_id` 的任务文档
- **那么** 系统返回结构校验失败
- **那么** 系统不得开始任何步骤执行

### 需求:步骤必须使用统一的结构字段
系统必须要求每个步骤至少包含 `id`、`type`、`kind` 和 `args` 字段。`tags` 与 `when` 可以缺省，但若出现则必须是可校验字段，而不是任意未约束片段。

#### 场景:步骤以统一外形声明
- **当** 调用方定义一个步骤，包含 `id`、`type`、`kind` 与 `args`
- **那么** 系统接受该步骤进入后续校验
- **那么** 系统可以基于 `type` 与 `kind` 分派对应执行逻辑

### 需求:执行器必须按顺序执行步骤并支持条件跳过
系统必须按照 `steps` 数组顺序执行步骤。若步骤声明 `when` 条件且条件结果为假，系统必须跳过该步骤，并在执行报告中记录其为 `skipped`，不得提交该步骤的状态变更。

#### 场景:未命中时跳过伤害步骤
- **当** 任务中的攻击步骤先执行并输出 `hit=false`
- **当** 后续伤害步骤声明仅在该结果为真时执行
- **那么** 系统跳过该伤害步骤
- **那么** 目标生命值不得被修改

### 需求:执行器必须解析多来源值引用
系统必须支持步骤输入从字面量、战斗状态、任务上下文和前序步骤结果中取值，并在执行某一步之前解析为确定值。若引用路径不存在且该字段为必需输入，系统必须将该步骤标记为失败并停止后续步骤。

#### 场景:步骤读取前序结果和状态值
- **当** 豁免步骤输出 `success=true`
- **当** 后续伤害步骤同时引用 `state.actors.goblin.hp.current` 与该豁免结果
- **那么** 系统在执行伤害步骤前解析两类值
- **那么** 伤害步骤获得的输入中同时包含当前生命值与豁免成功标记

### 需求:执行器必须支持结构化引用语法
系统必须支持以结构化 `$ref` 形式引用 `context`、`state` 和 `result` 命名空间中的值。系统不得要求调用方通过未区分来源的裸路径字符串完成所有引用。

#### 场景:步骤通过 $ref 读取前序结果
- **当** 后续步骤使用 `{ "$ref": "result.attack_roll.outcome" }` 作为输入
- **那么** 系统将其解析为 `attack_roll` 步骤的输出字段
- **那么** 该值可参与后续条件判断或参数计算

### 需求:任务文档必须允许步骤显式声明依赖字段路径
系统必须允许步骤在 `args` 中显式声明其依赖的状态字段路径或路径模板，用于读取或写回战斗状态。系统不得要求所有计算都依赖固定的默认字段路径。

#### 场景:伤害步骤显式声明生命值路径模板
- **当** 调用方定义一个伤害步骤
- **当** 该步骤提供 `target_hp_path_template`
- **那么** 系统接受该步骤结构
- **那么** 后续执行阶段按该模板定位目标生命值字段

### 需求:任务文档必须显式声明骰子规格
系统必须要求所有带随机性的步骤在任务文档中显式声明骰子规格，例如 `1d20`、`1d8` 或 `2d6`。任务文档禁止仅通过隐式操作默认值推断随机基础，也禁止把优势、劣势或暴击规则全部编码进一个不可分解的公式字符串。

#### 场景:攻击步骤显式提供 d20 规格与检定标签
- **当** 调用方定义一个攻击步骤
- **当** 该步骤以独立字段提供 `dice=1d20` 和 `tags=["nat","adv"]`
- **那么** 系统接受该任务结构
- **那么** 执行器将骰子规格与检定标签分别传递给对应操作

### 需求:任务文档必须支持统一的检定步骤描述
系统必须允许检定步骤以统一结构声明 `type=check`，并通过 `kind` 区分攻击、豁免、能力或技能等具体类别。若步骤声明了检定标签，系统必须将其作为可校验字段处理，而不是作为自由文本忽略。

#### 场景:攻击检定使用 type 与 kind 标识
- **当** 调用方定义一个步骤，包含 `type=check` 与 `kind=attack`
- **当** 该步骤同时提供显式骰子规格和标签
- **那么** 系统将该步骤识别为攻击检定
- **那么** 后续执行阶段按攻击检定规则解释其结果

### 需求:执行器必须支持目标集合作为步骤间数据流
系统必须允许步骤输出目标集合，并允许后续步骤通过前序结果引用该集合。目标集合至少必须支持 `target_ids` 数组，并可选携带用于调试或日志的筛选元数据。

#### 场景:范围选择结果被后续豁免步骤消费
- **当** 目标选择步骤输出 `target_ids=["hero_1","hero_2","wolf_1"]`
- **当** 后续豁免步骤引用该结果作为输入
- **那么** 系统将该目标集合解析为豁免步骤的确定输入
- **那么** 豁免步骤针对集合中的每个目标执行处理

### 需求:执行器必须支持以 `result.<step_id>` 形式传递步骤结果
系统必须将每个已完成步骤的标准输出挂载到 `result.<step_id>` 命名空间中，供后续步骤引用。若调用方引用了不存在的步骤结果，系统必须将任务判定为无效或在运行时失败并停止后续步骤。

#### 场景:伤害步骤引用前序攻击结果
- **当** 攻击步骤 `attack_roll` 已输出 `outcome`
- **当** 伤害步骤引用 `result.attack_roll.outcome`
- **那么** 系统将该字段解析为攻击步骤的结果
- **那么** 伤害步骤可基于该字段决定是否执行

### 需求:执行器必须支持点分路径状态访问与写入
系统必须支持通过点分路径读取和写入嵌套状态对象；路径片段为整数时必须视为列表索引。写入时系统必须允许创建缺失的字典节点，但禁止在目标为列表索引且索引不存在时静默扩容。

#### 场景:写入时创建缺失字典节点
- **当** 任务步骤要写入 `actors.goblin_1.status.hex.source`
- **当** `actors.goblin_1.status` 已存在但 `hex` 节点尚不存在
- **那么** 系统创建缺失的字典节点并完成写入

### 需求:执行器必须返回标准化执行报告
系统必须返回包含任务状态、每个步骤执行状态、步骤输出、已提交状态变更、跳过信息、错误信息与事件列表的执行报告，以便测试和上层系统消费。

#### 场景:运行时失败会在报告中保留已执行信息
- **当** 前两个步骤已成功提交状态变更
- **当** 第三个步骤因无效路径写入而失败
- **那么** 系统停止后续步骤执行
- **那么** 返回结果中包含前两个步骤的输出与已提交变更
- **那么** 返回结果中包含第三个步骤的失败原因
