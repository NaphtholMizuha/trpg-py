## 上下文

当前解析器已经把目标选择和后续检定、伤害结算分层开来，但选择步骤只负责“找出谁”，还不负责“这个目标能不能选”。这会让一些 DnD5e 常见动作缺少关键前置校验，例如近战攻击是否在 5 尺内、远程攻击是否在武器射程内、火球术选定的爆点是否在法术射程内。

现有系统已经具备两类可复用输入：
- `select.target` 已有单体目标声明语义。
- `select.area` 已有 `origin`、范围模板、候选池和 `field_map`。

这次变更只补“目标选取合法性”的距离校验，不扩展 LOS、掩护、可见性、路径绕行或复杂触及规则。

## 目标 / 非目标

**目标：**
- 为 `select.target` 增加基于 source 与 target 位置的距离校验。
- 为 `select.area` 增加基于 source 与 origin 的距离校验。
- 在任务 JSON 中提供统一且显式的 `targeting` 输入块。
- 明确超距时的失败语义和执行报告表现。

**非目标：**
- 不引入完整的视线、掩护、路径、障碍物和三维空间规则。
- 不在本次变更中修改 `check.*`、`damage.*` 的核心判定语义。
- 不要求所有选择步骤都必须配置距离校验；只有声明了 `targeting` 的步骤才执行该逻辑。

## 决策

### 决策 1：把目标选取距离校验放在 `select` 层

目标是否合法是选择问题，而不是攻击检定或伤害结算问题。把距离校验放入 `select.target` / `select.area`，可以让后续 `check`、`damage`、`effect` 继续只关注自身规则。

考虑过的替代方案：
- 放进 `check.attack` 或 `check.save`：会让目标选择规则与检定规则耦合，后续扩展法术选点时也会重复实现。
- 增加单独的 `targeting.validate` 步骤类型：语义可行，但会把一个紧密相关的前置步骤拆散，让任务文档更冗长。

### 决策 2：统一使用 `targeting` 块声明距离校验输入

选择步骤在 `args` 下可选提供 `targeting`。该对象至少支持：
- `source_position`
- `max_range`
- `range_metric`

`select.target` 还需要通过候选池和 `field_map` 读取目标位置；`select.area` 则使用已有的 `origin` 作为选点位置。

考虑过的替代方案：
- 把 `source_position`、`max_range` 平铺到 `args` 顶层：短期更省字段，但后续加入 LOS、reach、visibility 会迅速变乱。

### 决策 3：单体选目标与范围选点采用不同的测距对象

- `select.target` 的距离校验是 `source_position -> target_position`
- `select.area` 的距离校验是 `source_position -> origin`

这是本次设计中最重要的语义边界。`select.area` 在“选点是否合法”这一步不依赖范围内其他候选对象的位置；候选对象的位置只用于后续范围覆盖计算。

考虑过的替代方案：
- 将所有选择统一为 `source_position -> target_position`：无法表达火球术这类“选点后再覆盖范围”的技能。
- 将所有选择统一为 `source_position -> origin`：无法覆盖近战攻击与单体法术的目标选取距离判断。

### 决策 4：超距必须导致步骤失败

若目标或选点超出允许距离，步骤必须失败，并中止后续执行。这与“选点合法但范围内没有目标”不同；后者仍应成功，只是返回空 `target_ids`。

考虑过的替代方案：
- 超距返回空集合：会把非法选择与合法但无命中对象混淆，不利于日志展示、测试和调用方理解。

## 风险 / 权衡

- [风险] 现有示例 JSON 可能需要新增 `targeting` 字段。 → 缓解措施：保持 `targeting` 为可选字段，不影响未声明距离校验的旧任务。
- [风险] 距离度量规则如果后续扩展为格子制，当前字段可能不够。 → 缓解措施：保留 `range_metric`，后续可在不破坏顶层结构的情况下新增取值。
- [风险] `select.target` 对目标位置的依赖会提高输入复杂度。 → 缓解措施：继续复用 `entity_pool + field_map`，避免额外引入新的目标位置路径模板体系。
