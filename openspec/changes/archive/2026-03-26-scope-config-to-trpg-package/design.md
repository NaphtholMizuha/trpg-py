## 上下文

`centralize-project-config` 已经为 `trpg_py` 建立了统一配置入口，并把 planner、search 这类包内运行时能力迁移到了集中配置模型。随后 `unify-all-project-config` 继续把统一配置边界外推到仓库根目录脚本，例如 `main.py` 和 `test_fetch_keys.py`。这让“包内运行配置”和“仓库脚本示例默认值”被放进了同一个治理范围。

当前真正需要解决的问题不是统一配置是否有价值，而是它的适用边界。`trpg_py` 包内模块属于可复用运行时能力，适合由统一配置管理；而仓库根目录脚本更接近 demo、smoke runner 或开发辅助入口，它们不一定需要成为统一配置模型的一部分。

这次设计的主要利益相关者包括：
- 维护 `trpg_py` 包内运行时能力的开发者，需要明确哪些默认值必须接入统一配置。
- 使用仓库脚本做演示和调试的开发者，需要知道哪些默认值可以继续保留在脚本或 CLI 中。
- 后续新增配置的实现者，需要稳定边界，避免再次把脚本示例与库配置耦合在一起。

## 目标 / 非目标

**目标：**
- 明确统一配置只覆盖 `trpg_py` 包内长期运行配置与工具默认参数。
- 保留“新增包内项目级默认配置必须先接入统一配置入口”的治理规则。
- 明确仓库根目录脚本、demo 入口和演示测试脚本不受统一配置强制约束。
- 调整相关规范，使 `demo-runner` 与 `fetch-keys-tool` 不再隐含必须从统一配置读取脚本默认值。

**非目标：**
- 不移除现有统一配置入口，也不回退 planner/search 等包内模块的集中配置。
- 不禁止仓库脚本在需要时主动复用统一配置；本次只取消“必须接入”的约束。
- 不重做 `main.py`、`test_fetch_keys.py` 或其他脚本的整体结构。
- 不把“所有仓库文件都必须纳入配置治理”当作目标。

## 决策

### 决策: 统一配置的治理边界以 `trpg_py` 包目录为准

统一配置的规范边界以 `trpg_py/` 为主。只要某项长期默认值属于包内运行时行为，且调用方可能希望在不改代码的前提下调整它，它就必须进入统一配置模型。反过来，位于仓库根目录的脚本、演示入口和测试辅助脚本默认不纳入强制治理范围。

考虑过的替代方案：
- 继续沿用“整个仓库一份配置、所有长期默认值都必须接入”的方向：边界看似简单，但会让库配置和示例脚本耦合得过紧。
- 完全按文件位置分散管理，不再强调统一配置：会破坏已经在包内建立起来的唯一入口。

### 决策: 对仓库脚本采用“可复用但不强制”的策略

`main.py`、`test_fetch_keys.py` 这类仓库脚本可以在实现上选择复用统一配置，但规范层面不再要求它们把默认 demo、默认 fixture 路径或脚本级参数声明为统一配置真相。这样既保留工程灵活性，也避免把演示脚本误当成库 API 的一部分。

考虑过的替代方案：
- 明确禁止脚本读取统一配置：限制过强，会把本来可复用的能力也排除掉。
- 继续要求所有脚本必须读取统一配置：会扩大维护面，并增加对 demo/测试脚本的改造成本。

### 决策: 继续保留新增包内配置必须先扩展统一入口的治理规则

虽然统一配置边界收紧了，但包内治理规则不变。未来任何 `trpg_py` 模块若引入新的长期默认配置，仍必须先扩展统一配置模型与配置文件，再由消费方读取。这样可以避免“因为脚本出界了，所以包内模块也重新开始各自写 `DEFAULT_*`”的回摆。

考虑过的替代方案：
- 同时放松包内治理规则：会直接削弱前一轮已经建立起来的配置一致性。
- 只在设计文档中描述边界，不在规范里固化：后续很容易再次出现理解偏差。

## 风险 / 权衡

- [边界解释不清，导致团队误以为仓库脚本不能复用统一配置] → 在规范中明确“非强制”而非“禁止”。
- [边界收紧后，部分已经迁移的脚本实现仍然保留配置读取] → 允许实现继续存在，但规范不再把它当必须行为。
- [后续新增模块借口自己是脚本而绕开治理] → 用“是否属于 `trpg_py` 包内长期运行配置”作为判断标准，而不是仅凭文件名。
- [旧 change 的方向与新 change 同时存在，评审时容易混淆] → 在 proposal 与 specs 中明确这次 change 是对统一配置适用范围的收敛和澄清。

## Migration Plan

1. 新增 `project-config` 规范，明确统一配置只覆盖 `trpg_py` 包内代码。
2. 为 `demo-runner` 与 `fetch-keys-tool` 添加增量规范，声明仓库脚本入口不再承担统一配置义务。
3. 后续实现时，仅保留包内模块必须消费统一配置的约束；脚本侧按需简化。
4. 若已有脚本实现仍读取统一配置，可继续保留作为实现选择，但不再由规范强制。

回滚策略：若团队后来决定重新扩大治理范围，可以在新的 change 中把具体脚本重新列入规范，而不是依赖当前 change 的模糊解释。
