## 为什么

前一轮“统一配置”把仓库根目录的 demo 与演示脚本也纳入了集中配置治理，但这些代码并不属于 `trpg_py` 包的运行时能力。继续把它们和包内配置绑定在一起，会扩大统一配置的边界，让库配置与仓库脚本示例产生不必要的耦合。

现在需要把“统一配置”的范围重新收紧到 `trpg_py` 包内代码，只统一真正属于包运行时的默认配置，并明确仓库根目录脚本可以保留自己的局部默认值或 CLI 入口。

## 变更内容

- 新增统一项目配置边界能力，明确统一配置只覆盖 `trpg_py` 包内长期运行配置与工具默认参数，不强制覆盖仓库根目录脚本或演示入口。
- 约束包内模块新增长期默认配置时，仍必须接入统一配置模型，禁止重新引入零散 `DEFAULT_*`、独立配置文件或分散环境变量解析。
- 调整 demo runner 相关需求，明确 `main.py` 作为仓库脚本不属于统一配置治理范围。
- 调整 `fetch_keys` 演示脚本相关需求，明确 `test_fetch_keys.py` 这类仓库脚本不需要接入统一配置，只需继续满足可运行演示的目标。
- **BREAKING**: 统一配置的治理范围从“整个仓库中的长期默认行为”收紧为“`trpg_py` 包内长期运行配置”；此前要求仓库脚本接入统一配置的方向不再成立。

## 功能 (Capabilities)

### 新增功能
- `project-config`: 定义统一配置的边界、唯一入口以及“仅覆盖 `trpg_py` 包内运行配置”的治理规则。

### 修改功能
- `demo-runner`: 明确 demo runner 的脚本入口不受统一配置强制约束。
- `fetch-keys-tool`: 明确 `fetch_keys` 的演示脚本不受统一配置强制约束，但工具本体仍遵守包内规范。

## 影响

- 受影响规范：新增 `specs/project-config/spec.md`，并增量修改 `specs/demo-runner/spec.md` 与 `specs/fetch-keys-tool/spec.md`。
- 受影响代码：后续实现将主要收敛 `trpg_py` 包内配置读取逻辑，不再要求 `main.py`、`test_fetch_keys.py` 等仓库脚本迁入统一配置。
- 受影响测试：需要验证统一配置边界只覆盖包内模块，并移除或调整脚本级统一配置假设。
- 受影响使用方式：开发者在新增包内运行配置时仍必须扩展统一配置模型；仓库脚本可以继续使用局部默认值、fixture 或 CLI 参数。
