## 上下文

`centralize-project-config` 已经建立了统一配置入口和 `config/config.toml`，并把 planner/search 两个最明显的运行配置入口迁移了过去。但当前项目还存在两类残余问题：

- 一部分长期默认值仍然停留在脚本或 demo 入口里，例如 `test_fetch_keys.py` 的内置默认 state、若干 smoke script 的默认输入。
- 项目还没有形成“什么值必须进入统一配置、什么值可以继续留在代码里”的治理边界，因此后续新增模块仍有可能重新引入新的模块级 `DEFAULT_*` 或脚本级默认参数。

这次变更的关键不只是继续迁移几个值，而是把统一配置从“已有一套 loader”提升为“全项目统一规则”。受影响的主要利益相关者包括：

- 维护运行时行为的开发者，需要知道新增默认配置应该落在哪里
- 使用 demo / smoke script 的开发者，需要稳定地覆写脚本默认输入而不改代码
- 后续新增 agent/tool 能力的实现者，需要遵守统一配置接入方式

## 目标 / 非目标

**目标：**
- 扩展统一配置模型，使剩余的项目级默认行为也通过同一 TOML 文件和同一配置入口管理。
- 为 demo runner 和 `fetch_keys` 演示脚本建立统一配置接入要求，避免脚本继续维护长期默认配置真相。
- 定义“项目级配置”的边界：凡是会影响跨运行默认行为的长期默认值，都必须进入统一配置；凡是只服务于单个固定 fixture 的静态数据，不强制迁移。
- 建立新增配置治理规则，禁止后续模块重新引入新的独立配置真相。
- 保留显式参数覆写与测试注入能力，但默认业务和脚本路径必须先经过统一配置入口。

**非目标：**
- 不要求把所有示例 state、任务文档或 demo fixture 数据全部序列化进 TOML。
- 不要求把协议常量、领域常量或纯实现细节常量（例如字段映射默认表、固定 task schema 名称）一律迁移到配置文件。
- 不在本次设计中引入多配置文件分层、环境配置合并或远程配置中心。
- 不在本次设计中重做 demo registry 的整体结构，只处理其中属于“长期默认行为”的部分。

## 决策

### 决策: 继续使用单一 `config/config.toml`，但扩展为项目级配置治理入口

统一配置文件仍然保持为 `config/config.toml`。本次不新增第二份 TOML，也不为 demo/script 单独拆配置文件，而是在现有 `ProjectConfig` 下继续扩展新的配置分区，例如 demo runner 与脚本默认输入相关配置。

考虑过的替代方案：
- 为 demo/script 单独再建一个配置文件：会立刻破坏“全项目仅此一份配置”的目标。
- 继续把脚本默认值留在代码里：实现简单，但会让统一配置只停留在 planner/search 层面。

### 决策: 明确区分“项目级配置”与“静态 fixture / 领域常量”

本次需要给出一条可执行边界：
- 若一个值是跨运行的长期默认行为，调用方可能希望在不改代码的前提下调整它，它就是项目级配置，必须进入统一配置。
- 若一个值只是固定 demo/测试夹具的一部分，或是协议/领域常量，它可以继续留在代码或 fixture 文件中。

这条边界能防止“统一配置”演变成把所有常量都搬进 TOML，也能避免后续再为真正的运行配置找借口留在代码里。

考虑过的替代方案：
- 要求所有常量都进入配置：过度设计，TOML 会膨胀为难以维护的数据仓库。
- 不定义边界，只按感觉迁移：短期快，但后续非常容易再次分叉。

### 决策: demo runner 与脚本默认行为通过统一配置声明，可保留 fixture 文件引用

对于 `main.py` 和 `test_fetch_keys.py` 这类入口，本次优先迁移的是“默认选择和默认输入来源”，而不是把整份示例数据都内嵌进 TOML。更稳妥的做法是：统一配置声明默认 demo 名、默认输入文件路径、默认前缀等，而大块 state/task fixture 仍保留在 JSON/代码 builder 中。

考虑过的替代方案：
- 把所有 demo state 全部写进 TOML：配置文件会迅速变成难维护的大对象。
- 什么都不迁移，只保留脚本参数：调用方仍然无法通过统一配置审计脚本默认行为。

### 决策: 新增项目配置必须先扩展 `trpg_py.config` 模型

未来若新增模块需要项目级默认配置，必须先扩展 `trpg_py.config` 的类型化模型与 `config/config.toml` 示例，再在消费侧读取该配置。禁止新增独立 `DEFAULT_*`、独立配置文件或零散环境变量集合作为长期真相。

考虑过的替代方案：
- 允许模块先本地加默认值，之后再统一：看似灵活，但实践上很容易永远停留在“之后再说”。

## 风险 / 权衡

- [配置边界定义过宽，导致 TOML 膨胀] → 用“长期默认行为 vs 静态 fixture”边界约束纳入范围。
- [配置边界定义过窄，遗漏真实运行配置] → 在规范中要求新增项目级默认值必须先扩展统一配置模型。
- [demo/script 改造会影响现有开发习惯] → 保留 CLI 参数显式覆写，默认值只迁移到统一配置，不剥夺手工传参能力。
- [现有示例脚本与 README 可能同时需要更新] → 在任务中显式加入脚本与文档同步，避免规范和实际入口脱节。

## Migration Plan

1. 为 `project-config` 新增项目级配置边界和新增配置治理要求。
2. 为 `demo-runner` 与 `fetch-keys-tool` 增量补充统一配置要求。
3. 扩展 `trpg_py.config` 模型与 `config/config.toml`，加入 demo/script 相关默认配置。
4. 迁移 `main.py` 与 `test_fetch_keys.py` 的长期默认行为到统一配置入口。
5. 为新增治理规则补测试与文档，确保后续模块按同一路径扩展配置。

回滚策略：若脚本级迁移影响过大，可以暂时保留显式 CLI 参数路径并让统一配置只提供默认值，但不回退“统一入口是唯一真相”的规范。
