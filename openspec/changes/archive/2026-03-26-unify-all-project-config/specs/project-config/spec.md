## 新增需求

### 需求:系统必须将项目级默认行为统一纳入单一配置模型
系统必须将运行配置、工具默认参数、demo 入口默认行为和脚本默认输入来源统一纳入同一份项目配置模型与同一份 TOML 文件，禁止继续让这些长期默认行为分散在脚本或模块常量中。

#### 场景:剩余脚本默认行为纳入统一配置
- **当** 系统需要为 demo runner 或 smoke script 提供默认参数
- **那么** 这些默认参数通过统一项目配置声明
- **那么** 调用方可以通过统一配置入口查看和覆写它们

### 需求:系统必须明确区分项目级配置与静态夹具数据
系统必须定义稳定边界来区分“项目级默认行为配置”和“静态 fixture / 领域常量”。凡是会影响跨运行默认行为的长期默认值必须进入统一配置；只属于固定示例数据、协议常量或领域常量的值禁止被强制迁移为配置。

#### 场景:长期默认行为被识别为项目配置
- **当** 某个默认值会影响系统跨运行的默认行为，且调用方可能希望在不改代码时调整它
- **那么** 系统将其视为项目级配置
- **那么** 该值必须通过统一配置模型声明

#### 场景:固定 fixture 数据不被误判为项目配置
- **当** 某个值只属于单个 demo、单个测试夹具或协议/领域常量
- **那么** 系统允许该值继续留在 fixture 文件或代码中
- **那么** 统一配置文件不必承载该静态数据本体

### 需求:新增项目级配置必须先扩展统一配置入口
系统必须要求后续任何模块在引入新的项目级默认配置前，先扩展统一配置模型和统一配置文件示例，禁止新增独立 `DEFAULT_*`、独立配置文件或零散环境变量入口作为长期配置真相。

#### 场景:新增模块引入项目级默认值
- **当** 某个模块需要新增项目级默认配置
- **那么** 开发者先扩展统一配置模型与统一配置文件
- **那么** 该模块通过统一配置入口消费新字段
