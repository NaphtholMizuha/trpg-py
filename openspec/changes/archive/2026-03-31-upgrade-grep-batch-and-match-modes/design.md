## 上下文

当前 `grep` 只围绕 `list_state_keys(state)` 返回的 canonical 叶子路径工作，核心输出是带分数的路径候选。这个设计适合“先发现路径、再 read 值”的流程，但不适合新的 planner 两节点架构。新的 Intent 节点更需要的是：基于多个关键词组直接筛出一批可读事实行，再把这些行压缩为半结构化 `TaskBrief`，而不是先得到一批路径候选再额外拼接上下文。

现有实现里已经有几项可复用资产：
- 关键词归一化与同义词扩展
- 稳定的 `ok` / `no_match` / `error` 结构化语义
- runtime guard 和 loguru 可观测性

这次设计的重点不是引入一个全新检索系统，而是在保留上述稳定边界的前提下，把匹配对象和输入模型升级为更接近“文本 grep”的行为。

## 目标 / 非目标

**目标：**
- 让 `grep` 支持一次调用提交多组关键词输入。
- 让每组关键词支持 `and` 与 `or` 的布尔组合，而不是只能二选一。
- 将 state 展平成 `a.b.c = data` 文本行后再执行匹配。
- 返回所有命中的扁平化行，而不是只返回相关性排序后的少量路径候选。
- 保持 `grep` 仍然是只读工具，并继续提供稳定日志和错误语义。

**非目标：**
- 不把 `grep` 改造成写状态工具或值确认工具。
- 不在本次变更中重做 `search`、`read` 或 planner runtime guard 的整体协议。
- 不引入新的外部索引或全文检索依赖。
- 不要求本次变更继续保留旧的“路径打分排序优先”返回形态作为长期主语义。

## 决策

### 决策 1：将匹配对象改为扁平化状态行，而不是仅匹配叶子路径名

`grep` 将先把 state 展平成一组文本行，形如 `actors.aldera.hp = 44`、`actors.malik.spell_slots.1 = 4`，然后在这些行上执行关键词匹配。返回结果中的核心对象也改为这些文本行。

这样做的原因是，planner 的 Intent 节点需要直接消费“路径 + 当前值”的可读事实片段；如果仍只返回路径，调用方还要立刻补一次 `read` 才能得到有意义上下文。把匹配对象上移到扁平化行，可以让 `grep` 更像低成本事实筛选器。

考虑过的替代方案：
- 保持只匹配路径，再由调用方手工把命中路径做 `read`：保留了旧的分层，但仍然让上游多一次往返，无法满足用户期望的“返回 grep 到的所有行”。
- 直接返回任意格式的字典对象：不如 `a.b.c = data` 文本行稳定，也不利于日志和人工阅读。

### 决策 2：输入模型升级为“批量请求 + 每组布尔条件”

`grep` 新输入将支持一次传入多组关键词请求。每组请求至少包含：
- 一个可嵌套的布尔条件树
- 叶子节点使用 `terms`
- 中间节点使用 `operator`，取值为 `and` 或 `or`

可选地仍允许单组简写输入，但工具内部统一归一为请求列表。

这样做的原因是，planner 需要同时尝试几组相近的实体/字段组合，例如“malik + slot”和“aldera + hp”，如果每次都单独调用工具，会放大 tool budget 消耗，也增加 runtime guard 的重复主题问题。

考虑过的替代方案：
- 只在顶层增加一个全局 `match_mode`：无法表达同一次调用里不同关键词组拥有不同逻辑。
- 每组请求只允许一个 `match_mode`：无法表达 `(malik AND slot) OR spell_slots` 这类真实筛选条件。
- 要求调用方自己多次调用 `grep`：会让批处理能力落空。

### 决策 3：单组请求支持布尔表达式组合，批量组之间按并集收集结果

每组请求内部允许嵌套布尔表达式，例如：
- `(malik AND slot) OR spell_slots`
- `aldera AND (hp OR health)`

表达式求值规则是：
- `and` 表示子条件必须全部为真
- `or` 表示任一子条件为真即可
- 叶子条件使用归一化关键词集合在单条扁平化行上匹配

如果一次调用提供多组请求，则最终结果取所有组命中的并集，并在每条结果中保留命中了哪些组或哪些关键词的解释信息。

这样做的原因是，调用方一次调用多个请求通常是在做“批量查找多个主题”，而不是要求所有主题必须同时落在同一行上。按并集合并更符合批处理直觉，也更容易驱动上游 planner。

考虑过的替代方案：
- 让多组之间也做 `and`：结果会过于严格，很多状态行天然只覆盖一个主题。
- 让多组之间保留完全独立结果列表：调用方能区分来源，但会让响应结构更复杂；本次优先简化统一返回。

### 决策 4：返回“所有命中行”，并允许限制数量但不再默认做路径候选排序语义

`grep` 应返回所有命中的扁平化行；如有上限参数，也只是用于截断命中数量，而不是强调“最佳路径候选”。返回对象需要包含：
- `line`
- 可选的 `path`
- 命中的关键词或请求摘要
- 匹配原因

这样做的原因是，用户明确要求“返回 grep 到的所有行”。旧的排序思路可以作为稳定输出顺序的辅助手段，但不应再定义为“候选发现器”的核心价值。

考虑过的替代方案：
- 继续只返回 top-N 候选：不符合本次目标。
- 不保留任何元数据只返回字符串数组：会削弱可解释性和调用方可操作性。

## 风险 / 权衡

- [返回扁平化行会弱化 `grep` 与 `read` 的边界] → 在规范中明确 `grep` 返回的是当前快照中的文本行，调用方若需要机器可消费的精确值或路径校验，仍可继续使用 `read`。
- [批量请求会让返回量变大] → 保留数量上限，并要求结果结构可解释地记录命中原因，避免调用方只能处理超大裸文本数组。
- [旧调用方可能依赖 `matches[].path` 排序语义] → 在变更中明确这是 `grep-tool` 的行为升级，并为返回项保留 `path` 或等价字段，给调用方迁移空间。
- [runtime guard 目前按单一 theme 缓存，批量输入会改变主题归一逻辑] → 在实现任务中显式包含 guard theme 归一化更新，避免错误短路不同批次请求。

## Migration Plan

1. 先更新 `grep-tool` 规范，明确扁平化行、批量输入和可组合布尔条件语义。
2. 重写 `grep` 输入/输出 schema 与匹配核心逻辑，新增 state flatten 步骤。
3. 调整 runtime guard、日志和 smoke 输出，使新输入语义可观测。
4. 更新单元测试和 smoke，用批量输入、布尔组合、无命中三类场景覆盖新行为。

## Open Questions

- 是否需要在返回体中按请求组分桶保留结果来源，还是只保留统一命中列表加来源标记即可？本设计默认后者。
- 顶层是否继续保留旧的 `query` 简写输入以兼容旧调用方，还是直接收敛到新的请求列表协议？本设计倾向保留一个轻量兼容层，但以请求列表为规范真相。
