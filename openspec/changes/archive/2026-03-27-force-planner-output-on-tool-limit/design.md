## 上下文

当前 planner 通过 `ToolCallLimitMiddleware(..., exit_behavior="error")` 在运行期限制单轮工具调用次数。一旦 LangChain 抛出 `ToolCallLimitExceededError`，`planner.py` 立即捕获并返回 `needs_human/tool_budget_exhausted`。这条路径虽然能防止无限打转，但它把“停止继续取证”和“无法输出结果”绑定到了一起，导致已经拿到的路径、状态值、规则证据和候选文档无法被最后一次整理成可消费的 `PlannerResult`。

这次变更只调整预算触发后的收尾语义，不改变 planner 的三态输出契约，也不放宽 `ready` 所需的结构与语义校验。核心约束是：达到工具上限后必须彻底禁止新的工具调用，但仍要给模型一次基于现有上下文的最终结构化输出机会。

## 目标 / 非目标

**目标：**
- 让 planner 在工具预算耗尽时进入一次无工具的最终收敛阶段，而不是立刻结束整个规划。
- 保证最终收敛阶段仍输出标准 `PlannerResult`，并继续经过现有 schema 与语义校验。
- 保留预算耗尽这一事实的日志和调试可观察性，方便区分“护栏触发但成功收尾”和“护栏触发且仍未收敛”。
- 让 smoke 和单元测试覆盖“预算耗尽后仍可正常 ready/needs_human/blocked”的行为。

**非目标：**
- 不取消运行期工具预算限制。
- 不引入新的 planner 状态类型。
- 不让最终收敛阶段重新开启工具、HITL 或额外的多轮探索。

## 决策

### 决策 1：预算耗尽后追加一次独立的无工具终局收敛
- 选择：当主 planner agent 因 `ToolCallLimitExceededError` 中断时，runtime 立即启动一次独立的“forced finalize”调用。该调用复用同一结构化输出 schema，但不挂载任何工具，只允许模型基于已存在的对话上下文与异常说明输出最终结果。
- 理由：当前异常是在 agent runtime 内部抛出，无法指望同一次有工具调用自动“自然收尾”；最稳妥的方式是显式切到一个零工具收尾通道。
- 替代方案：
  - 将 middleware 改成非异常退出并期待 agent 自动返回结果。缺点是可控性和可测试性较弱，而且不同 runtime 版本的行为不稳定。
  - 预算耗尽后直接把已有半成品文档硬塞进 `ready`。缺点是会绕过现有校验闭环，风险过高。

### 决策 2：终局收敛阶段必须显式携带“禁止再调用工具”的约束
- 选择：无工具终局收敛输入中必须明确声明“工具预算已耗尽，不允许再调用工具，只能基于已知证据输出最终结果”；同时运行时也通过空工具集保证模型即使尝试也无法再次取证。
- 理由：单靠 prompt 约束不够稳；需要 prompt 和 runtime 双重保证“这是收尾，不是第二次探索”。
- 替代方案：
  - 仅在 prompt 中提醒不要再用工具。缺点是模型仍可能尝试，失败路径不稳定。
  - 让终局收敛继续带工具但把预算设为 0。缺点是仍然耦合到工具中间件异常语义。

### 决策 3：只有终局收敛仍失败时，才保留 `tool_budget_exhausted` 作为最终原因
- 选择：如果无工具终局收敛成功产出合法 `PlannerResult`，最终结果保留真实的 `status` 和 `reason`；预算耗尽作为 debug/log 事件记录，而不是覆盖最终业务语义。只有当终局收敛本身无法得到合法结果时，才返回 `needs_human/tool_budget_exhausted` 或对应系统错误。
- 理由：调用方最关心的是“最终能不能执行/需不需要人类/是否阻塞”，而不是中途是否触发过护栏。护栏应是调试维度，不应无条件吞掉最终结果。
- 替代方案：
  - 任何命中过预算都强制返回 `needs_human`。缺点是继续保留当前问题。
  - 任何命中过预算都强制返回 `blocked`。缺点是把正常护栏误报为系统故障。

### 决策 4：日志与测试需要显式区分“护栏触发”和“最终失败”
- 选择：新增强制收敛开始/结束日志事件，并在 debug 负载中保留预算耗尽事件。测试要分别覆盖“护栏触发但 ready”“护栏触发后 needs_human”“终局收敛自身失败”三类结果。
- 理由：否则从日志上仍然很难判断 planner 是真的失败了，还是只是命中过预算但成功收尾。
- 替代方案：
  - 仅复用现有 `tool_budget_exhausted` 事件。缺点是无法看出是否执行过 forced finalize，以及 forced finalize 的结果。

## 风险 / 权衡

- [终局收敛缺少工具后可能更容易输出保守结果] → 这是有意权衡；预算耗尽后必须优先保证收尾而不是继续探索。
- [新增一次无工具调用会增加少量延迟] → 该调用只发生在异常护栏场景，而且可以换来更高的成功收尾率。
- [最终结果不再把 `tool_budget_exhausted` 作为顶层 reason，可能让部分调用方忽略护栏触发] → 通过 debug/log 保留完整事件，并在需要时把该信息透出到 smoke 摘要。
- [如果终局收敛拿不到足够上下文，可能仍然失败] → 明确把已有验证反馈、工具预算异常说明和当前会话上下文注入终局收敛输入；失败时再回退到现有 `needs_human` 语义。

## Migration Plan

1. 为 planner 增加无工具 forced-finalize agent 或等价的零工具结构化输出路径。
2. 调整 `ToolCallLimitExceededError` 分支，改为记录护栏事件后触发 forced finalize，而不是直接构造最终 `PlannerResult`。
3. 更新日志与 debug 负载，区分预算触发、forced finalize 开始/结束、forced finalize 失败。
4. 为 planner 单测和 smoke 增加预算耗尽后的结果断言，覆盖成功收尾与失败回退两条路径。

## Open Questions

- forced finalize 是否需要复用原始 thread_id，还是以独立无状态调用实现会更稳妥？
- smoke 的默认人类可读输出是否要在成功收尾时额外提示“本次结果经过预算耗尽后的强制收敛”？
