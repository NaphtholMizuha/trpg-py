## 上下文

当前项目的统一配置把 planner 和 search 的 API key 直接放在 `config/config.toml` 中。这虽然方便本地测试，但会让敏感值进入工作区文件，增加泄露风险，也不利于把示例配置提交到仓库。

现有实现里，planner 和 search 都通过 `trpg_py.config` 读取统一配置，因此这是一个适合在配置层统一收口的变更。只要把配置模型从 `api_key` 改成 `api_key_env`，并在加载配置时解析环境变量，就可以同时覆盖 planner factory、search 默认构造和 smoke 脚本等所有配置消费路径。

## 目标 / 非目标

**目标：**
- 让统一配置文件只保存环境变量名，不再保存 API key 值。
- 让配置加载层统一解析 `api_key_env`，并在缺失环境变量时给出明确错误。
- 让 planner 与 search 的默认配置消费逻辑继续通过统一配置工作，但改为消费解析后的密钥。
- 让示例配置、README 和测试样例同步更新为 `api_key_env` 模式。

**非目标：**
- 不在这次变更中引入新的 secrets manager 或外部凭证服务。
- 不改变调用方显式传入 `api_key=` 参数时的优先级语义。
- 不要求仓库脚本必须改成额外的环境变量加载框架（如 dotenv）。

## 决策

### 决策 1：统一配置使用 `api_key_env`，而不是 `${ENV}` 占位语法
- 选择：在配置模型中新增并使用 `api_key_env` 字段，配置文件直接写环境变量名，例如 `LINGYA_API_KEY`。
- 原因：显式字段更容易做 schema 校验，也更容易给出“缺少哪个环境变量”的清晰错误。
- 备选方案：保留 `api_key`，支持 `${LINGYA_API_KEY}` 这类占位语法。
- 不选原因：这会把普通字符串和占位规则混在一起，解析逻辑更隐式，错误提示也更模糊。

### 决策 2：环境变量解析放在 `trpg_py.config` 加载层统一完成
- 选择：`load_project_config()` 返回的配置对象已经是“密钥已解析完成”的最终值，planner/search 无需自己再解析环境变量。
- 原因：这样配置消费方可以继续保持简单，也避免多个模块重复实现相同的密钥解析逻辑。
- 备选方案：planner 和 search 各自读取 `api_key_env` 再解析。
- 不选原因：会让同一规则散落在多个模块中，增加不一致风险。

### 决策 3：缺失环境变量视为配置错误，而不是静默降级为空字符串
- 选择：如果 `api_key_env` 指向的环境变量不存在或为空，配置加载阶段应返回明确错误。
- 原因：认证信息缺失属于硬错误，越早失败越容易定位。
- 备选方案：把空值传到运行时，等网络调用失败再报错。
- 不选原因：这会把配置问题延迟成运行时故障，排查成本更高。

## 风险 / 权衡

- [现有本地配置文件从 `api_key` 切到 `api_key_env` 后需要同步设置环境变量] → README 和示例配置明确迁移步骤，并在错误信息中指出缺失的环境变量名。
- [测试样例需要整体调整] → 统一更新 `tests/config_helpers.py` 和相关断言，避免新旧配置格式混用。
- [调用方显式传 `api_key` 时可能与配置模型并存] → 保持显式参数优先级不变，只把统一配置默认值迁移到 `api_key_env`。

## Migration Plan

1. 将 `trpg_py.config` 的 planner/search 配置模型从 `api_key` 迁移为 `api_key_env`，并在加载时解析环境变量。
2. 更新 `config/config.toml` 示例、README 和测试样例，移除直接保存密钥的方式。
3. 调整 planner/search 默认构造与相关测试，确保通过解析后的密钥继续运行。
4. 运行现有测试，确认配置迁移未破坏显式参数覆写和默认构造逻辑。
