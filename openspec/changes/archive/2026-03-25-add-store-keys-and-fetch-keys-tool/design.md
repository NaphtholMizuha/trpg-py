## 上下文

当前项目的 `state-store` 规范和实现只提供点路径的读写能力，不提供可枚举路径接口。与此同时，planner agent 已引入 `search` 工具用于规则检索，但仍缺少“查看当前 state 可引用路径”的能力，导致 LLM 在生成 `TaskDocument` 时容易猜错路径。

本次变更横跨两个层次：

- `trpg_py.store`：新增标准化 key 枚举能力（全量 + 按范围）
- `trpg_py.agent.tools`：新增 `fetch_keys` 工具包装，提供给 agent 直接调用

因此需要明确 store 与 agent 的职责边界，避免把路径发现逻辑散落在多个调用层。

## 目标 / 非目标

**目标：**
- 为 `state-store` 增加 `keys` 公共接口，并纳入统一导出。
- 让 `keys` 同时支持全量枚举与按范围枚举（至少支持 `prefix` 过滤）。
- 在 `trpg_py.agent.tools` 提供 `fetch_keys` 工具包装，并与 `store.keys` 语义保持一致。
- 规定 `fetch_keys` 的结构化返回语义，明确区分命中、无命中和错误。
- 提供一个可直接运行的测试脚本，让开发者无需阅读测试代码即可观察新能力行为。

**非目标：**
- 不在本次变更中实现 `search` 以外的更多规则工具能力。
- 不在本次变更中扩展 `TaskDocument` DSL。
- 不在本次变更中实现复杂查询语言（例如布尔表达式过滤、排序 DSL）。

## 决策

### 决策: key 枚举能力落在 store 层，而不是仅在 agent 层拼装

`fetch_keys` 的核心依赖是“遍历 state 并产出路径”。该能力属于状态访问范畴，应在 `store` 层成为标准接口，agent 工具仅做包装与输出适配。

考虑过的替代方案：
- 仅在 agent 工具层自行遍历 state：实现快，但会绕过 `store` 能力边界，后续复用和测试更差。
- 在 engine 层提供枚举能力：职责不匹配，engine 应消费 store 而非反向定义状态访问语义。

### 决策: `keys` 同时支持全量与按范围，按范围以 prefix 为第一优先

第一版 `keys` 需要覆盖两种典型调用：
- 全量枚举：供初始化观察状态表面
- 按范围枚举：供 planner 针对实体/子树做精确探索

范围控制第一版使用 `prefix` 即可满足主要需求，同时保留后续增加 `max_depth`、`limit/cursor` 的演进空间。

考虑过的替代方案：
- 只支持全量：token 成本高，规模上来后不可用。
- 一开始引入复杂过滤表达式：灵活但成本高，不适合当前阶段。

### 决策: `fetch_keys` 返回结构化 payload，与 `search` 风格对齐

`fetch_keys` 需要被 planner 可靠消费，应返回结构化结果（如 `status/items/error`），而不是自由文本。这样 planner 可以稳定判断“无命中”和“错误”并决定下一步行为。

考虑过的替代方案：
- 返回纯文本 key 列表：对人可读，但对 agent 分支判断不稳定。
- 直接返回复杂统计与推断字段：超出本次范围，且会提高耦合度。

### 决策: `keys` 默认返回可引用路径集合，避免暴露多余语义

`keys` 的目标是提供路径可见性，不承担值读取或语义解释。调用方若要读取值，应继续使用 `read/reads`；这可保持接口职责单一，并减少不必要的敏感数据暴露。

考虑过的替代方案：
- 在 `keys` 中附带值预览：有帮助，但会抬高接口复杂度和 token 成本。
- 同时返回路径和类型树：可扩展但本次非必需。

## 风险 / 权衡

- [大状态下全量枚举开销高] → 通过 `prefix` 优先收敛调用范围，并在契约中保留分页扩展空间。
- [store 与 agent 对返回语义不一致] → `fetch_keys` 明确复用 `store.keys` 并做薄包装，避免重复定义。
- [路径格式不一致导致 planner 混淆] → 统一使用与 `read/write` 相同的点路径格式。

## Migration Plan

1. 扩展 `store` 规范和实现，新增 `keys` 接口并加入导出。
2. 新增 `agent.tools.fetch_keys`，调用 `store.keys` 并输出结构化 payload。
3. 补充单元测试覆盖全量枚举、按范围枚举、空结果与错误语义。
4. 增加 `test_fetch_keys.py` 等可运行测试脚本并给出演示输出。
5. 在 agent 使用说明中补充 `fetch_keys` 职责边界与调用示例。

## Open Questions

- 第一版是否需要同步引入 `limit/cursor`，还是先只落 `prefix` 过滤。
- `keys` 默认应返回全部路径还是叶子路径；两者各有 token 与可用性权衡。
