## 修改需求

### 需求: lint 工具必须显式区分合法、非法和错误
系统必须通过稳定的结构化语义区分候选文档合法、候选文档非法和工具执行错误，禁止把字段错误、语义错误和系统故障折叠成同一种模糊字符串结果。

#### 场景:lint 返回合法结果
- **当** 调用方向 `lint` 提交一个满足 Schema 与执行器语义约束的候选 `TaskDocument`
- **那么** `lint` 返回合法语义
- **那么** 返回体可以明确表明该候选文档通过校验

#### 场景:lint 返回非法结果
- **当** 调用方向 `lint` 提交一个缺少步骤字段或违反执行器语义的候选 `TaskDocument`
- **那么** `lint` 返回非法语义
- **那么** 返回体必须包含可供调用方定位问题的结构化错误信息
- **那么** 在同一轮可独立发现多个错误时，返回体必须尽量汇总这些错误，而不是只停在第一个语义错误

#### 场景:lint 返回工具错误
- **当** `lint` 在处理过程中发生非候选文档本身导致的异常
- **那么** `lint` 返回明确错误语义
- **那么** 调用方可以区分这是工具故障而不是文档非法

### 需求: lint 返回结果必须可直接驱动 planner 修复分支
系统必须保证 `lint` 返回结果足够结构化，使 planner 可以根据字段定位和错误摘要修复候选文档，而不是只能消费一段不可分解的大文本报错。

#### 场景:planner 根据 lint 错误修复步骤字段
- **当** `lint` 发现某个步骤缺少 `id`、`type`、`kind` 或 `args`
- **那么** 返回结果中必须能定位到对应字段路径
- **那么** planner 可以据此补齐候选文档后再次校验

#### 场景:planner 根据 lint 错误修复多处独立 DSL 问题
- **当** 候选 `TaskDocument` 同时包含多个互不依赖的 DSL 错误，例如不支持的 step type、缺失的必需参数和非法的 tags
- **那么** `lint` 必须尽量在一次返回中暴露这些独立问题
- **那么** 调用方不需要通过多轮“修一个错再看到下一个错”的方式才能发现全部明显问题

#### 场景:lint 拦截 runtime-sensitive DSL 形状错误
- **当** 候选 `TaskDocument` 使用了当前 runtime 不支持但结构上看似合理的形状，例如错误的 `select.area.shape` 嵌套对象或错误层级的参数字段
- **那么** `lint` 必须在执行前把该候选判为 `invalid`
- **那么** 返回体必须指出对应步骤路径和形状错误，而不是把问题留到 engine runtime 才暴露
