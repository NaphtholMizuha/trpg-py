## 上下文

当前 planner 已经具备真实工具取证、结构化三态输出，以及最终的 Schema + 执行器双层校验闭环，但它对 `TaskDocument` DSL 的掌握主要依赖简短 prompt 和失败后的被动修复反馈。这导致 planner 容易生成“外层结构正确、内层步骤字段不合法”的候选文档，并在最终校验时才暴露问题。另一方面，现有工具集聚焦规则证据与状态路径发现，缺少一个专门用于任务文档自检的只读工具。

这次变更会同时触及 `config/prompts/`、`trpg_py.agent.planner` 与 `trpg_py.agent.tools`。设计目标不是让 lint 取代最终守门，而是让 prompt 负责“教会 DSL”，让 `lint` 工具负责“主动发现偏差”，再由现有后端校验承担最后兜底。

## 目标 / 非目标

**目标：**
- 让 planner prompt 显式暴露合法 `TaskDocument` 的最小骨架、步骤类型约束、引用约定和代表性示例。
- 提供名为 `lint` 的只读工具，允许 planner 在准备返回 `ready` 前主动校验候选文档。
- 复用现有 `TaskDocumentSchema` 与执行器校验逻辑，避免出现第二套不一致的合法性定义。
- 让 lint 返回结构化错误信息，便于 planner 基于字段路径和错误摘要进行修复。

**非目标：**
- 不让 `lint` 执行任务、写入 state 或替代执行器。
- 不引入新的值读取工具，也不改变现有 `ready/needs_human/blocked` 三态契约。
- 不把 planner 变成无限试错循环；最终仍受规划轮数、工具预算和现有兜底校验约束。

## 决策

### 决策 1：prompt 增强与 lint 工具同时推进，而不是只做其中一项

prompt 增强解决“模型不知道合法 DSL 长什么样”的问题，lint 工具解决“模型在生成过程中无法主动确认自己是否写对”的问题。两者职责不同但互补，如果只做其中一项，planner 要么继续盲猜 DSL，要么只能把 lint 当作碰运气的试错墙。

考虑过的替代方案：
- 只增强 prompt：可以降低部分错误，但难以稳定吸收复杂的执行器语义约束。
- 只增加 lint 工具：模型缺少 DSL 先验，会频繁产生低质量候选并浪费工具预算。

### 决策 2：`lint` 复用现有 Schema 与执行器校验链路，而不是维护独立规则集

`lint` 将基于现有 `TaskDocumentSchema` 与 `validate_task_document(...)` 执行校验，确保 planner 自检结果与最终守门结果保持一致。这样可以避免出现“lint 说合法、执行器说非法”或相反的双重真相。

考虑过的替代方案：
- 仅复用 Pydantic Schema：能发现基础结构问题，但看不到步骤级语义错误。
- 单独实现轻量 lint 规则：实现简单，但长期会与执行器校验逐步漂移。

### 决策 3：`lint` 采用只读、结构化返回语义

`lint` 输入为候选 `task_document`，输出必须区分至少三类结果：合法、非法、工具错误。非法结果需要携带结构化错误列表，至少包含可定位字段路径和错误摘要，便于 planner 做针对性修复。该工具不得执行任务、不得写入 state、不得触发副作用。

考虑过的替代方案：
- 直接返回原始异常字符串：实现快，但模型更难精准定位错误。
- 让 lint 试跑任务：会把校验与执行边界混淆，并引入副作用风险。

### 决策 4：planner 将 `lint` 作为收口工具，而不是替代现有兜底回路

planner 的推荐策略是：先使用 `search` 和 `fetch_keys` 完成规则与路径取证，再生成候选 `TaskDocument`，然后在准备返回 `ready` 前使用 `lint` 做自检。若 planner 未调用 lint 或 lint 后仍存在遗漏，现有最终校验与 repair feedback 仍然保留，作为最后防线。

考虑过的替代方案：
- 强制每轮都调用 lint：会显著增加工具预算消耗，并鼓励机械式试错。
- 用 lint 替换最终后端校验：会削弱当前稳定的守门机制。

## 风险 / 权衡

- [prompt 变长导致模型注意力分散] → 采用“最小骨架 + 高价值约束 + 1~2 个 canonical examples”的紧凑写法，而不是堆完整 schema dump。
- [lint 返回信息过少，模型仍难修复] → 要求 lint 输出结构化错误列表，而不是只暴露异常大字符串。
- [planner 过度依赖 lint 反复试错] → 将 lint 定位为候选文档收口工具，并继续受工具预算和规划轮数控制。
- [校验链路出现双重真相] → 复用同一套 `TaskDocumentSchema` 与执行器校验逻辑，避免维护第二套规则。

## 迁移计划

1. 先增强 planner prompt 模板，使 DSL 教学在不接入新工具时也能立即生效。
2. 再新增 `lint` 工具及其测试，验证其输出与现有后端校验结果一致。
3. 将 `lint` 接入 planner 默认工具集与提示词策略，并补足 planner/smoke 测试。
4. 保留现有最终校验回路作为兜底，无需迁移调用方接口。

## 开放问题

- lint 的错误列表是否需要标准化错误码，还是先提供 `path + message` 即可。
- planner 是否应在 prompt 中强约束“返回 ready 前优先调用 lint”，还是采用较软的策略提示以平衡工具预算。
