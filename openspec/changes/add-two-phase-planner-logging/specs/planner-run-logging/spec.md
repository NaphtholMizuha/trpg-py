## 新增需求

### 需求:planner 运行必须自动生成按次日志文件
系统必须为每次 planner 运行自动生成一份独立的详细日志文件，并将其写入项目内约定的 `logs/` 目录层级中。系统禁止继续只依赖终端瞬时日志作为 planner 运行诊断的唯一载体。

#### 场景:一次 planner 运行生成独立日志文件
- **当** 调用方发起一次新的 planner 规划请求
- **那么** 系统必须创建与本次运行对应的 planner 日志文件
- **那么** 该日志文件路径必须位于项目内约定的 `logs/planner/` 目录层级下
- **那么** 该日志文件必须能够与本次运行稳定对应，而不是与其他运行混写在同一个匿名日志流中

### 需求:planner 文件日志必须覆盖基础运行诊断信息
系统必须在 planner 文件日志中记录足以解释运行边界的基础诊断信息，包括 run 标识、线程或恢复标识、instruction 摘要、轮次边界、输入模式和最终 planner 状态。系统禁止让 blocked 排障仍然只能依赖工具层零散日志拼接推断。

#### 场景:日志记录 run 元数据与轮次边界
- **当** planner 开始一次包含一个或多个 planning round 的运行
- **那么** 文件日志中必须包含本次运行的唯一标识或等价标记
- **那么** 文件日志中必须包含每轮开始或结束的边界信息
- **那么** 文件日志中必须包含最终返回的 `ready`、`needs_human` 或 `blocked` 状态摘要

### 需求:planner 在结构化输出失败时必须记录原始异常上下文
系统必须在结构化输出解析失败导致 `blocked` 时，把底层结构化输出异常中的关键上下文写入 planner 文件日志，包括 schema 或 tool 名称、底层异常来源，以及导致解析失败的 AI 响应摘要。系统禁止继续只把 `str(exc)` 作为唯一 blocked 诊断信息。

#### 场景:结构化输出校验失败被写入日志
- **当** planner 因结构化输出解析失败而进入 `status=blocked`
- **那么** 文件日志中必须包含导致失败的 schema 或 tool 名称
- **那么** 文件日志中必须包含底层异常来源或解析错误摘要
- **那么** 文件日志中必须包含 AI 响应的可读摘要，例如 content、tool_calls 或等价元数据

### 需求:planner 文件日志必须扩展到轮次级修复与响应快照
系统必须在基础运行诊断之外，支持记录轮次级 prompt/response 摘要、validation feedback、结构化响应快照和修复轨迹，以便开发者复盘 planner 如何从初稿进入修复或 blocked。系统禁止把这类扩展快照永久排除在文件日志能力之外。

#### 场景:修复轮写入 validation feedback 与响应快照
- **当** planner 因 schema 或语义校验失败进入修复轮
- **那么** 文件日志中必须包含该轮对应的 validation feedback 或等价修复提示摘要
- **那么** 文件日志中必须包含该轮结构化响应快照或等价可读摘要
- **那么** 开发者可以通过同一日志文件复盘该次修复轨迹
