## 修改需求

### 需求:store 逻辑必须组织为独立包
系统必须将状态存储相关代码组织到独立的 `src/augury/store/` 包中，而不是继续依赖单一的 `augury/store.py` 文件承载全部实现。

#### 场景:store 包作为公开入口
- **当** 调用方导入 `augury.store`
- **那么** 系统必须从 `src/augury/store/__init__.py` 提供稳定的公开接口入口

#### 场景:store 内部代码按职责分布
- **当** 维护者查看状态存储实现
- **那么** 与 store 相关的实现、导出和兼容辅助代码必须位于 `src/augury/store/` 包内，而不是继续分散在单文件实现中

### 需求:公开 store 接口语义保持兼容
系统在调整文件结构后，必须继续提供 `read`、`reads`、`write`、`writes`、`mod`、`mods` 六个公开接口，并保持其现有行为与调用语义兼容。

#### 场景:调用方继续使用现有 store 接口
- **当** 调用方通过 `augury.store` 访问六个公开接口
- **那么** 它们必须继续工作且不要求调用方改变参数协议

### 需求:兼容辅助语义必须收敛到 store 包内
系统在将 store 重构为包后，必须将兼容辅助函数收敛到 `augury.store.compat` 等 store 包内模块，而不是继续保留额外的 `augury.engine.state` 这类薄转发入口。已移除的包根目录 facade 也不得重新引入。

#### 场景:兼容辅助函数通过 store 包提供
- **当** 调用方需要访问状态路径兼容辅助函数
- **那么** 这些函数必须由 `augury.store.compat` 提供
- **那么** 它们必须继续复用 store 包实现并保持现有错误语义

#### 场景:store 包化不会恢复已移除的根目录 facade
- **当** 维护者调整 store 包内部结构
- **那么** 系统不得为了兼容重新引入 `augury.state` 这类包根目录转发模块
- **那么** 根目录 API 约束仍由 `root-api-layout` 统一约束
