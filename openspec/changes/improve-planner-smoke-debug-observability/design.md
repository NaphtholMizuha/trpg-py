## 上下文

当前 planner 已具备三态输出、工具编排和“结构校验 + 执行器校验”的修复闭环，但真实排查体验仍然较差：

- `smoke/test_planner.py` 默认只展示最终结果摘要，无法看见中间规划过程。
- `planner.plan()` 会把多轮修复中的结构化输出错误和执行器校验错误压缩为最终 `needs_human` 或 `blocked`，缺少可直接诊断的上下文。
- 当 planner 生成了非法 `TaskDocument` 且修复失败时，当前默认文案容易被理解为“用户信息不足”，而不是“系统内部未能产出合法文档”。

这次变更主要面向开发调试，不是要重写 planner 主流程，而是要为现有链路补充一条可观察、可解释的调试视图，并让 smoke 脚本能把这条视图稳定展示出来。

## 目标 / 非目标

**目标：**
- 为 planner 增加显式的 debug 可观测能力，覆盖规划轮次、工具调用、结构化输出和校验失败原因。
- 让 `smoke/test_planner.py` 能以人类可读和 JSON 形式展示调试轨迹，帮助开发者快速定位故障层级。
- 在失败时区分“真实需要澄清”和“系统未产出合法 TaskDocument”两类原因，避免误导调用方。
- 让调试输出保持可测试、可控且默认不会污染普通调用路径。

**非目标：**
- 不在本次设计中引入新的规则工具或值读取工具（如 `reads`）。
- 不在本次设计中改变 `ready/needs_human/blocked` 三态契约本身。
- 不在本次设计中实现完整的 LangGraph 可视化或外部 tracing 平台接入。
- 不在本次设计中重写 planner 提示词策略或核心规划算法。

## 决策

### 决策: 用显式 debug 轨迹承载可观测信息，而不是修改默认摘要输出

planner 将增加一份仅在调试模式下返回的结构化 debug 轨迹，承载本次规划的关键中间信息。默认调用继续返回简洁结果；只有调用方显式开启 debug 时，结果中才附带这些调试字段。

这能避免普通调用路径被大量内部细节污染，同时给 smoke 脚本和测试提供稳定的数据来源。

考虑过的替代方案：
- 始终在 `PlannerResult` 中附带完整中间状态：实现直接，但会让正常消费方背负额外噪音和兼容负担。
- 仅依赖日志输出：人眼排查方便，但不利于测试断言，也不便于 JSON 化展示。

### 决策: debug 轨迹以“轮次摘要 + 最终失败原因”为主，不记录不可控的全部原始上下文

调试轨迹重点记录：

- 每轮规划的序号
- 模型返回的结构化响应快照
- 本轮是否命中 schema/语义校验错误
- 若发生修复，传给下一轮的修复反馈
- 最终返回前的失败分类和原因

如果底层 agent 能直接暴露工具调用记录，则将其纳入 debug 轨迹；若当前集成层无法稳定获取，则至少保留“本轮是否进入修复”和最终错误原因，先把最关键的黑盒缺口补上。

考虑过的替代方案：
- 记录完整 prompt、全部消息和底层 token 细节：信息最全，但噪音过大，也更容易受底层 SDK 差异影响。
- 只记录最终异常字符串：太薄，仍无法解释多轮修复过程。

### 决策: 保留三态协议，但为失败增加更精确的解释字段

本次设计不新增第四种 planner 状态，而是在 `needs_human` 和 `blocked` 分支中增强解释信息，明确区分：

- 证据不足或目标不唯一导致的真实澄清
- 依赖错误导致的阻塞
- 结构化输出或 `TaskDocument` 校验未收敛导致的内部失败

当 `needs_human` 的根因是“planner 未能产出合法 TaskDocument”时，返回体和 debug 输出必须让调用方能直接看出这一点，而不是只看到泛化的“请补充关键细节”。

考虑过的替代方案：
- 引入新的 `invalid_output` 状态：语义更直接，但会扩大既有契约范围，影响当前调用方。
- 完全复用当前固定文案：兼容最强，但无法解决误导问题。

### 决策: smoke 脚本增加显式 debug 开关，并提供面向人类的故障摘要

`smoke/test_planner.py` 将增加适合手动排查的 debug 入口，例如额外 CLI 开关，用于：

- 打印调试轨迹
- 展示最后一次校验失败原因
- 在 `needs_human` 下区分“缺少业务信息”和“内部文档校验失败”

人类可读输出会保持“先摘要、再展开 debug”的结构；JSON 输出则直接包含 debug 负载，便于复制、存档和测试。

考虑过的替代方案：
- 单独新增一个 debug 脚本：隔离清晰，但会复制大部分 smoke 入口逻辑。
- 始终输出完整 debug：排查方便，但日常运行过于嘈杂。

## 风险 / 权衡

- [debug 轨迹字段过于依赖底层 agent 返回结构] → 优先记录本层可稳定获得的数据，把工具调用明细设计为“可选增强”。
- [调试信息过多导致输出难读] → 默认保持关闭，仅在显式 debug 模式下展开。
- [失败语义增强后仍沿用三态，调用方可能误解] → 在 smoke 输出和结构化字段中明确标注根因分类。
- [测试需要同时覆盖普通模式与 debug 模式] → 为脚本与 planner 分别增加最小代表性用例，避免回归。

## Migration Plan

1. 为 planner 结果设计可选 debug 负载与失败根因分类。
2. 在 `planner.plan()` 的多轮修复流程中累积调试轨迹，并在失败时保留最后一次校验上下文。
3. 为 `smoke/test_planner.py` 增加 debug CLI 和面向人类的故障摘要展示。
4. 补充单元测试与 smoke 脚本测试，覆盖普通模式、debug 模式、修复失败和依赖故障。
5. 若新输出对调用方兼容性产生疑问，可通过默认关闭 debug 和保留旧字段来回滚。

## Open Questions

- debug 轨迹是否需要包含完整原始 prompt，还是只保留修复反馈与结构化输出摘要即可？
- 底层 Deep Agents 当前是否能稳定暴露工具调用事件；若不能，本次是否仅先落地 planner 层轨迹？
- 对于“非法 TaskDocument 修复失败”的情况，是否需要额外标准化一个 machine-readable 根因字段？
