# DND5E 非完整规则知识库说明

本文档说明当前项目中的 DND5E 非完整规则知识是如何进入 Qdrant 集合 `trpg_knowledge` 的，重点描述当前已覆盖的数据来源、节点组织方式、payload 字段，以及这些信息在检索阶段的用途。

## 1. 当前覆盖范围

当前导入的资料来源包括：

- `data/怪物图鉴2025`
- `data/玩家手册2024`
- `data/城主指南2024`

这套数据并不是一份完整的 DND5E 全量知识库，而是当前项目已接入、可被统一检索的一批中文规则资料。因此更准确地说，它是一套“可检索的 DND5E 部分规则知识集合”。

## 2. 集合定位

统一集合名为 `trpg_knowledge`。集合中的每条记录都表示一个可检索节点：

- 可能是一个完整实体，例如某个怪物、法术、专长
- 也可能是该实体或某篇规则文章下面的一个局部子块

当前组织策略是“父子节点 + 多文档类型”。

## 3. 父子节点关系

父子关系通过 `parent_id` 表达：

- 父节点的 `parent_id` 为 `null`
- 子节点的 `parent_id` 指向所属父节点

这样做的好处是：

- 检索时可以优先命中更细粒度的内容块
- 命中后还能沿着父节点回收更完整的上下文
- 在召回精度和回答完整性之间取得平衡

## 4. 当前支持的文档类型

当前 `doc_type` 包括：

- `monster`
- `spell`
- `rule_article`
- `dm_advice`
- `class_article`
- `subclass_article`
- `feat`
- `table`

这些类型共同覆盖了实体型知识、说明文知识和表格型参考知识。

## 5. 三类主要来源的数据组织

### 5.1 怪物图鉴

怪物图鉴按“一个怪物 = 一个主实体”入库。

常见结构：

- 一个 `monster` 父节点
- 若干个 `monster` 子节点

父节点通常保存怪物全卡全文，子节点通常对应：

- `基础属性`
- 各个动作或特性小节

### 5.2 玩家手册

玩家手册是混合型来源，常见映射如下：

- 法术页 -> `spell`
- 职业/子职业页 -> `class_article` / `subclass_article`
- 专长页 -> `feat`
- 一般规则说明 -> `rule_article`
- 页内表格 -> `table`

法术通常会拆成：

- 一个 `spell` 父节点
- 一个 `spell` 子节点：头信息
- 一个 `spell` 子节点：效果正文
- 若干个 `table` 子节点

职业、子职业和专长页面则通常会拆成“主条目 + 子节 + 表格”。

### 5.3 城主指南

城主指南当前主要按说明文知识入库，使用 `dm_advice` 类型。

常见结构：

- 一个 `dm_advice` 父节点
- 若干个 `dm_advice` 子节点
- 若干个 `table` 子节点

如果页面标题层级不明显，则会退化为按段落组切块。

## 6. Qdrant 中每条记录包含什么

每个节点写入 Qdrant 时都会变成一个 point，由三部分组成：

- `id`
- `vector`
- `payload`

### 6.1 Point ID

`id` 由节点的稳定 `unique_key` 派生，因此同一源节点重复导入时会得到稳定 ID。

### 6.2 向量字段

当前每条记录会同时写入两种向量：

- `dense`
- `sparse`

`dense` 用于语义检索，`sparse` 用于关键词检索，两者共同组成混合检索能力。

### 6.3 Payload 字段

当前 payload 已经收敛为 7 个字段：

- `book`
- `path`
- `doc_type`
- `title`
- `parent_id`
- `section_titles`
- `text`

其中：

- `book` 和 `path` 用于来源定位
- `doc_type` 用于区分节点类别
- `title` 用于标题展示
- `parent_id` 用于父子关系回溯
- `section_titles` 用于保留章节路径
- `text` 用于命中后回显和上下文回收

## 7. 为什么保留 `text`

尽管 `text` 会让 payload 变大，但当前仍保留它，因为它直接支撑：

- 检索命中后的摘要展示
- 回答阶段的上下文回收
- 调试时对命中内容的快速核查

这也是当前 payload 中唯一保留下来的大字段。

## 8. 表格如何存储

表格不会被简单压平成普通段落，而是作为独立的 `table` 节点写入。

这样做可以：

- 保留表格作为单独语义单元
- 支持按表头、行值、规则项进行检索
- 与普通正文节点区分开

表格节点通常也是某个父节点下的子节点，因此会带有：

- `parent_id`
- `section_titles`

## 9. 当前默认配置

当前默认配置位于 [ingest.toml](/home/naifen/code/trpg-rag/ingest.toml)，关键项包括：

- Qdrant collection：`trpg_knowledge`
- dense 模型：`BAAI/bge-m3`
- sparse 模型：`Qdrant/bm25`
- 单批写入大小：`128`

## 10. 维护建议

后续如果继续扩展这套 DND5E 非完整规则知识，优先关注：

1. 新增 `doc_type`
2. 保持父子节点关系稳定
3. 避免在不更新文档的情况下修改 payload schema

如果未来要引入更完整的 DND5E 数据源，建议继续复用这套“父子节点 + 混合向量 + 最小 payload”结构，而不是再引入新的并行 schema。
